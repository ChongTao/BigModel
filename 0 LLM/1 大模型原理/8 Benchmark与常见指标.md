# 八 Benchmark 与常见指标

## 8.1 什么是 Benchmark

`Benchmark`（基准测试）是一套用于**可重复地评估和比较**模型、系统或方案的方法。它通常不只是一个分数，而由以下部分共同构成：

- 明确的评测目标，例如知识问答、代码生成、检索、推理速度或 Agent 任务执行；
- 固定或清晰定义的测试数据、任务和输入；
- 评分规则与一个或多个指标；
- 可复现的运行条件，例如模型版本、提示词、硬件、并发和采样参数；
- 结果报告方式，包括平均表现、分组表现和失败案例。

因此，Benchmark 回答的不是笼统的“谁更好”，而是在**相同任务、相同规则和相同条件下，谁在某个维度表现更好**。

一个 Benchmark 的价值，取决于它是否与真实使用场景相符、是否可复现，以及结果是否能帮助决策。高分不必然意味着线上体验好：测试集可能与业务任务不同，单一指标也可能掩盖成本、延迟、安全或长尾失败。

## 8.2 Benchmark、评测指标与排行榜的关系

三者容易混用，但含义不同：

- **Benchmark**：完整的评测方案，包括任务、数据、规则、环境和指标。
- **Metric（指标）**：把某一维表现转成数值的方法，例如 Accuracy、F1、Recall@K、P95 延迟。
- **Leaderboard（排行榜）**：将不同参评对象按某个 Benchmark 的结果展示出来。

例如，某个代码生成 Benchmark 可以包含一批编程题，以“单元测试是否通过”为评分规则，以 `pass@1` 为指标；排行榜则列出各模型的 `pass@1`。若模型版本、提示词、工具权限或测试环境不同，排行榜数字就未必能直接比较。

## 8.3 常见评测类型

### 8.3.1 模型能力评测

用于衡量模型在知识、语言理解、数学推理、代码、长上下文或多模态任务上的能力。常见形式包括选择题、问答题、代码题和结构化抽取任务。

这类评测适合做模型选型和版本回归，但要警惕训练数据污染、题目过于固定，以及测试集与业务场景不匹配。

### 8.3.2 生成质量评测

用于评估摘要、翻译、问答、写作等开放式生成结果。自动指标有助于快速比较，但通常还需要人工评审或 LLM-as-a-Judge 来判断正确性、完整性、事实性和风格。

### 8.3.3 检索与 RAG 评测

用于判断系统是否找回了正确证据、是否将其正确用于回答，以及端到端结果是否可靠。除质量外，还应关注引用正确性、延迟和成本。

详见 [RAG评测](../../2%20RAG/11%20RAG%E8%AF%84%E6%B5%8B.md)。

### 8.3.4 Agent 评测

用于衡量 Agent 能否完成多步骤任务，以及工具调用、过程效率、恢复能力和安全边界是否符合要求。只看最终结果往往不足，还应检查执行轨迹。

详见 [Agent评测](../../1%20Agent/3%20%E8%BF%90%E8%A1%8C%E6%97%B6/7%20Agent%E8%AF%84%E6%B5%8B.md)。

### 8.3.5 系统与推理性能评测

用于衡量部署系统的响应速度、吞吐、资源消耗和稳定性。它评测的是系统实现和运行条件，而不是模型知识能力本身。

详见 [推理性能指标与Benchmark](../5%20%E6%8E%A8%E7%90%86%E5%B7%A5%E7%A8%8B/9%20%E6%8E%A8%E7%90%86%E6%80%A7%E8%83%BD%E6%8C%87%E6%A0%87%E4%B8%8EBenchmark.md)。

## 8.4 常见质量指标

### 8.4.1 Accuracy（准确率）

`Accuracy = 正确样本数 / 全部样本数`

适合类别较均衡、每个样本同等重要的分类或选择题任务。类别极不均衡时可能产生误导：例如 99% 样本为负类时，始终预测负类也能得到 99% Accuracy。

### 8.4.2 Precision、Recall 与 F1

- `Precision = TP / (TP + FP)`：预测为正的结果中，有多少是真的正例；关注“误报少不少”。
- `Recall = TP / (TP + FN)`：所有真实正例中，有多少被找出来；关注“漏报多不多”。
- `F1 = 2 × Precision × Recall / (Precision + Recall)`：Precision 和 Recall 的调和平均。

其中 `TP`、`FP`、`FN` 分别是真正例、假正例和假负例。风险检测常更重视 Recall，垃圾内容拦截等场景则往往也要严格控制 Precision；不能只报 F1 而不说明取舍。

### 8.4.3 Exact Match（EM）与 Pass Rate

`Exact Match` 要求预测与标准答案完全一致，适合答案格式唯一的抽取、数学短答或结构化任务；它对合理但表达不同的答案很严格。

`Pass Rate` 表示通过预先定义验证条件的比例。例如代码题可用单元测试是否通过来判定。验证规则应明确，避免“看起来正确”却无法复现。

### 8.4.4 ROUGE、BLEU 与 BERTScore

- `ROUGE`：主要看生成文本与参考答案的词或片段重叠，常用于摘要。
- `BLEU`：主要看 n-gram 精确率，常用于机器翻译。
- `BERTScore`：用语义向量相似度衡量生成内容与参考答案的接近程度。

这些指标衡量的是与参考文本的接近程度，不等同于事实正确或真正有用。开放式任务应补充人工评审，或采用定义清晰的裁判模型评测。

### 8.4.5 人工评审与 LLM-as-a-Judge

面对开放回答，可按正确性、完整性、事实性、相关性和表达质量等维度打分或两两比较。人工评审更可靠但成本较高；LLM-as-a-Judge 更易规模化，但应固定评审提示词和模型版本，并用人工抽样校验其偏差。

## 8.5 检索和排序常见指标

检索任务通常关心“相关文档是否被找回”以及“是否排在足够靠前的位置”。`K` 表示只看前 K 个结果。

- `Recall@K`：前 K 个结果是否覆盖了应找回的相关文档；适合关注漏召回。
- `Precision@K`：前 K 个结果中相关文档的比例；适合关注结果噪声。
- `MRR`：第一个正确结果排名倒数的平均值；越早出现正确结果越好。
- `nDCG@K`：考虑位置权重和多级相关性的排序指标；高相关结果排得越靠前，得分越高。

对于 RAG，检索指标只能说明证据是否到位，不能替代最终回答的正确性、忠实性和引用质量评测。

## 8.6 系统性能与成本指标

- **Latency（延迟）**：一次请求从发出到完成所需时间；应同时报告 P50、P95、P99 等分位数，避免平均值掩盖慢请求。
- **TTFT**：Time To First Token，用户收到第一个输出 token 的等待时间，尤其影响流式对话体验。
- **Throughput（吞吐）**：单位时间完成的请求数或处理的 token 数；必须说明统计的是输入、输出还是总 token，以及并发条件。
- **Error Rate（错误率）**：请求失败、超时或被错误拒绝的比例。
- **Cost（成本）**：可按单请求、单任务、每千 token 或成功任务计算；应结合任务成功率看，而非只看绝对价格。
- **Resource Utilization（资源利用率）**：GPU、CPU、内存或缓存使用情况，用于定位瓶颈，不能单独代表用户体验。

## 8.7 如何正确解读 Benchmark 结果

阅读或发布结果时，至少确认以下问题：

1. 测的是什么任务，是否代表目标业务？
2. 测试集、样本量、数据版本和评分规则是什么？
3. 模型版本、提示词、采样参数、工具权限和硬件条件是否一致？
4. 报告的是平均分、分组分还是最优单次结果？是否有置信区间或多次运行结果？
5. 是否同时呈现质量、延迟、成本、安全等必要维度？
6. 失败样本集中在哪些任务或人群，而不是只看总分？

一个可用于工程决策的评测，通常应先用公开 Benchmark 理解能力边界，再用贴近自身数据和流程的任务集做离线回归，最后在受控线上流量中验证真实效果。

## 8.8 总结

Benchmark 是一套可复现的比较方法，指标只是其中的计分工具。没有放在明确任务、数据和运行条件中的分数，比较价值很有限。

选择指标时，应从目标反推：分类任务关注 Accuracy、Precision、Recall、F1；检索任务关注 Recall@K、MRR、nDCG；生成任务补充事实性和人工或裁判评审；系统上线还必须关注延迟、吞吐、错误率和成本。最终应以多维结果而非单一排行榜分数支持决策。
