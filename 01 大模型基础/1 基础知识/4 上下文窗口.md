# 上下文窗口

一次模型调用能同时处理的 Token 总量叫上下文窗口。输入与输出共享这个预算，它决定了一次请求能装多少资料、多轮对话能保留多少历史，也直接影响成本和延迟。

## 1. 上下文窗口是什么

上下文窗口（Context Window）是一次模型调用中模型能处理的 Token 总量上限，按 Token 计量，不按字符或页数计量。每次调用都是独立的：模型不会自动记得上一轮请求，之前说过的内容必须重新放进这一次的上下文，模型才看得到。

### 1.1 三个容易混淆的上限

| 名称 | 限制的是什么 | 常见形式 |
| --- | --- | --- |
| 上下文窗口 | 一次调用中输入与输出的 Token 总和 | 32K、128K、1M 等标称值 |
| 最大输入 | 只限制请求侧的 Token 数 | 可能小于窗口，为输出预留空间 |
| 最大输出 | 只限制生成的 Token 数 | 由 `max_tokens` 等参数控制 |

三者同时生效：`输入 Token + 输出 Token ≤ 上下文窗口`，且输入不超过最大输入、输出不超过最大输出。

### 1.2 上下文窗口决定了什么

- 一次请求能容纳多少指令、资料和示例
- 多轮对话能保留多少历史，超出后必须裁剪或摘要
- 长文档和 RAG 召回内容能装进去多少
- 成本与延迟随长度上升的速度

因此很多工程问题表面上看是“模型不够聪明”，本质是“上下文装不下”或“上下文太乱”。

### 1.3 多轮对话与 Agent 场景

对话接口自身不保存历史，框架会把 system 提示、历史消息和工具返回值全部拼进每一次新请求。轮数越多输入越长，费用与首 Token 延迟随之上升。

## 2. 窗口大小由什么决定

| 因素 | 决定什么 | 说明 |
| --- | --- | --- |
| 位置编码方案 | 模型能表示多长的位置关系 | RoPE 及其外推、内插改造是扩展窗口的主要手段 |
| 训练时的序列长度 | 模型是否真的在长序列上训练过 | 只在短序列上训练，放大窗口不保证可用 |
| 注意力机制与显存 | 长序列的工程可行性 | 注意力计算量与 KV Cache 随长度增长 |
| 部署配置 | 实际可用的上限 | 服务端可能按显存和吞吐另行限制 |

## 3. 标称长度不等于有效长度

模型标称支持 128K 甚至更长，不代表在这个长度下仍能稳定找到并使用关键信息。

- **位置有影响**：同样的关键信息放在开头或结尾比放在中段更容易被用上，即 Lost in the Middle 现象。
- **大海捞针不够**：needle-in-a-haystack 只测能否找到一句被插入的话，不测多跳推理、信息聚合与长文改写。
- **要按任务评测**：RULER 这类基准用多类任务在不同长度上测有效上下文，结果通常明显低于标称值。

## 4. 上下文预算怎么花

### 4.1 先算输入的固定开销

除了资料本身，一次请求里还有不少容易漏算的部分：

- system 提示与角色设定
- 对话模板注入的角色分隔与起止标记
- 工具定义与调用格式说明
- 历史消息与历史工具返回值
- 输出格式要求与 few-shot 示例

### 4.2 给输出留余量

输入塞满窗口会挤压可用输出空间，表现为回答被截断或直接报错。做法是先确定期望输出长度，再用 `窗口 - 期望输出 - 安全余量` 反推输入上限，而不是把输入顶到最大值。

### 4.3 超预算时的裁剪优先级

1. 去掉与当前问题无关的历史轮次和旧工具输出
2. 保留 system 提示、任务指令和输出格式要求
3. 对长资料先检索或摘要，只放最相关片段
4. 最近若干轮保留原文，较早历史用摘要代替
5. 仍超限时按重要性截断，并显式告知模型内容有删减

## 5. 超限会发生什么

| 情况 | 行为 | 风险 |
| --- | --- | --- |
| 接口直接拒绝 | 返回长度超限错误 | 请求失败，需应用侧裁剪后重试 |
| 静默截断输入 | 头部或尾部内容被丢弃 | 模型没看到关键信息，答案看着合理却是错的 |
| 输出被截断 | 触到 `max_tokens` 或窗口上限 | JSON、代码等结构化输出不完整，解析失败 |
| 框架自动裁剪历史 | 由 Agent 框架或 SDK 决定保留策略 | 裁剪规则不透明，可能丢掉必要上下文 |
