# 05 Prompt Cache

Prompt Caching（提示缓存，本文简称 Prompt Cache）是推理系统对符合条件的提示前缀复用已处理状态的能力。命中时，系统可以减少该前缀的重复预填充计算；在部分 API 平台上，缓存输入还使用不同的计费费率。

Prompt Cache 缓存的是可复用的前缀计算状态，不是最终答案。缓存不会删除提示内容，也不会减少这段内容占用的模型上下文额度；当前问题和新增内容仍需处理，生成答案也仍需执行。

不同厂商 API 和自部署推理框架对 Prompt Cache、Prefix Cache 的实现与控制方式不同。本文将它们作为相关但不完全等同的能力介绍。

## 1. 概念与边界

### 1.1 Prompt Cache 优化什么

许多应用的请求会重复携带较长的固定内容，例如系统指令、工具定义、输出规范或同一份文档。满足平台的缓存条件时，后续请求可以复用相同前缀的处理结果，减少重复预填充工作；API 平台也可能对缓存读取使用不同价格。

常见的稳定内容包括：

- 长期稳定的系统指令和输出约束。
- 顺序及定义基本稳定的工具描述。
- 多个请求共同使用的规范、模板或文档版本。
- Agent 工作流中重复使用的固定运行规则。

Prompt Cache 主要优化重复前缀的推理开销。它不提升模型本身的回答质量，也不代替上下文压缩、结果缓存或应用层的权限控制。

### 1.2 与相关缓存机制的区别

| 机制 | 主要缓存内容 | 典型作用 |
| --- | --- | --- |
| 请求内 KV Cache | 当前请求已处理 Token 对应的注意力 Key/Value 状态 | 生成后续 Token 时复用当前请求的历史状态 |
| Prefix Cache | 多个请求共同前缀对应的推理状态；自部署框架可能以 KV 块形式管理 | 减少相同前缀的重复预填充计算 |
| 厂商 API Prompt Caching | 按 API 规则可复用的提示前缀状态，内部实现由平台决定 | 减少符合条件的重复计算；部分平台对缓存读取采用优惠费率 |
| 应用结果缓存 | 已生成的完整答案，或应用定义的相似请求结果 | 命中时可以直接复用旧答案，通常不需要重新生成 |

厂商提供的 Prompt Caching 和自部署 Prefix Cache 有相似目标，但开发者看到的边界、配置、缓存生命周期和计费方式并不相同。不要据 API 的功能名称推断其底层实现一定与某个开源推理框架完全相同。

### 1.3 与上下文长度和成本的关系

缓存命中的前缀仍然是模型当前上下文的一部分，依然占用上下文窗口。缓存优化的是前缀的重复处理；它不等同于删除输入 Token，也不会自动减少本轮动态内容、输出 Token 或重试带来的成本。

API 平台可能区分未缓存输入、缓存写入和缓存读取的使用量与价格；自部署推理系统的收益则更多体现为预填充计算、显存管理和服务吞吐。具体成本应按平台公布的价格和使用量核算。

## 2. 工作方式与命中条件

### 2.1 基本流程

一个常见的前缀复用流程如下：

1. 请求包含达到平台要求的提示前缀。
2. 推理系统处理请求；如果平台启用缓存且请求符合规则，系统可能保留可复用的前缀状态。
3. 后续请求到达时，系统按平台定义的范围、断点和匹配规则查找可用前缀。
4. 命中后复用匹配部分，并继续处理剩余内容和生成答案；未命中时则按平台规则重新处理。

“首次请求像预热、后续必定命中”不是可靠假设。首次请求可能不满足最小长度或写入条件；后续请求也可能受到缓存过期、容量淘汰、路由、模型配置或缓存隔离范围的影响。

### 2.2 前缀匹配与缓存断点

Prompt Cache 通常不是语义缓存：“主题相似”不意味着可以命中。是否复用取决于提供方或推理框架定义的匹配规则，包括请求结构、前缀内容、模型和缓存断点等因素。

设计时应注意：

- 共享前缀之后再追加变化内容，通常更有利于复用共享部分。
- 前缀某处变化时，其后的内容可能不再属于可复用前缀；变化之前的稳定部分仍可能按平台规则命中。
- 有的平台按显式断点或模型规定的边界匹配；最小可缓存长度和匹配粒度因模型与平台而异。
- 字段顺序、工具顺序和序列化方式可能影响匹配，但具体行为取决于 API 如何组装及规范化请求。
- 不要仅凭请求文本“看起来相同”推断一定命中；应观察平台返回的缓存使用量。

### 2.3 缓存生命周期与作用范围

缓存可能受 TTL、容量淘汰、模型版本、路由、工作区或组织范围等因素影响。请求中带有相同会话标识，也不代表缓存一定存在或一定命中。

缓存键、断点和 TTL 是平台提供的缓存控制参数，不是用户身份验证或访问控制机制。业务仍需独立校验用户、租户和资源权限。

## 3. 适用场景

| 场景 | 适合复用的内容 | 需要注意 |
| --- | --- | --- |
| 长系统提示 | 稳定的角色说明、安全规则和输出约束 | 规则更新时应使用新版本，避免沿用过期前缀 |
| 工具较多的 Agent | 工具定义、参数规范和固定工作流说明 | 工具集合或定义变化后，缓存边界和命中情况可能改变 |
| 长文档问答 | 同一文档版本的正文或共同背景 | 将每轮问题放在共享正文之后；文档更新后应使用新版本 |
| 多轮复杂任务 | 长期不变的项目规则和任务说明 | 会话摘要、个人状态和最新工具结果往往会变化，不要误当作全局共享前缀 |
| 高频重复工作流 | 大量请求共同使用的固定模板或规则 | 要有足够的复用次数，并在缓存有效期内复用，才能抵消写入或维护成本 |

缓存通常更适合“足够长、反复复用、前缀稳定”的请求。一次性请求、较短提示、变化频繁的前缀或低频调用，收益可能有限，甚至不划算。

## 4. 前缀设计与使用建议

### 4.1 稳定内容前置，变化内容后置

当目标平台按前缀复用时，可将请求概念上组织为：

~~~text
稳定共享部分：
  系统指令
  固定工具定义
  共享模板、规则或已版本化的文档

本次变化部分：
  当前用户问题
  时间戳和本轮参数
  最新检索结果
  用户或租户特定的状态
~~~

这是一种缓存布局建议，不是所有 API 的固定消息格式。应遵循目标 API 支持的角色和字段，同时验证内容顺序对任务质量的影响。不要为了提高命中率而挪动、削弱或混淆安全指令与用户数据的信任边界。

### 4.2 稳定序列化并管理版本

- 对平台参与前缀匹配的稳定内容使用一致的模板和序列化方式。
- 如果工具顺序或数组顺序会进入缓存前缀，保持其确定性；不要假设所有 API 都以相同方式处理字段。
- 规则、工具、文档或权限版本发生变化时，应按平台支持的方式更新前缀或缓存标识，避免继续复用旧内容。
- 避免在共享前缀中放置每请求变化的时间戳、随机 ID 或实时数据。
- 不要频繁改写稳定提示的标点、空白或文案；同时也不要为了缓存而保留已过期的规则。

### 4.3 显式断点和缓存键

部分平台支持自动识别缓存前缀，部分平台还提供显式缓存断点、缓存控制字段或缓存键。它们不是跨平台统一接口，使用前应核对目标 API 对模型、请求结构、最小长度、TTL 和计费的要求。

如果平台提供缓存键，应先确认它用于缓存路由、复用分组还是使用量归集。只有平台文档明确说明缓存键参与路由或复用时，才按稳定分组设计；有些模型会自动处理缓存路由，缓存键可能只用于分组计量。缓存键不能保证命中，也不能代替身份校验；是否共享缓存必须与租户、权限和数据范围相一致。

### 4.4 数据隔离与保留策略

- 只有在权限范围相同的请求之间，才应共享用户或租户相关的前缀。
- 不要把访问令牌、密钥等凭证加入提示；个性化数据、权限状态和私有检索内容应按租户及权限范围隔离，避免进入所有用户共用的前缀。
- 按提供方文档确认缓存的作用范围、存留时间、数据保留规则及适用的零数据保留策略。
- 不要把缓存命中或缓存键当成安全边界；应用层仍要执行授权与访问控制。

### 4.5 先保证上下文质量

稳定前缀有利于缓存复用，但不应让缓存结构主导上下文设计。指令、证据、历史和当前问题的顺序应结合模型和任务评估；统一标签和包装模板有助于表达结构，但不会自动提供权限隔离或抵御提示注入。

| 实现 | 可观察到的方式 | 使用时需确认 |
| --- | --- | --- |
| OpenAI API Prompt Caching | 当前指南区分隐式缓存和显式断点；断点策略、最小前缀与保留模式依模型及请求而异。部分模型支持 in_memory 与 24h 保留模式 | 查看模型条件、最小前缀、断点、保留模式和计费；默认保留策略可能受组织的数据保留设置影响。缓存按组织和区域隔离，路由到持有缓存实例也不保证 |
| Anthropic API Prompt Caching | 当前官方指南介绍自动缓存和显式缓存断点；可配置的 TTL 与断点匹配规则按其 API 文档执行 | 当前文档列出 5 分钟和 1 小时 TTL 选项，并要求到缓存断点（含断点所标记内容）为止的前缀精确匹配；具体支持和价格应以当前文档为准 |
| vLLM Automatic Prefix Caching | 自部署推理服务可复用匹配前缀的 KV 状态，降低重复预填充开销 | 关注缓存容量、淘汰、并发和实际服务吞吐；这是推理计算优化，不是 API 缓存输入折扣 |
| SGLang UnifiedRadixCache / Session-Aware Radix Cache | 以 Radix Cache 管理可复用的前缀 KV；启用会话感知功能后，可在淘汰时优先保留仍被活动会话引用的 KV | `session_id` 只标记缓存引用，不会追加或重建对话上下文；每次请求仍需提供本轮需要的 Prompt。会话引用也不是永久 pin，内存压力下仍可能淘汰 KV |

SGLang 的会话感知缓存只适用于相应的 UnifiedRadixCache 实现，其驱逐策略和缓存生命周期需结合部署版本配置。可参阅 [Session-Aware Radix Cache](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/session_radix_cache.mdx) 与 [Radix Cache Eviction Policies](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/radix_eviction_policy.mdx)。

厂商 API 的缓存计量与自部署 Prefix Cache 的资源指标不同，评估时不要混用“缓存读取价格”“KV 块命中”和“缓存请求命中率”等口径。

## 6. 收益、限制与评估

### 6.1 收益和限制

Prompt Cache 可能带来的收益：

- 降低重复前缀的预填充耗时。
- 在提供缓存读取优惠费率的平台上，降低重复输入的部分成本。
- 在自部署系统中减少重复预填充计算，为服务吞吐留出资源。

需要同时考虑这些限制：

- 缓存不会缩短提示内容，也不会减少它占用的上下文长度。
- 缓存命中不改善模型回答质量，也不会替代对输出质量的评测。
- 缓存创建、续期或未命中可能产生成本；收益取决于复用频率和缓存生命周期。
- 前缀、模型、路由或缓存范围变化可能降低命中率。
- 具体计费和使用量字段由平台定义，不同平台之间不宜直接比较单一命中率。

### 6.2 监控指标

应结合平台报告字段和自部署框架指标，至少观察：

| 指标 | 用途 |
| --- | --- |
| 缓存读取 Token 与缓存写入 Token | 了解实际复用和创建规模 |
| 缓存 Token 占输入 Token 的比例 | 比单看“命中请求数”更能反映复用覆盖面 |
| 缓存命中率与缓存重建情况 | 发现前缀变化、TTL、路由或淘汰造成的失效 |
| 缓存前后总成本 | 按实际的未缓存、写入、读取和输出价格核算 |
| 首 Token 延迟及端到端延迟 | 确认缓存是否改善用户可感知时延 |
| 每个成功任务的成本和质量 | 防止以缓存率上升换来错误回答或额外重试 |

按模型、提示版本、工作流和租户等维度汇总数据，有助于定位命中率变化。日志应遵循数据最小化原则，避免为诊断缓存而记录不必要的原始提示内容。

### 6.3 评估净收益

应在代表性流量下对比启用与未启用缓存时的完整成本、延迟和任务质量，并计入缓存写入、缓存读取、未命中请求、输出、重试和缓存过期后的重建。缓存读取是否优惠、写入如何计价，都要按提供方当前规则计算。

缓存只有在复用带来的收益超过创建、维护和失效成本时才有价值。成本口径和缓存治理指标可参考[生产成本治理](../../05%20生产工程/成本与延迟/成本.md)。

## 7. 与 Prompt Engineering 和 Context Engineering 的关系

Prompt Engineering 关注指令、示例和输出要求；Context Engineering 负责为每次调用选择并组织提示、历史、检索结果、工具和状态。Prompt Cache 是推理服务或平台提供的复用能力，开发者可通过稳定的上下文结构提高复用机会，但不能把缓存当成提示优化或上下文质量本身。

- [Context Engineering](03%20Context%20Engineering.md) 介绍上下文的选择、顺序、生命周期和预算。
- [上下文压缩](04%20上下文压缩.md) 介绍筛选或改写内容；压缩内容变化时，应重新评估缓存前缀。
- [对话模板与上下文装配](02%20对话模板与上下文装配.md) 介绍消息结构与请求装配。
