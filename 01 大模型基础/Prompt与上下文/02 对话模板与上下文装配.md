# 对话模板与上下文装配

模型 API 接收的对话消息，通常会被转换成模型专用的 Token 序列。理解这一步有助于排查角色错乱、工具调用格式错误、提示词缓存未命中和多模态输入预算异常等问题。

## 一、消息接口与模型输入

应用层通常以消息数组表达一次对话，例如：

```json
[
  {"role": "system", "content": "你是一个严谨的助手。"},
  {"role": "user", "content": "请总结这段材料。"}
]
```

服务端会根据模型的 Chat Template，将消息边界、角色、内容和生成位置序列化为模型认识的特殊 Token。不同模型的模板和结束标记可能不同，因此：

- 训练、微调和推理应使用与模型匹配的模板。
- 对话格式应通过模型或服务端提供的模板实现，不要假设所有模型都使用同一套特殊 Token。
- assistant 消息结束、单轮结束和整段对话结束可能是不同标记。
- 对开放权重模型，直接把消息拼成普通文本可能造成角色边界和生成位置错误。

Hugging Face Transformers 的 [Chat Templates 文档](https://huggingface.co/docs/transformers/chat_templating)展示了将消息列表转换为模型输入的常见方式。

## 二、常见消息角色

| 角色 | 常见用途 | 装配注意点 |
| --- | --- | --- |
| system | 全局任务原则和稳定约束 | 内容尽量稳定，避免堆积无关背景 |
| developer | 应用侧指令、输出规范和产品限制 | 由应用控制，明确区分于用户提供的内容 |
| user | 当前用户问题、材料或多模态输入 | 明确具体任务和必要的输入边界 |
| assistant | 模型此前的回答、工具调用意图或当前生成 | 多轮场景保留必要状态，避免无限追加所有历史 |
| tool | 外部工具返回的结果 | 标记来源与可信度；工具输出仍需验证和控制长度 |

不同 API 可能采用不同角色名称、消息字段或权限语义。调用前应遵循目标 API 的消息协议，而不是只依赖上述通用概念。

## 三、上下文预算如何分配

上下文窗口按 Token 计量。实际请求需要给输入和输出共同留出空间，并考虑多模态输入的模型专用计量方式。

可把输入预算拆成：

1. 稳定指令和输出约束
2. 当前用户问题
3. 必要的对话历史或任务状态
4. 检索资料、工具结果或引用内容
5. 多模态内容的编码预算
6. 预留的模型输出 Token

装配时优先保证当前任务、关键约束和高价值证据可见。过期对话、重复资料和冗长工具输出应摘要、筛选或删除。详细的上下文设计见 [03 Context Engineering](03%20Context%20Engineering.md)，压缩策略见 [04 上下文压缩](04%20上下文压缩.md)。

## 四、把可信指令与外部资料分开

用户文档、网页、RAG 片段和工具结果可能包含与应用指令冲突的文本。上下文装配应尽量保留来源标记，并在模板中把外部材料清楚地界定为“待分析数据”：

- 明确标记引用资料的起止边界和来源。
- 将应用策略、用户请求与外部材料放在不同消息或明确分隔区。
- 不让检索片段或工具返回内容直接覆盖系统策略。
- 对影响权限、付款、删除或外发的动作进行应用侧校验。

角色或 XML/Markdown 分隔符有助于表达结构，但本身不构成安全边界；关键权限仍需在应用和工具层执行。

## 五、多模态上下文

多模态消息的 content 可能是文本、图像、音频、视频帧或结构化片段的组合。消息体看起来只有一个附件，模型内部却可能展开为多个图像裁剪、音频片段或时间帧。

- 图像分辨率和裁剪策略会影响 Token 与费用。
- 音频任务要区分转写、理解、语音生成和实时对话。
- 视频需要保留帧的时间信息；只抽取少量帧会影响事件理解。
- 多模态内容的可用格式、长度限制和预算按模型/API 而异。

因此应在目标模型上测试真实输入，而不是仅以文本字符数估算窗口占用。

## 六、一次请求的检查清单

- 消息角色和模板是否符合目标模型的要求？
- 输入中是否同时包含当前任务、必要资料和正确的来源边界？
- 历史记录是否有足够状态，也有没有无关内容占用预算？
- 是否预留输出空间，并处理输入超长时的截断或压缩？
- 结构化输出是否通过 Schema 或程序校验，而不是只靠文字约定？
- 多模态格式、分辨率、音频时长和视频采样是否符合服务限制？
