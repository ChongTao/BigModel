# 对话模板与上下文装配

托管模型 API 或本地推理运行时会把消息或结构化输入项转换为目标模型可处理的输入表示。理解消息装配和序列化，有助于排查角色错乱、工具调用格式错误、提示词缓存未命中和多模态输入预算异常。

## 一、消息接口与模型输入

聊天接口通常以带角色的消息数组表达一次对话，例如：

```json
[
  {"role": "system", "content": "你是一个严谨的助手。"},
  {"role": "user", "content": "请总结这段材料。"}
]
```

托管 API 通常在服务端完成消息序列化；开放权重模型则可能由 tokenizer 或推理框架应用模型对应的 Chat Template，将消息边界、角色、内容和生成位置转换为模型输入。不同模型的模板和结束标记可能不同，因此：

- 训练、微调和推理应使用与模型匹配的模板。
- 对话格式应通过模型或服务端提供的模板实现，不要假设所有模型都使用同一套特殊 Token。
- assistant 消息结束、单轮结束和整段对话结束可能是不同标记。
- 对开放权重模型，直接把消息拼成普通文本可能造成角色边界和生成位置错误。

上面的 JSON 仅用于说明角色消息的概念结构，并非所有 API 都能直接使用的请求体。部分接口使用 input 字段、内容块或其他结构化输入项；实际字段和角色语义应以目标 API 为准。

Hugging Face Transformers 的 [Chat Templates 文档](https://huggingface.co/docs/transformers/chat_templating)展示了将消息列表转换为模型输入的常见方式。

## 二、常见消息角色

| 角色 | 常见用途 | 装配注意点 |
| --- | --- | --- |
| system | 全局任务原则和稳定约束 | 内容尽量稳定，避免堆积无关背景 |
| developer | 应用侧指令、输出规范和产品限制 | 由应用控制，明确区分于用户提供的内容 |
| user | 当前用户问题、材料或多模态输入 | 明确具体任务和必要的输入边界 |
| assistant | 模型此前的回答、工具调用意图或当前生成 | 多轮场景保留必要状态，避免无限追加所有历史 |
| tool | 外部工具返回的结果 | 标记来源与可信度；工具输出仍需验证和控制长度 |

不同 API 可能采用不同角色名称、消息字段或权限语义。调用前应遵循目标 API 的消息协议，而不是只依赖上述通用概念。

### 工具调用与工具结果

工具调用是模型输出的结构化动作意图；工具结果由运行时执行后，按对应调用关联并交回模型。不同接口可能把调用表示为 assistant 消息，也可能使用独立的结构化项目；工具结果也不一定统一使用 tool 角色。

装配时应保留调用与结果的关联、顺序和类型，不要把调用意图或工具结果伪造成普通文本。应用还应在执行前校验工具权限、参数和可能产生的副作用。

## 三、单轮与多轮状态管理

### 单轮独立知识问答

单轮独立问答只处理当前问题，不依赖前序对话。单轮不等于不检索：问题涉及私有知识、最新资料或要求可追溯来源时，应用应先检索相关资料，再把有限、相关且带来源信息的证据装入当前请求。

一种概念性的装配方式是：

1. **应用指令**：按目标 API 支持的角色放置稳定规则，例如要求基于提供的证据作答、引用真实来源 ID、证据不足时说明无法确认。
2. **当前用户消息**：包含本次问题和检索资料；资料标记标题、来源 ID、章节或日期等必要元数据。
3. **输出约束**：要求回答只引用本次实际提供的来源；资料不能支持答案时，说明证据不足或提出澄清问题。

示例中的检索资料可以标为：

> - 问题：这项功能需要什么权限？
> - 检索资料：[source_id=kb-001；标题=产品手册；章节=账户权限]……
> - 输出要求：给出简短答案，并标注支持结论的 source_id；资料未说明时明确回答“资料中未说明”。

单轮请求通常不携带历史消息，也不需要续接已有会话状态。检索资料属于外部数据，应保留来源边界，不要因为其中出现指令性文字就提升其权限。RAG 链路见 [02 RAG 架构](../../02%20检索与RAG/RAG流程/02%20RAG架构.md)，答案忠实度和引用质量见 [07 RAG 评测](../../02%20检索与RAG/RAG流程/07%20RAG评测.md)。

### 多轮会话状态

多轮请求只应装入当前任务需要的历史消息或状态摘要，避免每轮无差别追加全部历史。如果新问题依赖“它”“刚才那个方案”等指代，应先利用相关历史还原问题，再按需要检索；不要用历史中没有的信息补全问题。

会话状态常见有两种管理方式：

- **应用管理**：应用每次选择必要的历史消息或摘要，并与当前问题一起发送。
- **API 管理**：由 API 通过响应 ID 续接，或通过持久化会话对象保存消息和工具交互。

例如，OpenAI Responses API 支持通过 previous_response_id 续接响应，也提供持久化的 Conversations API；会话对象可以保存消息、工具调用和工具结果。这些是特定 API 的能力，并非通用消息协议。单轮独立问答通常不需要复用响应 ID 或会话 ID；使用持久化状态前，还应确认目标服务的数据保留和删除策略。具体机制见 [OpenAI API：Conversation State](https://developers.openai.com/api/docs/guides/conversation-state)。

无论由应用还是 API 管理状态，历史内容都会影响上下文占用。不要同时重复传入 API 已续接的全部历史；应按目标 API 的状态语义选择一种装配方式，并验证续接后实际包含的消息和工具结果。

## 四、上下文预算如何分配

上下文窗口按 Token 计量。实际请求需要给输入和输出共同留出空间，并考虑多模态输入的模型专用计量方式。

可把输入预算拆成：

1. 稳定指令和输出约束
2. 当前用户问题
3. 多轮场景所需的对话历史或任务状态；独立单轮问答通常不带历史
4. 检索资料、工具结果或引用内容
5. 多模态内容的编码预算
6. 预留的模型输出 Token

装配时优先保证当前任务、关键约束和高价值证据可见。过期对话、重复资料和冗长工具输出应摘要、筛选或删除。详细的上下文设计见 [03 Context Engineering](03%20Context%20Engineering.md)，压缩策略见 [04 上下文压缩](04%20上下文压缩.md)。

## 五、把可信指令与外部资料分开

用户文档、网页、RAG 片段和工具结果可能包含与应用指令冲突的文本。上下文装配应尽量保留来源标记，并在模板中把外部材料清楚地界定为“待分析数据”：

- 明确标记引用资料的起止边界和来源。
- 将应用策略、用户请求与外部材料放在不同消息或明确分隔区。
- 不让检索片段或工具返回内容直接覆盖系统策略。
- 对影响权限、付款、删除或外发的动作进行应用侧校验。

角色或 XML/Markdown 分隔符有助于表达结构，但本身不构成安全边界；关键权限仍需在应用和工具层执行。

## 六、多模态上下文

多模态消息的 content 可能是文本、图像、音频、视频帧或结构化片段的组合。消息体看起来只有一个附件，模型内部却可能展开为多个图像裁剪、音频片段或时间帧。

- 图像分辨率和裁剪策略会影响 Token 与费用。
- 音频任务要区分转写、理解、语音生成和实时对话。
- 视频需要保留帧的时间信息；只抽取少量帧会影响事件理解。
- 多模态内容的可用格式、长度限制和预算按模型/API 而异。

因此应在目标模型上测试真实输入，而不是仅以文本字符数估算窗口占用。

## 七、一次请求的检查清单

- 消息角色和模板是否符合目标模型的要求？
- 本次请求是独立单轮还是多轮续接？是否只带入必要的历史状态？
- 输入中是否同时包含当前任务、必要资料和正确的来源边界？
- 若是知识问答，检索证据是否带有来源信息？证据不足时是否有明确处理方式？
- 若包含工具交互，调用意图、调用 ID 和工具结果是否按 API 结构正确关联？
- 历史记录是否有足够状态，也有没有无关内容占用预算？
- 是否预留输出空间，并处理输入超长时的截断或压缩？
- 结构化输出是否通过 Schema 或程序校验，而不是只靠文字约定？
- 多模态格式、分辨率、音频时长和视频采样是否符合服务限制？
