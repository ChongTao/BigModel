# 04 上下文压缩

上下文压缩（Context Compression）是在上下文窗口、成本或延迟预算有限时，对历史对话、检索材料、工具输出或任务状态进行筛选、提取、摘要或结构化处理，让下一次模型调用只携带完成当前步骤所需的信息。

压缩不等于把所有文本都改写得更短。它是一项上下文预算管理策略，目标是：

- 保留当前目标、硬约束、关键事实、决策和待办事项。
- 减少重复、过期、低相关内容及过长工具回填。
- 控制端到端 token 成本与延迟，同时维持任务质量。
- 保留事实来源、版本和必要的原始片段，便于核验或回溯。

压缩不能扩展模型的上下文窗口，也不能自动保证答案更准确。压缩是否有效，需要在具体模型、任务和调用方式上评估。

## 1. 概念与边界

### 1.1 上下文压缩解决什么问题

模型调用可用的上下文预算会被系统提示、对话历史、工具定义、检索材料、多模态输入和本轮输出共同占用。长历史或大段原始回填可能带来更高成本、更长延迟，以及关键约束被冗余内容掩盖等问题。

上下文压缩的关注点是：针对下一步任务，哪些信息必须继续保留、哪些可以删减、哪些必须原样保存。它与[上下文工程](03%20Context%20Engineering.md)相关，但范围更聚焦于上下文内容的筛选、表示和续接。

### 1.2 压缩不等于普通摘要

普通摘要通常以“概括一段内容”为目标；工程中的上下文压缩还要考虑：

- 当前任务的目标和约束是否完整。
- 参数、标识符、版本号、代码和引用是否需要原样保留。
- 信息的来源、时间和可信状态是否可追溯。
- 压缩后的结果是否适合后续模型调用或工具执行。
- 压缩调用本身是否抵消了节省的成本。

因此，不应只用压缩率或摘要长度判断压缩质量。

## 2. 压缩策略与组合

### 2.1 先区分不同分类维度

抽象、抽取、选择性和结构化压缩并非四种互斥、处于同一分类层级的方法：

| 分类维度 | 策略 | 主要操作 |
| --- | --- | --- |
| 信息如何变换 | 抽象压缩、抽取压缩 | 改写概括，或保留原文中的关键事实与片段 |
| 保留哪些内容 | 选择性压缩 | 根据当前任务保留、过滤和去重 |
| 内容如何组织 | 结构化压缩 | 按固定字段或状态模板重新编排 |

一个流程可以先筛除无关内容，再对一般讨论做摘要、对关键参数做原文抽取，最后整理成结构化状态。不同字段也可以采用不同策略。

实际运行时还可以按下表选择具体操作：

| 操作方式 | 是否改写内容 | 信息损失与回查 | 适用场景 |
| --- | --- | --- | --- |
| 滑动窗口或直接裁剪 | 否，直接移除旧消息或片段 | 被移除内容无法从当前上下文恢复；需要时应从外部会话记录或原始数据回查 | 旧历史已无关，且应用有明确的保留窗口 |
| 选择性删除 | 否，保留选中的原始片段 | 可能漏掉后续仍依赖的内容；保留 source ID 或原始记录定位便于恢复 | 历史、检索结果或工具输出中存在明显冗余 |
| 抽取 | 通常不改写被选中的字段或原文 | 精确字段较易核对，但抽取仍可能遗漏相关条件 | 数值、标识符、代码、引用或用户明确约束 |
| 摘要 | 是，生成更短的表达 | 属于有损改写，可能遗漏条件或把不确定内容写成事实 | 需要延续较长叙述或任务进展 |
| 结构化检查点 | 重新组织为字段或状态 | 便于检查和续接，但字段内容仍可能错漏；保留原始记录定位 | 跨阶段任务、Agent 运行状态或多轮会话 |
| API 原生 Compaction | 取决于平台能力 | 结构和续接语义由平台定义，结果可能不适合人工阅读；重要原文应按应用要求保留 | 需要使用特定 API 的状态压缩或续接能力 |
| Context editing（上下文编辑） | 通常直接清除指定历史内容，不生成摘要 | 被清除内容可能无法从后续上下文恢复；重要原文应在应用侧保留 | 按平台规则清理旧工具结果或其他指定内容 |

### 2.2 抽象压缩（Abstractive Compression）

抽象压缩是用更短的表述保留原文语义和任务状态，不要求复用原句。

例如：

原内容：

> 用户在实现 gRPC 客户端。此前讨论了连接池和超时配置；用户接下来要处理重试机制。

压缩后：

> 任务：实现 gRPC 客户端。已讨论连接池与超时配置；下一步讨论重试机制。

适用场景：

- 多轮长对话的阶段性续接。
- 项目任务的目标、进展和待办整理。
- 原始表述不重要、延续任务状态更重要的内容。

优点是压缩率通常较高；风险是遗漏约束、混淆事实与推断，或把不确定信息写成确定结论。可使用以下要求约束摘要：

~~~text
请整理以下历史，使下一步能够继续当前任务。
保留当前目标、用户明确约束、已确认事实、决策、未完成事项和阻塞点。
区分已确认事实、推断和待核验信息；重要事实标注来源及时间或版本。
不要补充原文未提供的信息。缺少的信息标记为“未知”。
~~~

### 2.3 抽取压缩（Extractive Compression）

抽取压缩是从原文中选取后续任务必需的事实、字段、代码或片段，尽量保持原样，减少改写带来的偏差。

适用场景：

- 技术参数、API Schema、配置项和代码。
- 用户明确提出的要求或限制。
- 文档问答中需要精确引用的证据。
- 任何改写可能改变含义的编号、路径、日期、版本或数值。

优点是精确细节较易保留；局限是压缩率通常低于摘要，抽取过程仍可能漏掉关键内容。

### 2.4 选择性压缩（Selective Compression）

选择性压缩关注“哪些内容应进入下一次调用”，重点是相关性筛选、去重和裁剪，而不只是改写文本。

适用场景：

- 一个长会话包含多个任务或旁支讨论。
- 工具返回大量日志、搜索结果或接口字段。
- Agent 已切换到新阶段，但少量旧决策和约束仍然有效。

筛选时应保留当前目标、仍生效的约束、已确认决策、未解决问题及必要的失败信息。不要因为某个阶段已经完成就一概删除其结果；先判断后续步骤是否依赖它。

~~~text
围绕当前任务筛选历史内容。
保留当前目标、仍然有效的约束、已确认决策、关键事实、未完成事项及必要来源。
删除与当前任务无关的内容和重复信息。
不要把不确定信息改写成事实；无法判断是否仍有效时，标注出来。
~~~

### 2.5 结构化压缩（Structural Compression）

结构化压缩将对话、日志或运行状态整理成稳定字段，便于模型和运行时准确读取。字段应根据应用需要设计，可参考：

~~~text
当前目标：
硬性约束：
已确认事实：
  - 内容：
    来源：
    时间或版本：
    状态：原文事实 / 用户确认 / 推断 / 待核验
关键决策：
未解决问题：
当前阶段与已完成步骤：
下一步：
需原样保留的参数、标识符、代码或引用：
原始内容定位（文档、消息、日志或工具结果 ID）：
~~~

结构化格式能提升可读性和执行性，但字段名本身不保证信息准确。生成后仍需核对关键字段，并避免把用户内容或检索内容提升为系统规则。

### 2.6 组合使用

实际流程可按以下顺序组合策略：

1. 以当前任务定义必留信息和可丢弃信息。
2. 选择性过滤重复、过期和无关内容。
3. 抽取必须精确保留的数值、约束、引用、代码和标识符。
4. 对其余需要延续的内容做摘要。
5. 将结果整理为结构化状态，并校验来源和未完成事项。

## 3. 按内容类型选择策略

| 压缩对象 | 常见做法 | 需要特别保留的内容 |
| --- | --- | --- |
| 多轮对话 | 过滤旁支内容，摘要任务进展，抽取用户约束 | 目标、最新有效决策、待办、未解决分歧 |
| RAG 检索结果 | 先筛选、去重和排序，再按需抽取或摘要 | 来源、版本、片段定位、关键原文及访问控制信息 |
| 工具输出 | 过滤无关字段，提取状态变化、错误和下一步所需值 | 退出状态、错误位置、参数、对象 ID、可回查的原始结果 |
| 长任务状态 | 按阶段和任务状态结构化 | 已完成步骤、依赖关系、阻塞点和下一步 |
| 长期记忆写入 | 只保存经过确认且有复用价值的信息 | 来源、有效期、适用范围、纠错和删除所需信息 |

### 3.1 RAG：检索筛选与压缩是不同步骤

RAG 的候选召回、重排、过滤和去重属于检索结果选择；把保留下来的长片段改写为摘要或抽取事实，才是内容压缩。筛选与排序能减少注入上下文的内容，但不能代替对证据的忠实表达。

推荐流程：

1. 检索候选片段，并根据问题重排、过滤和去重。
2. 优先注入足以回答问题的原文证据；只有在确有预算或长度需要时才进一步压缩。
3. 对摘要或抽取结果保留文档 ID、版本、片段 ID、页码或字符位置等来源信息。若后续权限检查依赖权限元数据，也应保留该信息。
4. 保留关键数值、限定条件和原文引用。来源相互矛盾时，分开呈现各自来源，不要合并成一个未经证实的结论。

相关流程见 [RAG 架构](../../02%20检索与RAG/RAG流程/02%20RAG架构.md) 和 [RAG 评测](../../02%20检索与RAG/RAG流程/07%20RAG评测.md)。

### 3.2 工具输出、任务状态与记忆

工具输出不必整份复制到后续提示中。测试运行可保留失败用例、错误位置和退出状态；搜索工具可保留相关条目及来源；接口响应可保留下一步要用的业务字段。若后续可能需要检查细节，应保留原始结果的引用或可重新获取的定位信息。

长任务状态宜记录当前阶段、完成情况、待办和阻塞点。写入长期记忆前，需确认内容确实稳定且有跨任务复用价值，并记录适用范围、来源及有效性；一次对话的摘要不应自动变成长期事实。

## 4. 触发条件与操作流程

### 4.1 根据预算触发，不依赖固定轮数

超过固定轮数或 Token 数可以作为实现简单的启发式条件，但不存在适用于所有模型、任务和 API 的通用阈值。应按目标模型和 API 的计量规则估算完整请求，包括消息结构、工具定义、结构化输出约束及图片、音频等多模态内容，并为本轮输出和运行时开销留出预算。

可将输入预算粗略理解为：

> 可用于输入的额度 ≈ 模型或 API 的上下文额度 − 预留输出额度 − 请求及运行时开销 − 安全余量

具体限制和计量方式因模型、API 和模态而异；有官方 token 计数能力时优先使用，其他估算方法应留有余量。可参考 [Counting tokens](https://developers.openai.com/api/docs/guides/token-counting)。

常见触发信号包括：

- 预计下一次调用会接近输入预算，或挤压必要的输出空间。
- 单次工具或检索结果过大，直接回填会占用大量预算。
- 任务进入新阶段，先前的详细过程已不再需要，但其结论仍需保留。
- 重复或过期信息明显增加，影响任务聚焦或成本。
- 准备写入长期记忆，需要先筛除临时、未确认的信息。

轮数或比例阈值应通过目标工作负载的 token 使用和质量数据校准，而不是照搬固定数字。

### 4.2 建议的压缩流程

1. 确认下一步目标，以及不可丢失的约束、事实和证据。
2. 估算调用预算，确定需要减少的内容及目标长度。
3. 先筛选和去重；对精确字段抽取原文，对叙述性内容再做摘要。
4. 将结果整理成可续接的状态，并保留来源、时间、版本和不确定性。
5. 检查关键字段、约束、待办和引用是否仍然完整。
6. 记录压缩前后 token 与质量数据；如果效果下降，缩小压缩范围或恢复原始证据。

## 5. 自然语言摘要与 API 原生 Compaction

自然语言摘要和模型平台提供的 API 原生 Compaction 不是同一种输出：

| 维度 | 自然语言摘要 | API 原生 Compaction |
| --- | --- | --- |
| 输出形式 | 面向人和模型阅读的文本 | 按提供方约定生成的状态或专用消息结构 |
| 可检查性 | 通常可直接阅读、编辑和审查 | 可能不是面向人工阅读的摘要 |
| 可移植性 | 可在不同模型或系统间改造使用 | 通常依赖特定提供方、模型或 API 的续接语义 |
| 主要用途 | 应用自行管理对话历史和任务状态 | 按 API 约定压缩或续接模型交互状态 |

例如，OpenAI API 文档介绍了服务端上下文压缩和独立的 Compaction API。独立接口的压缩结果应按该 API 文档规定的方式用于后续请求；其中的专用压缩项不一定适合人工解读。具体可用模型、请求格式和续接要求应以当前平台文档为准。

使用原生 Compaction 时，不要假定返回内容等价于一段可任意改写的普通摘要；应保留 API 要求的结构并验证后续调用是否正确续接。无论使用哪种方式，仍需评测任务质量、总成本和延迟。

部分平台还提供 context editing，用于按配置清除旧工具结果或特定思考块等历史内容。它与摘要式 Compaction 不同：通常是清理指定内容，不会自动生成可替代原文的摘要，也不保证被清除的信息能在后续请求中恢复。应用应确认可清理的内容、轮次和续接规则，并为审计、重试或事实核验保留必要的原始记录。Anthropic 的 [Context editing 文档](https://platform.claude.com/docs/en/build-with-claude/context-editing)提供了平台特定示例。

## 6. 风险与效果评估

### 6.1 常见风险

- **遗漏约束或参数**：摘要没有保留用户明确要求、数值或异常状态。
- **事实漂移**：摘要把推断、不确定内容或模型生成内容变成确定事实。
- **来源丢失**：压缩后无法判断结论来自哪个文档、版本、工具或时间点。
- **选择错误**：相关性筛选删除了后续步骤仍依赖的信息。
- **错误累积**：反复对摘要做摘要，逐轮放大早期遗漏或误解。
- **缓存收益下降**：如果压缩改变了稳定提示前缀，可能影响部分平台的缓存复用。

可通过明确必留字段、标记来源和可信状态、保留原始内容定位，并定期从可信原始记录重建状态来降低这些风险。缓存效果应结合 [Prompt Cache](05%20Prompt%20Cache.md) 的命中与计费指标评估。

### 6.2 评估指标与方法

不要只看压缩前后的长度；至少应同时观察质量、信息保留、成本和延迟：

| 维度 | 可观察指标 |
| --- | --- |
| 任务质量 | 任务完成率、答案正确性、长任务连续性 |
| 信息保留 | 关键事实与约束召回率、精确参数正确率、引用和来源保留率 |
| 工具使用 | 工具选择与参数正确率、任务执行成功率 |
| 成本 | 所有压缩调用与后续调用的总输入/输出成本；区分缓存与非缓存用量 |
| 延迟 | 端到端耗时，以及压缩步骤带来的额外延迟；按需观察 P50、P95 |

评估时使用有代表性的任务样本，在模型、提示、工具和其他关键设置一致的情况下，对比未压缩与不同压缩策略。除自动指标外，对事实准确性、关键约束和引用进行人工抽查，并把已知失败样例纳入回归集。

成本应以完整工作流计量：压缩模型调用本身也会消耗 Token 和延迟；后续请求可能因输入减少而节省成本，也可能因稳定前缀变化而降低缓存命中。应根据提供方实际使用量和计费规则核算净收益，而不是只比较最后一次请求的输入长度。评测方法可参考 [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。
