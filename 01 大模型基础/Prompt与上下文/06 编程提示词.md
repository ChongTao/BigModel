# 06 编程提示词

本文整理代码和软件开发任务中可复用的提示词模板。模板是起点，使用时应补充项目背景、相关代码、约束和验收标准，并删除不适用的字段。

提示词不能替代系统规则、用户要求或仓库规范。面向代码 Agent 的任务应明确修改范围和验证要求；缺少信息只有在会实质改变方案时才需要先提问，其余情况可说明合理假设后继续。

## 1. 通用代码任务模板

适用于新增功能、修复问题、重构和小型实现任务。

~~~text
任务目标：
【希望实现或修复什么】

项目背景：
【业务用途、当前行为、相关模块；不清楚的内容可留空】

验收标准：
【如何判断任务完成；列出可观察的行为或示例】

相关文件或入口：
【已知的路径、函数、组件或接口；不确定时请先检索】

约束：
【语言与版本、兼容性、性能、安全、依赖、修改范围、代码风格等】

工作方式：
1. 先阅读仓库中适用的 Agent 说明和项目规则，例如 AGENTS.md 或 CLAUDE.md，并检查相关实现。
2. 需求中有会影响实现的关键缺口时，先指出并提问；其他可合理处理的部分说明假设后继续。
3. 只修改完成任务所需的范围；遵循现有架构和代码风格，不加入未经说明的依赖。
4. 按任务要求和项目规则进行验证。明确列出实际执行的检查及结果；未执行的检查标记为未执行。

交付格式：
- 修改了哪些文件，以及各自的改动目的
- 执行了哪些验证及结果
- 仍未解决的问题、假设或限制
~~~

提交任务时，尽量提供最小复现、输入输出示例、相关错误日志和预期行为。不要在提示或示例中粘贴真实密钥、访问令牌或其他凭证。

## 2. 按任务类型使用

### 2.1 代码审查员

~~~text
请审查下面的代码变更。

审查范围：
【代码、Diff 或文件路径】

背景与预期行为：
【相关需求、接口约定或业务规则】

重点检查：
- 正确性、安全性、数据完整性和错误处理
- 边界条件、并发与资源使用
- 与现有接口、兼容性和项目约定的冲突

输出要求：
- 按严重程度排序，每个问题说明触发条件、影响和依据。
- 能确定时给出文件路径与行号；行号无法核实时不要猜测。
- 对每个问题给出修复方向；必要时提供最小代码示例。
- 区分确定的问题、潜在风险和一般建议。
- 不重写整个文件，不报告与本次审查目标无关的风格意见。
- 如果没有发现可操作的问题，说明审查范围，并避免把“未发现问题”表述成“代码已被证明正确”。
~~~

严重级别应按项目约定使用；没有约定时，先简要说明判定标准，避免只贴等级标签。

### 2.2 架构顾问

~~~text
请根据以下需求提出架构建议。

目标与用户：
【要解决的问题、使用者和主要工作流】

已知规模与约束：
【吞吐、数据量、可用性、安全、预算、技术栈、部署环境、兼容要求】

输出要求：
1. 列出会影响架构选择的关键假设；只有缺失信息会显著改变方案时才先提问。
2. 给出推荐方案，并说明核心组件、数据流、边界和主要取舍。
3. 只有存在有意义的技术取舍时才比较其他可行方案。
4. 评估安全、故障处理、运维和成本；不确定的估算标注假设或范围。
5. 需要图示时使用 Mermaid；实施计划或文件清单应基于已检查的仓库结构。
~~~

不要为了满足固定方案数量而引入不必要的复杂度。复杂度估算应说明依据，不能伪装成精确承诺。

### 2.3 调试助手

~~~text
请帮助诊断下面的问题。

问题输入：
- 预期行为：【……】
- 实际行为：【……】
- 错误信息或堆栈：【……】
- 最小复现或相关代码：【……】
- 运行环境、版本及最近变更：【……】

请按以下步骤回答：
1. 区分已知事实与待验证假设。
2. 根据现有证据解释最可能的原因；没有足够证据时说明还缺什么。
3. 给出最小修复方案，并解释它如何对应根因。
4. 提出有针对性的回归检查，以及可能受影响的部分。
~~~

不要在证据不足时把假设写成根因。只有缺少的信息会阻止有效诊断时，再请求补充复现材料或环境信息。

### 2.4 API 文档助手

~~~text
请根据提供的 API 规范或实现代码编写开发者文档。

事实来源：
【OpenAPI 规范、接口实现、示例请求或其他权威材料】

需要覆盖的内容（适用时）：
- HTTP 方法、路径、版本和用途
- 身份验证要求及权限
- 请求参数、类型、必填性、约束和示例
- 成功响应结构及示例
- 已定义的错误响应和处理建议
- 分页、幂等、限流等接口行为

写作规则：
- 不推测材料中没有的信息；未知或未定义的内容标为“未说明”。
- 示例使用占位值，不包含真实凭证。
- 只有经过接口规范或实现核对的示例，才标为可直接运行。
- 如果规范和实现不一致，先列明冲突来源，不要替用户擅自选择。
~~~

### 2.5 测试用例编写助手

~~~text
请为以下功能设计或编写测试用例。

功能与验收标准：
【……】

项目测试信息：
【测试框架、相关测试文件、现有命令；未知时先检查仓库配置】

测试要求：
- 根据实际行为覆盖正常路径、重要边界、错误处理和相关回归风险。
- 每个用例包含清晰名称、必要前置条件、操作和可验证的预期结果。
- 沿用仓库的测试框架、命名、Fixture 和断言习惯。
- 只在与功能交互确有关系时建议集成测试；避免重复和无关的组合爆炸。
- 区分测试建议、测试代码和测试执行结果，不要声称执行过未运行的测试。
~~~

### 2.6 技术解释器

~~~text
请向以下读者解释这个技术概念。

概念：【……】
读者的背景：【……】
希望的深度或篇幅：【……】

回答应包含：
1. 简洁定义，以及它解决的问题。
2. 一个贴近实际的例子。
3. 常见误解或适用边界。
4. 如果类比能帮助理解，可以给出类比，并说明类比不适用的部分。
5. 最后用几句话总结重点。
~~~

根据读者需要解释术语，不要求把所有专业词汇都删除；准确性优先于过度简化。

## 3. 填写与调整建议

- 把任务目标、背景、约束、输入材料和验收标准写清楚；角色名称本身不能代替这些信息。
- 对代码 Agent 明确是否需要检查、修改、提出方案或执行验证，避免混淆任务范围。
- 对长任务可分阶段给出目标和检查点；复杂度不高时不要强制先写长计划。
- 指定答案语言和输出格式。本文模板采用中文；实际使用时可以按模型和团队语言习惯调整。
- 对目标模型和工作流验证模板效果。模型间的指令遵循、主动性和验证习惯可能不同，不能假定一套措辞对所有模型都产生相同行为。
- 按需调整模板字段，不要为了填满所有栏目而补造信息。
