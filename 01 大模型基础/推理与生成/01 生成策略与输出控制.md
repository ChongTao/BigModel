# 01 生成策略与输出控制

大语言模型按自回归方式逐步生成 Token。一次请求的输出行为既取决于模型如何从候选中选择 Token，也取决于 API 设置的长度、停止条件和格式约束。

本文介绍解码原理、常见生成参数、输出预算、结构化输出与工具调用。重点是区分解码原理与 API 字段：相同概念在不同模型、端点和 SDK 中可能有不同名称、默认值和限制。

## 1. 解码与采样

### 1.1 从 logits 到下一个 Token

模型输出层给出词表中各 Token 的 logits（未归一化分数）。经过 softmax 后，logits 才变为概率。Token 是文本片段或特殊标记，不一定对应一个完整的词。

- **解码（decoding）**：从候选分布中选择 Token、扩展候选序列，并决定何时结束的过程。
- **采样（sampling）**：解码的一种方式，按概率随机抽取下一个 Token。

一轮生成可以抽象为：

`上下文 -> logits -> 约束与分数调整 -> 概率变换与候选过滤 -> 重新归一化 -> 选择 Token -> 追加到上下文`

不同模型、API 和推理引擎可能采用不同的处理顺序，也可能不开放全部控制项；组合参数时应以目标实现的文档为准。

### 1.2 常见解码策略

| 策略 | 如何选择 | 特点与常见用途 |
| --- | --- | --- |
| 贪心解码（greedy） | 每一步选当前分数最高的可用 Token | 开销低，选择过程直接；只看当前一步，长文本可能重复或错过更好的后续序列。 |
| 概率采样（multinomial sampling） | 按处理后的概率分布随机抽取 Token | 同一输入可以产生不同续写；开放式生成常用，结果会受随机种子和运行环境影响。 |
| 束搜索（beam search） | 保留多条部分序列，按累积序列分数扩展和筛选 | 适合翻译、语音识别等输入约束较强的序列任务；束宽有限，长度归一化等评分规则会影响排序，不保证找到全局最优序列。 |

束搜索常用累积 log 概率为候选序列打分，有些实现还会使用长度惩罚或其他归一化。部分框架允许把束搜索与随机采样结合，具体行为以框架文档为准。

### 1.3 temperature 与候选过滤

`temperature` 调整下一 Token 概率分布的尖锐程度。设第 `i` 个 Token 的 logit 为 `z_i`，温度为正数 `T` 时，一种常见变换是：

`p_i = softmax(z_i / T)`

- `T = 1` 不因温度改变分布。
- `0 < T < 1` 会放大分数差异，使分布更尖锐。
- `T > 1` 会缩小分数差异，使分布更平坦。

温度不是正确率开关，也不会补充模型缺少的知识。候选过滤方法包括：

| 方法 | 保留规则 | 说明 |
| --- | --- | --- |
| Top-k | 保留分数最高的 `k` 个候选 | 候选数量固定。 |
| Top-p（nucleus sampling） | 按概率排序，保留累计概率达到 `p` 所需的最小候选集合 | 候选数量随分布变化；不天然优于 Top-k。 |
| Min-p | 通常保留概率不低于最高候选概率乘以 `min_p` 的 Token | 按相对阈值过滤，并非所有 API 都支持。 |
| Typical、epsilon、eta 等 | 按局部典型性或概率阈值筛选 | 部分框架提供，定义和支持范围不统一。 |

过滤后，保留项的概率会重新归一化，再用于抽样。温度与 Top-p、Min-p 会共同影响候选集合；叠加多个过滤器可能让候选过少。不同实现的处理顺序也可能不同。刚开始调参时优先使用模型建议的默认值，一次只调整一个变量。

### 1.4 重复惩罚与 logit bias

在提供这些参数的接口中，常见语义如下：

| 参数 | 常见作用 |
| --- | --- |
| `presence_penalty` | 根据 Token 是否已经出现过调整分数；正惩罚通常会降低它再次出现的倾向。 |
| `frequency_penalty` | 常见实现会随 Token 出现次数增加而加重惩罚。 |
| `repetition_penalty` | 通过引擎定义的规则抑制已出现 Token；作用范围可能包含输入提示词。 |
| `logit_bias` | 按指定 Token ID 调整分数；可用范围和正负值语义由接口定义。 |

这些规则通常作用于 Token 或 Token 计数，不会识别抽象的“话题”。不同 API 的公式、计数范围和参数支持可能不同，同名参数也不一定等价。惩罚过强还可能影响代码标识符、专有名词或需要重复的术语，应在目标数据上评估。

`temperature = 0` 也没有跨 API 的统一语义：有的实现会特殊处理为贪心选择，有的会拒绝该值。应按目标模型和端点文档理解。

## 2. API 参数与输出预算

### 2.1 字段名称与兼容性

| 控制目标 | 常见字段名示例 | 使用时确认 |
| --- | --- | --- |
| 采样分布 | `temperature`、`top_p`、`top_k`、`min_p` | 参数是否支持、取值范围及可否组合。 |
| 输出预算 | `max_tokens`、`max_completion_tokens`、`max_output_tokens`、`maxOutputTokens` | 上限如何计数，达到上限时如何报告。 |
| 停止条件 | `stop`、`stop_sequences` | 是否支持、匹配规则及停止文本是否返回。 |
| 输出格式 | `response_format`、`text.format`、`responseSchema` | JSON mode 与 Schema 约束的区别及 Schema 支持范围。 |

这些字段名不是跨平台通用别名。常见例子包括 OpenAI Responses API 的 `max_output_tokens`、Chat Completions 的 `max_completion_tokens`、Anthropic Messages 的 `max_tokens`，以及 Gemini API 的 `maxOutputTokens`。REST API 与 SDK 的字段大小写也可能不同。

未支持的参数可能被拒绝、忽略或由服务端固定处理；不要只凭参数名推断实际行为，应核对正在调用的模型、端点和版本。

### 2.2 输出 Token 上限

输出预算限制生成侧的 Token 数，不等同于模型的上下文窗口。上下文窗口还要容纳输入和对话历史；一些推理接口会把内部推理 Token 计入输出预算，因此用户可见文本可能短于设置的上限。

预算过小可能导致答案、代码或结构化结果不完整。不能仅凭 HTTP 请求成功或已经收到部分文本，就判断生成已完整结束；还要检查 API 返回的完成状态和结束原因。

### 2.3 stop 与响应结束状态

`stop` 或 `stop_sequences` 可在生成命中特定字符串时终止输出，但支持范围、匹配规则以及停止字符串是否出现在返回内容中都因接口而异。停止字符串可能截断 JSON 等结构化内容，不应把它当作格式校验机制。

处理响应时，应区分正常结束、达到长度上限、拒答、工具调用和其他未完成状态。字段名由 API 决定；使用流式输出时，应等到收到完整结束事件后再解析结果。

## 3. 结构化输出与工具调用

结构化输出用于让结果符合可解析的数据协议。只在提示词里写“请返回 JSON”只是表达意图，不能可靠保证格式。

| 方式 | 能解决什么 | 仍需注意什么 |
| --- | --- | --- |
| 提示词约定 | 告诉模型期望的格式。 | 不保证语法、字段或类型正确。 |
| JSON mode | 在支持的接口中约束输出为 JSON 语法。 | 通常不保证特定字段、类型、枚举或业务规则；拒答和不完整响应也要单独处理。 |
| JSON Schema / constrained decoding | 在接口支持的范围内约束字段、类型、枚举和嵌套结构。 | 不同模型支持的 Schema 子集不同；拒答、长度截断或未完成响应不能当作有效结果。 |

### 3.1 结构化输出的接入与校验

1. Schema 只保留下游需要的字段，明确类型、必填项和枚举值；先确认目标 API 支持哪些 Schema 关键字及限制。
2. 使用模型服务提供的原生结构化输出功能。不同服务的字段名和支持范围并不相同。
3. 先检查响应是否完整、是否拒答或被长度上限截断，再解析内容。流式响应要等到结束后再解析完整对象。
4. 解析后仍要做本地 Schema 校验和业务校验。合法 JSON 不代表事实正确，也不代表金额、权限或跨字段规则成立。
5. 对失败重试应设置次数上限；如果后续操作有副作用，重试前先确认操作是否已经执行。

### 3.2 工具调用

工具调用应使用模型服务定义的工具或函数调用协议。模型返回的是一条待应用处理的调用请求，不代表工具已经执行。应用需要校验参数、用户权限和操作范围，再决定是否执行。

## 4. 模型专属参数与复现

`reasoning effort`、`thinking budget`、`verbosity`、随机种子（`seed`）和候选数量等参数具有明显的模型与平台差异。部分推理模型或端点不接受 `temperature`、`top_p` 等采样参数；不要默认传入全部字段。

如果接口支持 `seed`，它可以帮助在相同模型和运行配置下复现实验，但模型版本、服务端实现、推理框架和硬件变化仍可能改变输出。记录模型与端点版本、提示词、Schema、生成参数、结束状态和评估结果，才能进行有意义的比较。

## 5. 实际配置流程

1. 先查目标模型和 API 的参数支持、默认值及组合限制。
2. 从模型推荐配置开始；如果输出必须满足协议，使用原生结构化输出，并为最坏情况留出足够的输出预算。
3. 调整随机性时一次只改少数参数，用代表性样例评估正确性、格式合规性、重复、延迟和成本。
4. 在应用中处理拒答、截断、解析失败和业务校验失败；不要把重试当作默认的格式保证。

可以把控制拆开理解：解码策略决定如何选择 Token，请求参数限制候选和生成预算，结构化输出约束结果形状，应用校验判断结果是否可用。
