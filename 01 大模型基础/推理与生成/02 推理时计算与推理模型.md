# 推理时计算与推理模型

复杂任务的效果除了取决于模型能力，也受一次任务中投入多少推理预算影响。**推理时计算**（test-time compute，也常称 inference-time compute）通常指模型部署后，为提升当前任务表现而增加的生成、候选搜索、评分或验证计算。不同研究对这个词的范围略有差异；本文聚焦推理阶段增加这些预算，不讨论根据输入更新模型参数或适配状态的 test-time adaptation。

增加预算可能提高困难任务的成功率，但收益不会随计算量线性增长；它也会增加延迟和成本，并可能让模型重复错误或陷入无效推演。

## 1. 区分训练、推理时计算与 Serving 优化

| 类别 | 发生阶段 | 常见做法 | 主要目标 |
| --- | --- | --- | --- |
| 预训练与后训练 | 模型训练阶段 | 预训练、SFT、偏好优化、强化学习 | 获得知识、指令遵循和求解任务的能力 |
| 推理时计算 | 模型部署后，处理具体任务时 | 生成更长的推理、采样多个候选、分支搜索、调用验证器 | 用额外计算提高当前任务的结果质量 |
| 推理系统优化 | 模型部署与服务阶段 | KV Cache、连续批处理、量化、投机解码、GPU 调度 | 改善吞吐、延迟、显存或单位请求成本 |

Prefill（处理输入）和 Decode（逐 Token 生成）描述推理引擎处理请求的阶段，本身不等于推理时计算扩展。扩展预算可能表现为生成更多 Token、额外调用模型评分，或展开并验证多个候选路径。Serving 优化可以让请求更快或更省资源，但不一定提升答案的推理质量。

更多计算有助于模型分解问题、检查答案或组合已学到的知识；它不能仅靠延长生成可靠地补充缺失事实或最新信息，需要时应提供可信上下文或调用外部工具。

## 2. “推理模型”不是单一架构分类

“推理模型”是研究和产品中常用的称呼，没有统一的架构定义。它通常指经过专门训练或后训练、在多步问题上更擅长规划求解，并可能在推理阶段投入更多计算的模型。能力来源要区分模型本身、推理策略和应用系统：

| 来源 | 典型机制 | 所在层面 |
| --- | --- | --- |
| 预训练能力 | 学习语言、知识、代码和模式 | 模型训练 |
| 推理相关后训练 | 推理示例、SFT、偏好优化、强化学习或可验证任务反馈 | 模型后训练 |
| 推理时策略 | 更长的推理预算、多候选采样、搜索、评分和校验 | 模型调用过程 |
| 外部系统能力 | 检索、计算器、代码执行、数据库和人工复核 | 应用或 Agent/Harness |

这些机制在不同模型中的组合不同。外部工具和验证器能增强整个系统，但不应被当作模型自身学到的能力。

部分推理模型会先生成内部推理 Token，再产生用户可见回答；API 可能隐藏原始推理内容，只提供最终结果或受限摘要。OpenAI API 文档也说明，其推理 Token 对调用方不可见，但会占用上下文并按输出 Token 计费；`reasoning.effort` 等控制项的支持范围依模型而异。其他服务的字段、预算和计费规则可能不同，参数细节见[01 生成策略与输出控制](01%20%E7%94%9F%E6%88%90%E7%AD%96%E7%95%A5%E4%B8%8E%E8%BE%93%E5%87%BA%E6%8E%A7%E5%88%B6.md)。

可见思考文本的长短不能代表完整计算量，也不能证明答案正确。评估时应看任务结果、验证证据和接口提供的用量信息，而不是要求模型展示长篇思考过程。

Chain-of-Thought、Self-Ask 和 ToT 是提示或搜索策略，可以用于不同类型的模型；使用它们并不会把普通模型训练成推理模型。相关介绍见 [03 CoT](03%20CoT.md)、[04 Self-Ask](04%20Self-Ask.md) 和 [05 ToT](05%20ToT.md)。

## 3. 常见的预算扩展方法

| 方法 | 做法 | 适用条件 | 主要风险或成本 |
| --- | --- | --- | --- |
| 增加串行推理预算 | 允许模型生成更多推理步骤或内部 Token | 困难题需要分解、推导或复核 | 延迟和 Token 成本上升；可能出现重复或无效推演 |
| Self-Consistency | 多次采样不同推理路径，聚合或投票选择最终答案 | 答案可比较，且不同路径有一定多样性 | 错误可能相关；多数票不保证正确 |
| Best-of-N 与重排序 | 生成多个答案，再由评分器、排序器或验证器选出候选 | 存在相对可靠的评分依据 | 评分器偏差会选错，生成和评估成本随候选数增长 |
| 分支搜索 | 展开多个中间状态，评估后保留或扩展部分路径；ToT 是一种代表 | 状态、约束和分支质量能够评估 | 搜索空间可能快速扩大，部分路径的评分也可能不准 |
| 验证后修正 | 生成候选，运行测试或规则，再让模型修正 | 有单元测试、计算器、约束检查等可靠验证器 | 验证器有盲点时会误导修正；必须限制循环次数 |
| 按难度分配预算 | 简单问题使用较小预算，困难或未通过校验的问题再升级 | 能估计难度或观察到明确的失败信号 | 难度判断或停止信号不准时会错配预算 |

这些方法不能互换：Self-Consistency 聚合多条路径的最终答案，Best-of-N 依赖评分器挑选候选，ToT 等搜索方法会在中间步骤扩展和筛选分支。增加候选只有在候选有差异、且聚合或评分有效时才可能带来收益。

检索、计算器和代码执行能提供外部信息或确定性计算，常与推理预算扩展配合使用；它们属于应用运行时能力，不是模型内部推理 Token。工具调用还需要校验参数、权限和执行结果，见 [Agent与Harness](../../03%20Agent%E4%B8%8EHarness/README.md)。

## 4. 与 Agent 和推理系统的边界

模型生成工具调用请求，不代表工具已经执行。由运行时执行工具、回填结果、管理多步循环与权限的部分属于 Agent/Harness。更多内容见[Agent与Harness](../../03%20Agent%E4%B8%8EHarness/README.md)。

KV Cache、连续批处理、量化、投机解码和 GPU 调度等推理系统优化的实现细节见[推理与部署](../../04%20%E6%8E%A8%E7%90%86%E4%B8%8E%E9%83%A8%E7%BD%B2/README.md)。

## 5. 如何评估预算是否值得

1. 建立覆盖简单、普通和困难样本的留出评测集，并确保它接近实际请求分布。
2. 固定模型、提示词、工具和评测条件，对比基础配置与多个推理预算；多候选方法应重复运行，以估计波动。
3. 对数学、代码等任务优先使用可复现的答案检查或测试；开放式任务使用明确评分标准、人工抽查或成对偏好评估。
4. 同时记录任务成功率、事实错误、拒答、格式合规性，以及验证器和工具调用失败。
5. 统计完整成本：可见与隐藏 Token（若接口提供用量信息）、工具和验证器调用、端到端延迟及费用。
6. 比较质量—成本曲线，找出收益开始变小的预算区间；设置 Token、时间和循环次数上限，并为无法验证或预算耗尽的情况定义回退策略。
7. 抽检长推理和失败样例，避免把流畅解释或更多推理 Token 当成正确性的证明。

对于有验证器的任务，可以把流程概括为“生成候选 → 验证 → 选择或修正”；开放式任务也可以通过人工评测衡量额外预算的收益。评测设计可参考[09 Benchmark与常见指标](../模型原理与训练/09%20Benchmark%E4%B8%8E%E5%B8%B8%E8%A7%81%E6%8C%87%E6%A0%87.md)。
