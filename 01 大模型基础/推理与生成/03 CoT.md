# Chain-of-Thought（CoT）：提示方法与边界

Chain-of-Thought（CoT，思维链）是一种提示方法：通过示例或指令，引导模型在处理多步任务时生成或利用中间推导。

**定位：CoT 是推理诱导范式，不是模型架构、解码规则或独立的搜索算法。** 它可以增加生成阶段的中间 Token，但不等同于推理时计算预算管理，也不代表模型会向调用方展示完整的内部推理过程。

## 1. 常见形式

### 1.1 Few-shot CoT

在提示中提供带有中间推导的示例，让模型参照示例处理新问题。示例的正确性、任务相似度和表达格式都会影响效果。

### 1.2 Zero-shot CoT

不提供带推理过程的示例，而是使用分步提示引导模型，例如“请逐步分析后作答”。“Let's think step by step.” 是研究中常见的触发语之一，但不是所有模型或任务都适用的固定开关。

## 2. 为什么它有时有帮助

自回归模型每生成一个 Token，后续生成都会以它为上下文。对某些多步任务而言，把中间变量、子结论或计算步骤展开，可能帮助模型维持求解过程，而不是一次性猜测最终答案。

这种效果取决于模型、任务、示例质量和提示写法。CoT 不会为模型补充缺失事实，也不保证推导正确；必要时仍需检索可信信息、运行计算或使用外部验证器。

## 3. 适用场景

CoT 值得评估的场景包括：

- 多步数学或符号推理
- 需要组合多个前提的任务
- 中间状态有助于检查错误的分析任务
- 通过少量示例才能说明清楚任务模式的任务

简单问答、严格格式输出或只需查找明确事实的任务，未必需要展开推导。增加推理文本也会占用 Token 和响应时间。

## 4. 局限与使用边界

- **不保证更准确。** 前面某一步错了，后续推导可能围绕错误前提展开。
- **推理文本不是证据。** 一段连贯解释不代表结论正确，也不一定忠实记录模型实际使用的内部过程。
- **可见内容不等于完整计算。** 一些推理模型或 API 不会返回原始内部推理 Token；不要把展示完整思维链作为质量验收条件。
- **可能增加成本。** 更长的中间推导会增加 Token 消耗和延迟，复杂提示也可能让简单任务变得冗长。
- **不能替代外部信息和校验。** 需要最新事实、精确计算或关键业务判断时，应使用可信来源、确定性程序或人工审核。

若需要审查结果，可以要求简要说明依据、关键假设、可复核的计算结果或引用证据，而不是要求展示完整内部推理过程。

## 5. 与相关方法的关系

| 方法 | 与 CoT 的区别 |
| --- | --- |
| Self-Ask | 把复杂问题组织成一系列子问题并逐个回答；CoT 更强调连续的中间推导。 |
| Self-Consistency | 多次采样不同推理路径，再聚合最终答案；它可以建立在 CoT 提示之上，但还增加了采样和聚合步骤。 |
| Tree-of-Thoughts（ToT） | 扩展并评估多个中间分支，属于带搜索和状态评估的框架；算法结构比单条 CoT 更明确。 |
| ReAct | 结合推理、工具行动和观察结果，重点在 Agent 执行闭环，不只是生成推理文本。 |
| 推理模型 | 通常涉及专门的后训练和模型调用预算；用 CoT 提示普通模型，不等同于训练或调用推理模型。 |

## 6. 如何评估 CoT 是否有用

1. 用同一模型和评测样例比较直接回答与 CoT 提示，避免只根据少数成功案例判断。
2. 同时检查答案正确率、任务完成率、推理文本长度、延迟和成本。
3. 对数学、代码等任务使用可复现的答案检查或测试；对开放式任务使用清晰评分标准或人工评估。
4. 若 CoT 没有稳定收益，或显著增加成本，就采用更短的提示或直接回答。
