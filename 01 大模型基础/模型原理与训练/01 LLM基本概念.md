# LLM 基本概念
## 什么是 LLM

LLM（Large Language Model，大语言模型）通常指：

- 在海量语料上训练
- 参数规模很大
- 以语言建模目标为核心
- 常常建立在 Transformer 或其变体之上

的通用语言模型。

自回归 LLM 通常按以下方式生成内容：

**对于自回归 LLM，根据当前上下文计算下一个 Token 的概率分布，再逐步生成后续 Token。**

### “大”通常指什么

讨论模型规模时容易把三件事混在一起，实际应分开看：

| 维度 | 常见表述 | 主要影响 |
| --- | --- | --- |
| 参数量 | 7B、70B；MoE 还要区分总参数与激活参数 | 权重体积和潜在计算规模；实际开销也受架构、精度和硬件影响 |
| 训练 Token 数 | 训练语料处理过的 Token 规模 | 反映训练数据量；质量、多样性、去重和训练目标同样重要 |
| 训练计算量 | 总 FLOPs 或加速器计算时长 | 反映训练资源；卡数 × 时长只是未考虑硬件和利用率差异的粗略估算 |

这三项不能单独预测模型能力，数据质量、模型结构、训练方法和后训练也会影响结果。

### 常见的模型形态

同一个模型家族通常会放出多种形态，用途差别很大：

- **Base / 预训练模型**：主要通过预训练学习续写；可以接受提示，但不保证稳定遵循助手对话格式。
- **Instruct / Chat 模型**：经过指令适配，可能还经过偏好、安全等后训练；具体行为因模型而异。
- **Reasoning 模型**：通过专门训练、推理时预算或两者配合来提升多步任务表现；不一定向用户展示完整思考过程，见[推理时计算与推理模型](../推理与生成/02%20%E6%8E%A8%E7%90%86%E6%97%B6%E8%AE%A1%E7%AE%97%E4%B8%8E%E6%8E%A8%E7%90%86%E6%A8%A1%E5%9E%8B.md)。
- **Embedding / Reranker 模型**：面向文本表示或相关性评分等任务；这些用途不限定模型主干，表示细节见 [04 Embedding](04%20Embedding.md)，检索流程见 [检索与RAG](../../02%20%E6%A3%80%E7%B4%A2%E4%B8%8ERAG/README.md)。

这些标签描述训练过程、任务或产品行为，不是互斥的架构类别。

### 文本自回归模型的一次调用链路

```text
文本 → Tokenizer → Token ID → 输入表示 → 序列模型层 → 词表概率分布 → 解码或采样 → 输出 Token → 文本
```

文本模型的输入和输出通常按 Token 计量；预算、计费和延迟的具体口径由模型和服务接口决定。链路中每一步的细节在后续章节展开。

## Token

Token 是 Tokenizer 和模型词表定义的文本离散单位。它既不完全等于“一个字”，也不完全等于“一个单词”，还可能对应子词、字节片段或专用标记。

例如：

- 中文里，一个汉字有时是一个 Token。
- 常见词组、标点、空格，也可能被单独编码成 Token。
- 英文单词则可能被拆成多个子词片段。

可以把 Token 理解为模型眼中的“文本积木”。

### Token 的三种常见形态

同一个 Token 在模型链路里通常会经历三种形态：

1. 文本片段：例如 `"我"`、`"模型"`、`"un"`、`"able"`
2. 整数编号：即 `token id`
3. 向量表示：进入神经网络后的浮点数向量

要特别区分：

- Token 本身不是向量。
- Token 本身也不是概率。
- Token 最初只是被切分出来的文本单位及其编号。

### 分词器与词表

Token 怎么切，由分词器和词表决定。常见子词方案包括 BPE、WordPiece 和 Unigram；例如 BPE 会逐步合并常见片段，低频词可能被拆成多个 Token。有些分词器以字节为基础处理文本。词表大小决定可用 Token ID 的数量，但具体切分规则由模型对应的 Tokenizer 决定。

由此产生几个直接影响：

- 同一段文本在不同模型下 Token 数不同，跨模型比较上下文长度和费用时不能直接套用。
- 中文与英文的 Token 数比例取决于具体 Tokenizer 和文本内容，不应按固定字符比例估算上下文或费用。
- 罕见词、代码标识符、长数字和 Emoji 可能被切成多个 Token，从而增加 Token 用量；具体结果应使用目标模型的 Tokenizer 检查。

### 特殊 Token

除可见文本外，模型还会使用不对应文字的特殊 Token，例如序列起止标记、填充标记，以及对话模板中的角色分隔标记。它们同样计入 Token 预算，并决定消息边界，见 [02 对话模板与上下文装配](../Prompt%E4%B8%8E%E4%B8%8A%E4%B8%8B%E6%96%87/02%20%E5%AF%B9%E8%AF%9D%E6%A8%A1%E6%9D%BF%E4%B8%8E%E4%B8%8A%E4%B8%8B%E6%96%87%E8%A3%85%E9%85%8D.md)。

Tokenization 在训练链路中的位置见 [05 大模型训练流程](05%20%E5%A4%A7%E6%A8%A1%E5%9E%8B%E8%AE%AD%E7%BB%83%E6%B5%81%E7%A8%8B.md)。

## 向量化

模型把 Token ID 映射为初始向量，这一步称为 Token Embedding。句子或文档 Embedding 通常还需要经过编码和池化，见 [04 Embedding](04%20Embedding.md)。

例如：

```text
token = "模型"
token_id = 18532  # 示例值；实际编号取决于具体分词器
```

经过向量化后，可能变成：

```text
[0.12, -0.84, 1.07, ..., 0.33]
```

这串高维浮点数就是模型可以真正处理的输入表示。

如果只看概念层面，可以先记住：

- Token 解决“文本如何切开”
- 向量化解决“离散符号如何变成可计算对象”

更完整的向量化内容见 [04 Embedding.md](04%20Embedding.md)。

## 上下文窗口

大模型不是无限读文本的。上下文窗口指一次模型调用可使用的 Token 总预算。对于生成任务，这个预算通常由输入和模型生成的内容共同占用；服务接口还可能单独限制最大输入量和最大输出量。

上下文窗口决定了：

- 一次请求能容纳多少输入和生成内容
- 多轮对话能保留多少历史
- 长文档和 RAG 信息能装进去多少
- 调用成本和延迟会不会快速上升

因此，很多工程问题表面上看是“模型不够聪明”，其实本质上是“上下文装不下”或“上下文太乱”。

### 标称长度不等于有效长度

模型标称支持 128K 甚至更长上下文，不代表在这么长的输入里仍能稳定找到并使用关键信息。随着上下文变长，信息定位和答案生成质量可能下降，位于中段的内容更容易被忽略。

因此长上下文是一种需要验证的能力：用目标长度和真实任务构造评测，比只看标称值可靠。

### 上下文预算怎么花

- 输入和输出共享同一预算；`max_tokens` 只限制输出，输入过长会挤压可用输出空间。
- 上下文变长通常会增加运行时显存、首 Token 延迟和费用。Decoder-only Transformer 服务常用 KV Cache 保存历史表示；其他架构管理历史状态的方式可能不同，见 [02 Transformer](02%20Transformer.md) 和 [推理与部署](../../04%20%E6%8E%A8%E7%90%86%E4%B8%8E%E9%83%A8%E7%BD%B2/README.md)。
- 多模态输入不能按文本 Token 数估算：图片和音频会按模型自己的方式折算成 Token，折算比例取决于分辨率、时长和具体实现。
- 能用检索、压缩或改写去掉无关内容时，通常比塞满窗口更稳定也更便宜。

## 下一个 Token 预测

自回归 LLM 的常见预训练目标是：给定前文，预测下一个 Token 的概率分布。

例如输入：

```text
今天天气很
```

模型不会直接给出整句答案，而是先输出下一步的概率分布，例如：

```text
晴: 0.42
好: 0.31
热: 0.08
冷: 0.05
```

然后从这些候选里选出一个 Token，再继续预测下一个。

因此，自回归 LLM 会逐 Token 生成内容。其他架构也可能使用不同的训练目标，例如掩码语言建模。

## 采样与输出风格

模型算出的是概率分布，但最终输出哪个 Token，还要经过采样策略。

这时候会涉及：

- greedy
- top-k
- top-p
- temperature

这些策略决定的是“怎么选”，而不是“模型知道多少”。

例如：

- 低温度更稳定、更保守
- 高温度更多样、更发散

更详细内容见 [01 生成策略与输出控制](../推理与生成/01%20%E7%94%9F%E6%88%90%E7%AD%96%E7%95%A5%E4%B8%8E%E8%BE%93%E5%87%BA%E6%8E%A7%E5%88%B6.md)，采样参数详解见 [06 LLM生成参数详解](../推理与生成/06%20LLM生成参数详解.md)。

## 为什么 LLM 会显得“很聪明”

表面上看，大模型只是不断预测下一个 Token；但为了把这个预测做准，模型必须在训练中学习很多更深层的规律，例如：

- 语法结构
- 词语搭配
- 事实共现
- 常识关联
- 某些局部推理模式

因此，大模型表现出的“理解感”“知识感”“推理感”，很大程度上来自这些统计规律在大规模训练中的压缩表达。

## 使用 LLM 时要管理的三个限制

随机性、事实可靠性和知识时效性分别受采样、训练目标和训练数据影响，使用时需要分别管理。

### 随机性：同样的输入可能得到不同的输出

除贪心解码外，采样本身引入随机性，同一请求多次调用可能得到不同结果。即使设置 `temperature=0` 或 `seed`，批处理组合、浮点运算顺序和服务端实现仍可能带来差异。

工程含义：

- 不要把单次输出当成稳定契约，关键字段用结构化输出和校验兜住。
- 回归验证要多次采样并统计通过率，而不是只看一次结果。

### 幻觉：输出可能流畅但没有依据

自回归预训练直接优化下一个 Token 预测，并不自动核验外部事实。后训练可以改善事实性和拒答行为，但不能保证答案真实。因此模型仍可能给出语法正确、语气自信、但事实错误甚至捏造的答案，包括不存在的接口、文献、数字和引用。

常见触发条件：

- 问题超出训练数据覆盖范围，或落在知识截止之后
- 上下文缺失、互相冲突，或提供的资料本身有误
- 问题带有错误前提，模型倾向顺着前提续写
- 要求模型给出它并不掌握的具体细节，例如精确条文、编号和统计值

缓解思路是让输出有可核验的依据：检索增强、工具调用、强制标注来源、限定“只根据给定资料回答”，以及应用侧的格式与事实校验。这些手段能降低发生概率，但无法把幻觉降为零；高风险场景还需要人工确认或自动校验环节。

### 知识截止：模型不知道训练之后发生的事

模型内化的知识来自训练数据，训练后发生的事件、版本更新、新发布的库，以及未进入训练数据的内部信息，不会自动写入模型参数。请求中提供的检索结果或工具返回值可以补充外部信息。

更难处理的是，模型通常也无法可靠判断“自己不知道”：信息缺失时它可能给出一个看起来合理的答案，而不是明确说明无法确认。

因此以下内容应放进上下文，而不是依赖模型记忆：

- 时效性信息：价格、版本、政策法规、近期事件
- 私有信息：代码库、内部文档、业务规则、用户数据
- 需要精确引用的信息：条文、编号、接口签名

## 能力从哪里来

模型效果可能来自训练、推理时计算或应用系统；这几个层面的作用和边界不同：

| 能力来源 | 做法 | 代价或边界 |
| --- | --- | --- |
| 训练时扩展 | 增加训练数据、参数或计算量，并进行后训练 | 需要训练资源；效果还取决于数据、目标和训练质量 |
| 推理时计算 | 增加生成预算、采样多个候选、搜索或验证 | 增加单次请求的计算、延迟和成本；不保证质量随预算线性提升 |
| 应用系统能力 | 通过 RAG、工具、代码执行或数据库提供外部信息和操作 | 为模型调用补充外部资料或操作能力；效果取决于数据、权限和工具执行结果 |

三条实践结论：

- 规模带来的收益会递减，且不同任务受益程度不同，换更大的模型不能解决所有问题。
- 指令遵循、格式稳定性和安全边界大多在后训练阶段形成，见 [06 后训练概述](06%20%E5%90%8E%E8%AE%AD%E7%BB%83%E6%A6%82%E8%BF%B0.md) 和 [07 微调](07%20%E5%BE%AE%E8%B0%83.md)。
- 推理时计算可按任务难度调整；RAG 和工具调用可补充外部资料或操作能力，也可与推理预算组合。具体分工见 [02 推理时计算与推理模型](../推理与生成/02%20%E6%8E%A8%E7%90%86%E6%97%B6%E8%AE%A1%E7%AE%97%E4%B8%8E%E6%8E%A8%E7%90%86%E6%A8%A1%E5%9E%8B.md)。

选型时把质量、延迟和成本放在一起评估，见 [09 Benchmark与常见指标](09%20Benchmark%E4%B8%8E%E5%B8%B8%E8%A7%81%E6%8C%87%E6%A0%87.md) 和 [成本](../../05%20%E7%94%9F%E4%BA%A7%E5%B7%A5%E7%A8%8B/%E6%88%90%E6%9C%AC%E4%B8%8E%E5%BB%B6%E8%BF%9F/%E6%88%90%E6%9C%AC.md)。

## LLM 不是什么

理解 LLM 时，也要同时知道它不是什么：

- 它不是数据库：不保证事实永远准确、最新；需要准确事实时，把数据放进上下文或走查询接口。
- 它不是搜索引擎：没有外部检索时，不能天然获取新信息。
- 它不是规则系统：输出不是严格可证明的逻辑推导结果；需要确定性时，由代码和校验承担。
- 它不是安全边界：模型可能被诱导输出越界内容，权限控制和输入输出防护要在应用侧实现。

所以在应用层，LLM 往往还要结合：

- Prompt
- 上下文工程
- RAG
- 工具调用
- 运行时约束
