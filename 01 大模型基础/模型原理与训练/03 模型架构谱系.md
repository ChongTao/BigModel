# 模型架构谱系

模型选型时，网络结构、参数路由、输入模态、训练后用途和部署格式经常被统称为“架构”。它们回答的问题不同，也可以组合。本文聚焦结构类别和组合关系；Transformer 计算细节、Embedding、后训练与部署实现分别见对应专题。

## 先区分模型的几个维度

| 维度 | 常见类别 | 主要回答的问题 |
| --- | --- | --- |
| 序列建模骨干 | Transformer、状态空间模型（SSM）、循环式与混合架构 | 序列信息如何建模和传递 |
| Transformer 结构 | Encoder-only、Decoder-only、Encoder-Decoder | 编码与生成模块如何组织 |
| 参数计算方式 | Dense、Mixture of Experts（MoE） | 每个 Token 会经过哪些参数 |
| 注意力中的 K/V 组织 | MHA、MQA、GQA、MLA | 注意力缓存如何组织与压缩 |
| 模态 | 文本、图像、音频、视频及组合 | 模型接收和生成什么类型的信息 |
| 上下文长度 | 模型或服务声明的 Token 上限 | 单次请求能处理多长的输入和输出 |
| 任务或训练后形态 | Base、Instruct、Reasoning、Coder、Embedding、Reranker 等 | 模型经过何种训练，面向什么任务 |
| 权重精度与格式 | FP16、BF16、FP8、INT4、GGUF 等 | 权重如何存储、量化和交给运行时 |

这些维度可以组合，但并非每个选项都适用于所有模型。例如，MHA、GQA 和 MLA 描述的是注意力中的 K/V 组织方式；GGUF 是模型文件格式；Reasoning 描述训练或推理用途。它们都不是 Transformer 主干的同义词。

上下文长度是模型与服务能力，不是网络结构的类别。标称长度也不等于长文任务质量，实际效果要用目标长度和任务评测，预算概念见 [01 LLM基本概念](01%20LLM%E5%9F%BA%E6%9C%AC%E6%A6%82%E5%BF%B5.md)。

## Transformer 的三种常见结构

这里按信息流区分结构；各层的计算过程见 [02 Transformer](02%20Transformer.md)。

### Encoder-only

常见 Encoder-only 模型使用双向注意力，为输入各位置生成上下文化表示。BERT 是典型代表，可通过任务头或专门训练完成分类、实体识别和文本表示。

它没有标准的因果解码路径，因此通常不直接用于开放式逐 Token 生成。文本 Embedding 的效果取决于训练目标和池化方式，不能仅凭 Encoder-only 标签判断；详见 [04 Embedding](04%20Embedding.md)。

### Decoder-only

Decoder-only 模型使用因果注意力，根据已有上下文预测后续 Token。GPT、Llama、Qwen 和 DeepSeek 等生成模型采用这一结构。

它适合对话、代码和其他可写成续写的生成任务。标准自回归解码存在逐 Token 的依赖，服务端通常用 KV Cache 避免重复计算历史表示；缓存的原理和工程实现见 [推理与部署](../../04%20%E6%8E%A8%E7%90%86%E4%B8%8E%E9%83%A8%E7%BD%B2/README.md)。

### Encoder-Decoder

Encoder-Decoder 先编码输入，再让 Decoder 基于编码结果生成输出。原始 Transformer 和 T5 是代表，可用于翻译、摘要等输入输出边界清楚的转换任务。

通用对话模型常见 Decoder-only 结构，但这不代表 Encoder-Decoder 已被取代，也不代表某种结构对所有任务都更高效。选型要比较目标任务的质量、延迟和成本。

## Transformer 以外的序列建模骨干

| 类别 | 信息传递方式 | 代表与边界 |
| --- | --- | --- |
| 全注意力 Transformer | 在可见位置之间直接计算注意力关系 | 适合灵活读取上下文；标准全注意力的计算量随序列长度平方增长 |
| 状态空间模型（SSM） | 通过状态递推聚合序列信息 | Mamba 是代表；Mamba-2 研究了 SSM 与注意力之间的数学联系，但两者并不能因此视作完全相同 |
| 线性注意力与 Retention | 改写注意力或递推计算，避免显式构造完整的两两注意力矩阵 | RetNet 等属于相关路线；不同方法的状态更新和表达能力并不相同 |
| 循环式架构 | 逐步更新状态并传给下一位置 | RWKV 是代表之一；生成按序列递推 |
| 混合架构 | 在同一模型中组合注意力层与其他序列模块 | Jamba 组合了 Transformer 与 Mamba 模块；其缓存和计算取决于具体层设计 |

纯递推模型的推理状态通常不随已处理 Token 数持续增长；混合模型若含有全注意力层，仍可能需要随上下文增长的 KV Cache。递推状态是压缩表示，精确取回任意历史片段的能力和全注意力不同，效果应按目标任务评测。更深入的 Transformer 结构与复杂度见 [02 Transformer](02%20Transformer.md)。

## Dense 与 MoE

Dense 与 MoE 是参数计算方式，可以和不同的序列建模骨干组合。

| 结构 | 每个 Token 的计算 | 主要权衡 |
| --- | --- | --- |
| Dense | 经过各层的主要参数 | 路径直接；扩大参数规模通常会同步增加每 Token 的计算 |
| MoE | 路由器为每个 Token 选择部分专家参与计算 | 总参数容量可以较大，而单 Token 只激活部分专家；路由和跨设备通信会增加实现复杂度 |

MoE 通常把部分前馈网络替换为多个专家，由路由器选择 Top-k 专家。比较 MoE 时要区分**总参数**和**激活参数**：总参数影响权重存储需求，激活参数可粗略反映单 Token 的计算规模，但都不能单独预测服务速度或整体显存。

完整 MoE 权重通常需要由部署系统提供访问；可以分片到多卡，也可按实现进行卸载，但卸载可能增加延迟。MoE 不保证在所有硬件和负载下都比 Dense 更快或更便宜，路由均衡、批量大小、通信和权重精度都会影响结果。Mixtral、DeepSeek-V3 和 Qwen3 MoE 是不同设计的公开实例，不应只按总参数或激活参数直接比较能力。

MoE 的层内设计见 [02 Transformer](02%20Transformer.md)；并行、显存和服务调度见 [推理与部署](../../04%20%E6%8E%A8%E7%90%86%E4%B8%8E%E9%83%A8%E7%BD%B2/README.md)。

## 注意力中的 K/V 组织

MHA、MQA、GQA 和 MLA 描述注意力中 Key/Value 的组织方式，不是与 Encoder-only、Decoder-only 并列的主干分类。MQA 和 GQA 通过共享 K/V 头减少缓存需求；MLA 将相关信息压缩到潜在表示中。它们对缓存容量、带宽和模型效果的影响不同，细节见 [02 Transformer](02%20Transformer.md) 和 [KV Cache与PagedAttention](../../04%20%E6%8E%A8%E7%90%86%E4%B8%8E%E9%83%A8%E7%BD%B2/%E6%8E%A8%E7%90%86%E5%B7%A5%E7%A8%8B/02%20KV%20Cache%E4%B8%8EPagedAttention.md)。

## 多模态模型

多模态模型的输入和输出模态可以不同。常见的信息融合方式包括：

| 方式 | 基本做法 | 公开实例 |
| --- | --- | --- |
| 编码器加投影层 | 把图像或音频编码后映射到语言模型的表示空间 | LLaVA |
| 交叉注意力 | 让语言模型通过交叉注意力读取其他模态表示 | Flamingo |
| 共享表示序列 | 把不同模态表示放入统一的序列或计算空间 | 多种原生多模态模型采用不同实现 |

融合方式本身不能决定模型是否会生成图像或音频；输出能力还取决于相应的解码器、输出头和训练数据。图像、音频和视频在模型内部可能表示为 Patch、连续特征或专用 Token，具体上下文预算和计费规则要查模型及服务文档。

## 任务标签不等于架构

| 常见标签 | 描述 | 深入内容 |
| --- | --- | --- |
| Base / Pretrained | 预训练模型，可作为研究或继续训练的起点；不一定有稳定的助手交互格式 | [05 大模型训练流程](05%20%E5%A4%A7%E6%A8%A1%E5%9E%8B%E8%AE%AD%E7%BB%83%E6%B5%81%E7%A8%8B.md) |
| Instruct / Chat | 经过指令适配的模型；具体偏好、安全训练方式随模型而异 | [06 后训练概述](06%20%E5%90%8E%E8%AE%AD%E7%BB%83%E6%A6%82%E8%BF%B0.md) |
| Reasoning | 面向多步问题的训练或产品形态，不是单一架构，也不保证展示完整思考过程 | [推理时计算与推理模型](../推理与生成/02%20%E6%8E%A8%E7%90%86%E6%97%B6%E8%AE%A1%E7%AE%97%E4%B8%8E%E6%8E%A8%E7%90%86%E6%A8%A1%E5%9E%8B.md) |
| Coder | 针对代码任务的数据或目标做适配；可以采用不同主干 | 按目标语言、仓库任务和工具能力评测 |
| Embedding / Reranker | 输出向量或相关性分数，服务于匹配和检索 | [04 Embedding](04%20Embedding.md) 与 [检索与RAG](../../02%20%E6%A3%80%E7%B4%A2%E4%B8%8ERAG/README.md) |
| Reward / Guard | 用于偏好评分或安全分类，可作为训练或服务链路中的组件 | 按目标任务和误判成本评测 |
| Distilled / Small | 描述能力迁移方式或模型规模，不是互斥的架构类型 | 查看模型卡并按目标任务评测 |

同一模型可以同时具备多种标签。思考模式也可能是同一份权重支持的推理配置，而不是独立架构或独立模型；具体行为以模型文档为准。

FP16、BF16、FP8、INT4 描述数值精度；GGUF 是模型文件格式，AWQ、GPTQ 常指量化方法及相关权重格式。它们不定义网络主干，但会影响权重占用、运行时兼容和数值效果。模型名称的后缀没有统一顺序，应以具体模型卡为准。开放权重也不自动代表训练数据、训练代码或使用许可开放；商用前要核对该版本的许可证和附加条款。

## 用架构信息辅助选型

1. 先明确输入、输出、任务和质量要求。
2. 判断需要生成、双向理解、向量检索，还是多模态输入输出。
3. 再比较主干、Dense/MoE、上下文能力、精度格式、硬件和服务成本。
4. 使用目标数据与实际负载评估质量、延迟、吞吐和成本；不要只凭参数量或模型标签下结论。
