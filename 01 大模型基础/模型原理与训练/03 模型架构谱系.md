# 大模型架构谱系与模型形态

讨论“大模型架构”时，通常会把网络结构、计算方式、输入模态和训练后形态混为一谈。实际选型应把这些维度分开看：它们彼此组合，单个标签不足以说明模型适不适合某项任务。

## 一、先区分四个维度

| 维度 | 常见类别 | 主要回答的问题 |
| --- | --- | --- |
| 序列建模结构 | Encoder-only、Decoder-only、Encoder-Decoder | 模型如何读取输入、产生输出 |
| 参数计算方式 | Dense、Mixture of Experts（MoE） | 每个 Token 会激活多少参数，计算和显存如何权衡 |
| 输入与输出模态 | 文本、图像、音频、视频及组合 | 模型如何表示和融合不同类型的信息 |
| 训练后产品形态 | Base、Instruct、Reasoning、Embedding、Reranker | 模型经过何种训练，面向什么任务 |

这些维度可以交叉组合。例如，一个模型可以是 Decoder-only、MoE、支持图像输入，并经过指令和推理后训练。

## 二、序列建模结构

### Encoder-only

Encoder 对输入序列进行双向上下文化表示，适合分类、检索表示和文本理解等任务。BERT 是这类结构的典型代表。它通常通过专门的任务头或对比学习目标，形成分类、Embedding 或排序能力。

### Decoder-only

Decoder-only 模型使用因果注意力，根据已有上下文逐 Token 生成后续内容。GPT、Llama、Qwen 和 DeepSeek 等通用生成模型主要采用这一类结构。统一的自回归目标便于覆盖对话、代码、摘要、工具参数生成等任务。

### Encoder-Decoder

Encoder-Decoder 先编码输入，再由 Decoder 生成输出，常用于输入与输出边界清晰的转换任务。T5 是典型代表。当前通用对话模型以 Decoder-only 为主，但这不意味着其他结构失去价值；检索、分类、翻译和专用生成仍会按任务选择结构。

## 三、Dense 与 MoE

| 结构 | 每个 Token 的计算 | 优势 | 需要评估的代价 |
| --- | --- | --- | --- |
| Dense | 经过模型中的全部主要参数 | 计算路径直接，部署和容量规划较容易 | 增大参数规模通常会同步增加每 Token 计算量 |
| MoE | 路由器为每个 Token 选择部分专家参与计算 | 总参数容量可以较大，而每 Token 只激活一部分专家 | 专家权重仍需存放和调度；路由、负载均衡、通信与显存会增加工程复杂度 |

MoE 的“激活参数量较小”不等于模型整体显存一定小，也不保证任何硬件和请求负载下都更快或更便宜。比较 Dense 与 MoE 时，应同时看总参数、激活参数、权重精度、显存容量、并发、通信和真实吞吐。

## 四、多模态模型

多模态模型会把图像、音频、视频等信号转换成模型可处理的表示，再与文本或其他模态的信息融合。实现方式包括模态编码器、投影层、跨注意力或统一 Token 序列等，并不存在一种适用于所有模型的固定结构。

- **图像**：可能先切成多个 Patch 或裁剪区域；一张高分辨率图像消耗的上下文预算会因模型和分辨率而异。
- **音频**：常见任务包括语音识别、语音生成、语音对话和音频理解；输入与输出可能使用离散音频 Token、连续特征或专用编码器。
- **视频**：通常需要抽取或编码时间片段和帧，还要处理时间顺序与音视频同步。
- **多模态交互**：API 中的“图片附件”或“音频输入”会在模型侧转成模型专用表示，不能按普通文本 Token 数简单估算。

因此，评估多模态模型时要检查具体任务、分辨率、时长、输入格式、输出能力和计费口径，不能只根据“支持多模态”的产品标签推断能力。

## 五、训练后常见模型形态

| 形态 | 典型用途 | 选型提示 |
| --- | --- | --- |
| Base / Pretrained | 继续预训练、研究或作为下游训练起点 | 通常不具备稳定的助手交互格式 |
| Instruct / Chat | 问答、对话、指令跟随和工具参数生成 | 检查指令遵循、格式稳定性和安全行为 |
| Reasoning | 复杂数学、代码、规划或多步问题 | 同时评估推理质量、延迟、Token 消耗和工具协作能力 |
| Embedding | 语义检索、聚类和相似度计算 | 按语言、领域、向量维度和检索任务评估 |
| Reranker | 对候选文档或结果进行相关性重排 | 与召回模型组合评估排序收益和额外延迟 |
| Distilled | 从教师模型的输出、评分或轨迹学习能力 | 在目标任务上验证能力迁移和错误变化 |
| Compact / Small | 低延迟、低成本、边缘或专用任务 | 检查实际硬件、量化精度和目标负载下的效果 |

Embedding 和 Reranker 描述任务形态，不限定 Backbone；实际模型可以使用 Encoder-only，也可以使用 Decoder-only 等结构。Distilled 描述能力迁移方式，Small 描述规模或部署形态，两者并不等价。

这些形态不一定对应不同的 Transformer 主干。例如 Reasoning 模型的能力通常与训练数据、后训练目标和推理预算共同相关，不能仅凭模型名称或是否输出“思考文本”判断。

## 六、从公开模型实践中能看到的模式

公开技术报告中常能看到以下组合：同一模型家族提供 Dense 或 MoE 变体、不同尺寸、通用对话与推理形态，也可能提供蒸馏版本或多模态版本。Qwen3 技术报告展示了 Dense/MoE 与思考/非思考模式的组合；DeepSeek-R1 报告讨论了推理后训练及蒸馏模型。

这些例子说明，模型家族不是一条简单的“参数越大越好”序列。真实选型还要看：

- 任务类型、语言和领域分布
- 上下文长度与多模态输入要求
- 指令遵循、推理、工具调用及结构化输出质量
- 延迟、吞吐、成本、硬件和输出 Token 预算
- 部署约束、许可证和安全要求
- 与目标数据集相符的离线评测及小规模线上验证

上下文窗口标称值也不等于长文任务质量。长上下文能力还取决于训练分布、位置编码扩展、信息定位和答案生成等因素；应使用目标长度和任务构造评测。

## 七、把架构知识用到选型

1. 先确定输入输出：文本生成、检索向量、排序、图像问答、语音交互或视频理解。
2. 再选择模型形态：通用对话、推理、Embedding、Reranker 或多模态模型。
3. 对开放权重模型，核对 Dense/MoE、总参数与激活参数、许可证、量化方案和目标硬件。
4. 用同一数据、提示、输出约束和解码设置比较质量；同时记录延迟、吞吐、成本和失败类型。
5. 依据结果决定是否组合模型，例如“Embedding 召回 + Reranker 排序 + 生成模型回答”。

Embedding 与 Reranker 在知识库检索中的设计见 [检索与RAG](../../02%20%E6%A3%80%E7%B4%A2%E4%B8%8ERAG/README.md)；运行时引擎、KV Cache、量化和吞吐见 [推理与部署](../../04%20%E6%8E%A8%E7%90%86%E4%B8%8E%E9%83%A8%E7%BD%B2/README.md)。
