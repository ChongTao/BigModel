# RAG数据预处理

很多 RAG 项目一开始看起来是在“调模型”或“调检索”，但真正最容易卡住的地方，往往是数据接入与清洗。

原因很简单：

- 模型再强，也无法理解脏数据
- 检索再强，也召不回没有被正确入库的内容
- 重排再强，也很难修复源数据本身的结构缺陷

从工程视角看，RAG 的上限通常不是先被模型限制，而是先被数据质量限制。

## 1 RAG 为什么先卡在数据而不是模型

很多团队做 RAG 时，第一反应是：

- 换更好的 Embedding
- 换更强的 Reranker
- 换更大的 LLM

但如果底层数据有问题，这些优化通常收益有限。

常见问题包括：

- 文档根本没有被接入
- PDF 解析后顺序错乱
- 表格、标题、代码块被打散
- 元数据缺失，无法过滤
- 重复文档过多，污染召回
- 历史旧版本和新版本混在一起
- 文本切分前没有清洗，导致 chunk 质量很差

RAG 检索本质上是在“已有数据”里找内容。  
如果数据没有被正确抽取、清洗、切分和标注，那么后面的检索、重排和生成都会建立在不稳定地基之上。

## 2 数据接入阶段要处理什么

数据接入不是简单“把文件丢进向量库”，而是一条完整的数据管道。通常要处理下面几类问题。

### 2.1 数据源识别

首先要明确知识从哪里来，常见来源包括：

- 本地文件系统
- 企业网盘
- Wiki / Confluence / Notion
- Git 仓库
- 数据库
- 工单系统
- FAQ / CRM / 工单评论
- 邮件、聊天记录、客服对话
- 外部网页和 API

不同来源的数据结构完全不同，接入方式也不同。

### 2.2 拉取与同步

接入阶段要解决的不是“一次导入”，而通常是“持续同步”，常见同步方式包括：

- 全量导入
- 增量同步
- 定时批处理
- 事件驱动更新
- 手工触发重建

如果同步机制设计不好，就会出现：

- 知识库内容滞后
- 已删除内容仍被检索到
- 新旧版本同时存在
- 部分更新成功、部分更新失败

### 2.3 格式解析

接入后的第一步通常不是建索引，而是解析原始格式，典型格式包括：

- PDF
- Word
- Excel
- Markdown
- HTML
- JSON / CSV
- 代码仓库文件
- 图片 OCR 文档

格式解析的目标不是“把它转成一串文本”，而是尽量保留原始结构信息，例如：

- 标题层级
- 段落
- 列表
- 表格
- 代码块
- 页面与章节关系

### 2.4 权限与可见性

企业场景里，数据接入还必须考虑权限边界，例如：

- 哪些文档能被入库
- 哪些元数据可以暴露
- 哪些用户能检索哪些文档
- 是否需要按部门、项目、角色做隔离

如果接入阶段不处理权限，后续很容易出现“能检索到不该看到的文档”。

## 3 清洗阶段的关键问题

数据清洗的目标不是让文本“更好看”，而是让数据变得更可检索、更可切分、更可用于生成。

### 3.1 去除无效噪音

原始文档里经常包含大量对检索无帮助的内容，例如：

- 页眉页脚
- 页码
- 导航栏
- 版权声明
- 重复目录
- 模板化按钮文本
- OCR 产生的杂乱字符

这些噪音如果不清除，会直接污染 chunk，影响 Embedding 和召回质量。

### 3.2 保留语义结构

对 RAG 来说，更重要的是保留文档结构，例如：

- 一级标题、二级标题
- 段落边界
- 表格行列关系
- 列表项归属
- 代码块边界
- 引用块

结构一旦丢失，后续很难恢复，因此，清洗应该是“去噪但不去语义结构”。

### 3.3 统一编码与文本规范

不同来源的数据，常见会出现：

- 编码不一致
- 全角半角混乱
- 换行符不一致
- 空格、制表符异常
- 标点与数字格式不统一

这些问题单看很小，但在大规模索引时会不断累积，最终影响切分、去重、过滤和精确匹配。

### 3.4 版本与重复问题

企业知识库里，最常见的脏数据之一就是重复和过时版本：

- 同一份文档多个副本
- 新版旧版同时存在
- 导出文件和源文件都入库
- 相同段落被重复切成多份

如果不处理，会导致：

- 检索结果高度重复
- 新旧结论冲突
- Rerank 资源浪费在重复候选上
- 最终上下文被无效内容占满

### 3.5 结构化字段补全

很多数据在原始形态里并不适合直接检索，例如工单、FAQ、知识条目、合同记录，通常更适合被拆成结构化字段，例如：

- 标题
- 正文
- 作者
- 时间
- 类型
- 标签
- 所属系统
- 版本号

这会显著提升后续过滤、路由和召回质量。

## 4 结构化与非结构化数据的差异

### 4.1 非结构化数据

非结构化数据通常指：

- PDF
- 网页正文
- Word 文档
- Markdown 文档
- 会议纪要
- 对话记录

它们的特点是自然语言多、结构弱、解析成本高，对这类数据，重点通常是：

- 解析结构
- 去噪
- 保留标题层级
- 做合理 chunking

### 4.2 结构化数据

结构化数据通常指：

- SQL 表
- CSV
- 业务记录
- 工单字段
- 商品属性
- 用户资料
- 监控指标

这类数据不一定适合直接做普通文本向量检索，更常见做法是：

- 先做字段映射
- 转成可检索文档
- 保留 schema 和字段含义
- 混合使用结构化查询与语义检索

### 4.3 半结构化数据

很多企业数据其实是半结构化，例如：

- HTML 页面
- JSON 文档
- YAML 配置
- API 返回
- Jira / GitLab / CRM 记录

这类数据通常最适合在接入阶段先抽成：

- 主体文本
- 关键字段
- 元数据

再进入统一索引流程。

## 5 元数据为什么重要

很多团队前期只关注正文内容，忽略了 metadata，但在实际 RAG 系统里，元数据往往决定了检索是否“可控”。常见元数据包括：

- 文档标题
- 来源系统
- 文档类型
- 创建时间 / 更新时间
- 作者 / 部门
- 标签
- 权限范围
- 版本号
- 语言
- 章节路径

元数据的价值主要体现在几个方面。

### 5.1 过滤

例如：

- 只查最近半年文档
- 只查某个系统的知识
- 只查当前用户有权限访问的文档
- 只查中文或英文内容

没有元数据，很多检索只能做全库盲搜。

### 5.2 排序与融合

即便向量相似度接近，也可以基于元数据做额外排序，例如：

- 新版本优先
- 权威来源优先
- 官方文档优先
- 高频使用文档优先

### 5.3 上下文解释

生成答案时，元数据还能帮助模型和用户理解来源，例如：

- 这段内容来自哪个文档
- 是哪个章节
- 更新时间是什么时候
- 是否来自正式制度还是社区帖子

这对可信度和可解释性很重要。

## 6 数据质量对下游检索的影响

### 6.1 对 Embedding 的影响

如果 chunk 里混入了大量噪音，例如页码、导航、乱码、重复模板，那么 Embedding 学到的语义中心就会偏移，结果是：

- 向量表示不稳定
- 相似内容无法聚在一起
- 无关内容反而相似

### 6.2 对 Chunking 的影响

切分策略依赖输入文本的结构质量，如果解析后的文本顺序已经错乱，那么再好的 chunking 也很难救回来。

- 标题和正文分离
- 表格被打散成无意义短句
- 代码块和说明混在一起
- 多栏 PDF 顺序错位

这些都会直接影响 chunk 可读性和召回精度。

### 6.3 对检索结果的影响

脏数据常见会造成：

- 检索结果重复
- 错误版本被召回
- 召回内容缺关键上下文
- 明明有答案却召不回来

### 6.4 对生成结果的影响

生成阶段依赖的是召回结果，如果召回内容脏、旧、重复或互相冲突，模型很可能会：

- 给出模糊答案
- 混合多个版本的信息
- 错引来源
- 产生幻觉式补全

所以，很多生成问题其实不该先去改 Prompt，而应该先检查数据链路。
