# Honcho：状态化 Agent 的长期记忆基础设施

Honcho 是 Plastic Labs 开源的长期记忆基础设施，用于构建能够随时间理解用户、Agent、群组、项目和想法的状态化应用。它不是单纯的聊天记录库或向量数据库：系统先保存原始交互，再在后台提炼结论、画像和摘要，最后把适合当前任务的上下文交给任意模型或 Agent 框架。

在 Hermes 中，Honcho 是可选的记忆后端。它补充本地 `MEMORY.md`、`USER.md` 以及 SQLite Session 历史，而非机械替换它们。

## 1 解决什么问题

长时间运行的 Agent 会积累大量消息、工具结果和用户反馈。若每次都把完整历史放进 Prompt，会带来 Token 成本、延迟和上下文窗口问题；若只做关键词或向量检索，又难以回答“这个用户长期偏好什么”“这个项目已达成哪些共识”等需要归纳的问题。

Honcho 将记忆处理拆成两条路径：

| 路径 | 做什么 | 适合解决的问题 |
| :--- | :--- | :--- |
| 同步存储与查询 | 保存消息、获取会话上下文、检索相关片段 | 当前对话续接、事实回溯、低延迟读取 |
| 异步推理 | 从历史中生成摘要、结论、画像和表示 | 长期偏好、行为模式、跨会话个性化 |

这使 Agent 能够根据长期交互调整沟通方式、记住项目背景，并在多用户、多 Agent 场景中保留参与者关系，同时不必无限扩张单次 Prompt。

## 2 核心概念与数据关系

Honcho 以 Peer（参与者）为中心，而不是只以一条聊天线程为中心。

```text
Workspace（应用或租户隔离边界）
├── Peer（用户、Agent、群组、项目或其他实体）
│   └── Representation / Conclusion（对该实体的推理结果）
└── Session（一次对话、任务或协作上下文）
    ├── 多个 Peer 参与
    └── Message（对话、事件、文档、工具轨迹）
```

| 概念 | 含义 | 使用建议 |
| :--- | :--- | :--- |
| Workspace | 顶层数据隔离单元 | 一个应用、租户或环境使用独立 Workspace |
| Peer | 会持续变化、可被理解的参与者 | 用户和 Agent 都用 Peer 建模；不要把每条消息建成 Peer |
| Session | 一段有边界的对话或任务 | 使用稳定且可追溯的会话标识；多个 Peer 可共同参与 |
| Message | Session 内的原子记录 | 可存对话、事件、文档片段与工具结果，并标记来源 Peer |
| Context / Summary | 面向模型调用的上下文包和摘要 | 按 Token 预算获取，避免直接加载全部消息 |
| Representation | 面向低延迟读取的静态知识快照 | 适合实时个性化或 Agent 初始化 |
| Conclusion | 从观察中归纳出的结论 | 作为辅助信号，重要决策要回查原始事实 |

Session 与 Peer 是多对多关系：一个用户可参与多个 Session；同一 Session 也可包含用户、客服 Agent、专家 Agent 等多个 Peer。Honcho 还能表达一个 Peer 对另一个 Peer 的观察，因此比“用户 ID + 聊天记录”的模型更适合协作型 Agent。

## 3 Honcho Loop：存储、推理、查询与注入

Honcho 的典型工作循环可概括为四步：

```text
1. Store：将消息、事件、文档或工具轨迹写入某个 Session
2. Reason：后台 worker 消费队列，生成摘要、结论和 Peer representation
3. Query：获取会话上下文、混合检索结果、画像或自然语言洞察
4. Inject：把结果转换为模型消息，加入下一次 LLM / Agent 调用
```

### 3.1 Store：保留可追溯的原始材料

写入时至少应包含稳定的 Workspace、Peer 与 Session 标识，并区分消息来源。高价值的工具结果、人工纠正、任务完成情况也应作为事件或消息保存；否则后续推理只能基于不完整的对话文本。

不要将密码、访问凭证、完整个人身份信息或无业务必要的原始数据写入长期记忆。先进行数据最小化和脱敏，并为每类数据定义保留期限。

### 3.2 Reason：异步形成长期记忆

后台 worker 对新消息进行推理，并更新：

- Session 摘要：压缩较长对话，便于继续当前任务；
- Peer representation：对某个用户或 Agent 的低延迟快照；
- Conclusions：从多次交互中提取的偏好、事实、目标或关系性结论；
- 内部检索材料：为后续混合检索与上下文构建服务。

推理是异步过程，新写入的消息可以立即读取，但其新结论不保证立刻出现。实时链路应优先使用已有 representation 或近期 Session context；需要深度归纳时，可以等待后台任务完成或走异步结果通知。

### 3.3 Query：按任务选择读取接口

| 需求 | 推荐读取内容 | 原因 |
| :--- | :--- | :--- |
| 延续当前长对话 | Session context + summary | 直接获得满足 Token 预算的上下文 |
| 寻找历史事实 | Session / Peer / Workspace 范围检索 | 返回相关原始材料，便于溯源 |
| 实时个性化 | Peer representation | 读取快，适合在线请求 |
| 询问长期偏好或目标 | Peer chat / conclusion | 使用推理后的长期洞察 |
| 多人协作理解 | 多 Peer 的 Session 与观察关系 | 区分不同参与者的视角 |

检索结果和推理结论都应有范围限制：先缩小到正确 Workspace，再限制 Peer、Session、时间和数据类型，避免跨租户或跨任务错误召回。

### 3.4 Inject：将记忆变成模型可用上下文

注入时遵循“当前任务优先、长期记忆辅助”的顺序：系统策略和用户当轮请求优先，其次是近期消息、任务相关检索结果与摘要，最后才是长期 representation 或结论。为每个层级分配 Token 预算，并记录最终注入内容的来源，以便排查错误回答。

## 4 在 Hermes 中如何使用

Hermes 的本地记忆和 Honcho 可分工如下：

| 存储层 | 适合保存 | 特点 |
| :--- | :--- | :--- |
| `MEMORY.md` / `USER.md` | 明确、稳定、人工可维护的偏好和事实 | 可读、可控，会话启动时注入 |
| SQLite + JSONL Session | 原始对话、工具调用、运行状态 | 可追溯、本地检索、便于排障 |
| Honcho | 跨会话的实体画像、关系与推理结论 | 异步、可扩展、支持多参与者建模 |

启用路径通常为：

1. 先使用 `hermes memory setup`，选择 Honcho 并指定托管或自托管服务。
2. 为每个业务域规划 Workspace；不要让开发、测试和生产共享同一记忆空间。
3. 规定用户、Agent、项目等实体的 Peer 标识规则，并为会话设计稳定的 Session 标识。
4. 从用户消息、Agent 回复、工具执行结果和人工纠正中选择可保存的事件。
5. 在回复前按场景读取 Context、Representation 或检索结果，并限制注入 Token。
6. 通过抽样评估检验记忆是否有助于任务；无收益或造成错误联想时，收紧写入和检索范围。

对于现有 Hermes 用户，建议先从单个低风险场景灰度接入，例如个人知识助手或内部 FAQ。确认数据隔离、延迟和回答质量后，再扩展至多 Agent 或客户交互场景。

## 5 部署选择

| 方式 | 适用场景 | 需要关注 |
| :--- | :--- | :--- |
| 托管服务 | 快速验证、团队不想维护数据库与 worker | 数据处理边界、网络可用性、供应商成本 |
| 自托管 | 数据驻留、私网接入、定制策略或较大规模 | PostgreSQL、`pgvector`、后台 worker、备份与升级 |

Honcho 的开源服务以 FastAPI 为核心；自托管时使用 PostgreSQL 和 `pgvector` 保存持久化数据与向量检索材料，并需要后台 worker 处理推理队列。生产部署至少应把 API 服务、数据库与推理 worker 的健康状态分别观测，避免“写入成功但长期记忆不再更新”的隐性故障。

### 5.1 自托管运行要点

- 数据库：启用备份、迁移流程、连接池监控和恢复演练；升级前先在隔离环境验证迁移。
- Worker：根据写入量和推理时延独立扩缩容，监控队列积压、失败率和处理滞后。
- 模型：为摘要、推理、嵌入等不同工作选择合适的模型与预算，避免后台任务挤占在线流量。
- 网络：API、数据库、worker 之间使用最小网络权限；将凭证放入密钥管理系统，不写入文档、日志或消息。
- 可观测性：关联写入量、队列深度、推理耗时、查询延迟、召回质量与每个 Workspace 的成本。

## 6 功能与典型场景

### 个性化助手

通过 Peer 的长期表示保留用户的沟通风格、偏好和已确认目标。在生成回复前，读取有限的 representation，而不是把所有历史消息放入 Prompt。用户可以查看、修正或删除这类记忆，避免错误画像长期固化。

### 客服与工单协作

将客户、客服 Agent、订单或工单建模为 Peer / Session。Agent 可检索同类问题、当前工单摘要和客户历史偏好；涉及订单状态、退款金额等事实时，必须以业务系统返回的数据为准，不能以推理结论替代。

### 多 Agent 项目协作

让规划、执行、审查等 Agent 作为不同 Peer 参与同一项目 Session，保留决定、工具轨迹与待办。这样新加入的 Agent 能读取项目摘要和已达成结论，同时仍能追溯到原始消息。

### 知识助手与文档摄入

将文档片段作为消息或事件摄入，再按 Session / Peer / Workspace 范围检索。对于经常变化的制度或产品文档，要记录来源和版本，并设置更新与删除流程，防止旧知识持续影响回答。

## 7 生产治理与常见误区

### 数据治理

- 按租户、环境和业务域隔离 Workspace；开发样本不得混入生产记忆。
- 支持导出、删除与失效处理；当用户撤回授权或资料过期时，同步删除原始记录、索引和派生结论。
- 为每个 Message、摘要和结论保留来源、时间、版本与置信信息，便于审计。

### 质量治理

- 将“结论是否正确、是否有助于任务、是否引起错误个性化”作为评测指标，而不只看检索命中。
- 对长期结论设置有效期和重新验证机制；用户偏好、项目状态会随时间变化。
- 高风险场景使用原始证据或人工确认；不要将自然语言洞察直接转成有副作用的工具动作。

### 性能与成本

- 把同步上下文读取与异步推理分离，在线请求不要等待所有后台任务完成。
- 为 Context 设置 Token 上限，为检索设置范围和结果数上限，避免记忆召回本身造成成本失控。
- 监控队列积压、worker 错误率、查询 P95、模型调用量和每个 Workspace 的资源消耗。

常见误区是将 Honcho 当作“自动正确的用户画像库”。Honcho 提供的是可推理、可检索的记忆层；其结论仍可能过时、受样本偏差影响或被不可信输入污染。正确做法是保留原始来源、控制写入边界、持续评测，并提供用户纠正和删除能力。

## 8 与其他记忆方案的关系

| 方案 | 擅长内容 | 不足或需要补充 |
| :--- | :--- | :--- |
| Prompt 内历史 | 最近期上下文、实现最简单 | 容量有限，成本和延迟随历史增长 |
| Markdown 记忆 | 显式规则、人工维护的长期事实 | 不适合大量历史和自动关系推理 |
| 向量数据库 / RAG | 文档语义检索与知识问答 | 不能天然形成用户或 Agent 的长期画像 |
| Hermes SQLite Session | 本地会话历史、审计与全文搜索 | 跨实体推理和多参与者建模有限 |
| Honcho | 实体中心记忆、后台推理、摘要、结论和上下文构建 | 需要额外服务、数据治理和异步处理能力 |

实际系统通常组合使用：短期对话放在 Prompt，明确规则写入 Markdown，原始运行历史保留在 Session，文档知识走 RAG；Honcho 负责将长期交互提炼为可供 Agent 使用的实体记忆。
