# Neo4j Agent Memory：安装、使用与记忆管理

[Neo4j Agent Memory](https://github.com/neo4j-labs/agent-memory) 是构建在 Neo4j 上的图原生记忆系统，将 conversation、知识图谱与 reasoning memory 纳入同一图模型。它适合需要理解实体关系、保留历史演化，并让 Agent 参考过往任务经验的应用。

## 1 核心定位

| 维度 | 说明 |
| --- | --- |
| 类型 | Graph-native memory service |
| 核心记忆 | Conversation、knowledge graph、reasoning memory |
| 后端 | 托管 NAMS 或自托管 Neo4j |
| 适合场景 | 企业实体图谱、客户关系、关系推理与长期 Agent 经验沉淀 |

它不是“将聊天记录放进 Neo4j”这么简单。有效接入需要同时定义对话留存、实体与关系建模、推理轨迹的用途，以及用户/租户之间的数据边界。

## 2 部署与连接

### 2.1 两种部署路径

| 路径 | 适用情况 | 主要责任 |
| --- | --- | --- |
| Hosted NAMS | 希望快速验证，少管理基础设施 | 服务商管理运行与存储基础设施 |
| 自托管 Neo4j | 需要数据驻留控制、已有 Neo4j 平台或定制图模型 | 团队管理数据库、网络、升级、备份与权限 |

选择自托管时，先按 Neo4j Agent Memory 对应版本的官方 README 部署服务和 SDK；同时按 Neo4j 官方生产建议配置数据库版本、内存、TLS、备份和监控。

### 2.2 凭据与网络

连接服务所需的端点、数据库用户、密码或 API Key 必须由部署环境的密钥管理服务提供。不要将它们写入源码、Agent prompt、日志或 Markdown 示例。

生产网络应限制为应用服务到 Neo4j / NAMS 的必要通路，启用认证和加密传输，并为读写 Agent 使用最小权限的专用身份。

## 3 接入工作流

### 3.1 先确定记忆边界

为每个业务域明确以下范围：

- **Conversation memory**：哪些会话允许保留、保留多久；
- **Knowledge graph memory**：哪些实体、关系、事件应抽取并可查询；
- **Reasoning memory**：哪些任务过程、决策依据和结果值得复用；
- **作用域**：用户、组织、项目、Agent 与租户如何隔离。

不要直接把模型的全部内部推理或工具输出无差别持久化。应只保存可审计、确有复用价值、且符合数据与隐私政策的摘要、决策和可观察执行结果。

### 3.2 写入与检索

典型链路如下：

```text
对话 / 工具事件 / 业务事实
          ↓
写入 conversation、实体关系或任务经验
          ↓
Neo4j 图模型持续关联与更新
          ↓
当前任务查询相关会话、关系与历史经验
          ↓
只将少量高相关结果注入 Agent 上下文
```

使用 SDK 时，以所安装版本的官方示例为准：创建客户端或服务连接，带着已认证的作用域写入记忆，再按当前任务检索。不要混用 README 中不同版本或 Hosted / 自托管模式的参数。

### 3.3 查询设计

图记忆检索应同时考虑：

- 当前用户或组织的访问范围；
- 起始实体与允许的关系深度；
- 时间条件和事实来源；
- 返回给 Agent 的结果数量与 token 预算。

高风险事实（权限、账户状态、金额、实时库存等）需要返回权威业务系统复核，不能只依赖历史记忆图。

## 4 图记忆治理

### 4.1 实体、关系与来源

统一实体标识和关系命名；每条重要关系应尽可能保留来源、写入时间、有效时间和置信度。否则图会累积同义实体、冲突关系和无法解释的推理结果。

### 4.2 更正与删除

系统应支持：

1. 更正错误的会话摘要、实体或关系；
2. 删除用户要求清除的 conversation 和记忆；
3. 标识过期或已被新事实取代的关系；
4. 记录操作人、时间和影响范围，保留合规审计；
5. 对敏感字段写入前脱敏或禁止保存。

### 4.3 reasoning memory 的边界

Reasoning memory 应保存可验证的经验，例如“采用了何种策略、调用过哪些工具、结果是否成功、复用时应注意什么”。避免储存未经审查的模型思维过程、私人数据或可能被误当作事实的错误推断。
