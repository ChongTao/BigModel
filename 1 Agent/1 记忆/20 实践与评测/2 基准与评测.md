# Agent 记忆基准与评测

评测 Agent Memory 不应只看检索命中率，还要验证它是否在正确的时间召回正确的信息、避免错误信息进入决策，并能随着事实变化而更新。各阶段的职责与失效模式见[记忆生命周期](../3%20记忆生命周期.md)，系统模块见[记忆架构](../2%20记忆架构.md)，被评测的实现见[开源方案索引](../10%20开源方案/1%20开源方案索引.md)。

## 一、核心评测维度

| 维度 | 要验证的问题 | 示例指标 |
| --- | --- | --- |
| 写入质量 | 值得记的信息是否被正确抽取 | 精确率、召回率、人工接受率 |
| 检索质量 | 当前任务是否取回正确记忆 | Recall@K、MRR、nDCG、上下文相关性 |
| 更新与冲突 | 新事实能否替代过时事实 | 冲突解决正确率、过期记忆误召回率 |
| 端到端收益 | 记忆是否改善任务表现 | 任务成功率、用户满意度、重复澄清次数 |
| 系统成本 | 记忆是否可持续运行 | 延迟、token、存储与索引成本 |
| 安全与隐私 | 是否越权或泄漏 | 权限隔离通过率、删除完成率 |

## 二、维度与公开基准的对应

公开基准覆盖的维度并不重合，选型时应按要验证的问题反查：

| 评测维度 | 可优先参考 |
| --- | --- |
| 检索质量与事实召回 | LoCoMo、PerLTQA、MemoryAgentBench（准确检索） |
| 更新与冲突 | LongMemEval（知识更新、时间推理）、MemoryAgentBench（冲突消解）、StateMemBench |
| 不编造与弃答 | LongMemEval（abstention 题型） |
| 偏好遵循 | PrefEval、LongMemEval（偏好类题型） |
| 容量与效率 | MemBench（capacity / efficiency）、MemoryBench（memory time） |
| 实时性与长历史 | DialSim、LongMemEval_M |
| 端到端收益与持续学习 | MemoryBench、STATE-Bench |
| 安全、隐私与删除 | 公开基准基本不覆盖，必须自建 |

## 三、LoCoMo：超长多会话对话记忆

[LoCoMo](https://arxiv.org/abs/2402.17753)（Maharana et al., Snap Research, ACL 2024）是目前被引用最多的对话记忆基准，用于回答“系统能否记住并推理跨越很多个 session 的对话内容”。

### 3.1 数据构成

- 论文收集了 50 段超长对话；常被用于评测的子集约 10 段，合计 1,986 个问答对。
- 每段对话平均约 300 轮、9K token，最多跨 35 个 session；把完整历史拼进上下文时可达约 26K token。
- 构造方式是以 persona 与时间事件图为骨架由模型生成，再经人工校验，因此事实之间带有明确的时间与因果关系。

### 3.2 五类问题与三项任务

| 问题类型 | 考察内容 |
| --- | --- |
| Single-hop | 答案来自单个 session 的直接事实 |
| Multi-hop | 需要综合多个 session 的信息 |
| Temporal | 需要时间推理，捕捉对话中的时间线索 |
| Commonsense / world knowledge | 需要结合对话外的常识作答 |
| Adversarial | 对话中并不存在答案，考察是否编造 |

除问答外，LoCoMo 还提供事件图摘要（event summarization）与多模态对话生成两项任务，可用于评估记忆是否支持归纳与续写，而不只是检索。

### 3.3 判分方式

问答常用 F1 或 LLM-as-judge 判分，摘要与对话生成多用 ROUGE / BLEU 类指标加人工评估。不同论文对“是否给完整历史、是否截断、用哪个裁判模型”的处理并不一致，比较分数前必须对齐这些设置。

### 3.4 使用注意

- **标注与判分缺陷**：社区审计发现答案键存在错误（约 6.4%），LLM 裁判对刻意错误答案的接受率偏高，直接刷榜的分数解释力有限。
- **上下文规模偏小**：以 2026 年的长上下文能力衡量，9K~26K token 已不算压力测试。
- **不显式考察演化**：知识更新、失效与弃答不是 LoCoMo 的重点，这部分应交给 LongMemEval 或自建集。
- **复现分歧明显**：不同记忆系统在 LoCoMo 上的公开对比结论差异较大，厂商自测与第三方复现常不一致。
- **衍生版本**：[LoCoMo-Plus](https://aclanthology.org/2026.acl-long.1150/)（ACL 2026, arXiv:2602.10715）新增第六类 Cognitive 任务，专门考察线索与触发语义不一致时的隐性召回；同一批模型与记忆系统从 LoCoMo 切到 LoCoMo-Plus 后普遍下降 25~37 分，是比原版更严格的升级选项。

## 四、LongMemEval：长期交互记忆的五项能力

[LongMemEval](https://arxiv.org/abs/2410.10813)（Wu et al., ICLR 2025）面向“聊天助手的长期交互记忆”，把记忆能力拆成五项可分别度量的维度。

### 4.1 五项能力与七种题型

| 能力 | 含义 | 对应题型 |
| --- | --- | --- |
| 信息抽取 | 从历史中准确回忆用户或助手说过的内容 | single-session-user、single-session-assistant |
| 偏好记忆 | 记住并沿用用户偏好 | single-session-preference |
| 跨会话推理 | 综合多个 session 的信息作答 | multi-session |
| 知识更新 | 事实变化后使用新值而不是旧值 | knowledge-update |
| 时间推理 | 判断事件发生时间与先后顺序 | temporal-reasoning |
| 弃答 | 历史中没有的信息应回答不知道 | abstention |

共 500 道人工构造问题。其中 knowledge-update 与 abstention 两类题目，正对应生命周期里的演化阶段与“不编造”的降级要求，是 LoCoMo 覆盖不到的部分。

### 4.2 两种规模

| 测试集 | 每题历史规模 | 用途 |
| --- | --- | --- |
| LongMemEval_S | 约 115K token，30~40 个 session | 常规评测，成本可控 |
| LongMemEval_M | 约 500 个 session，约 1.5M token | 压力测试，检验规模化后的检索与成本 |

### 4.3 主要结论

- 长上下文模型在 LongMemEval_S 上出现约 30%~60% 的性能下降，说明“把历史全塞进上下文”并不等于有记忆。
- 商用记忆增强系统相对直接提供完整上下文也有明显下降（论文报告 ChatGPT、Coze 分别约 37% 与 64%），说明记忆层的抽取与检索本身会丢信息。
- 带索引与时间感知设计的记忆系统能显著缩小这一差距。

### 4.4 使用注意

- 弃答题目要求系统能输出“没有相关信息”，评测时要允许空答案，否则会把保守策略误判为失败。
- 知识更新题目应同时统计“新值正确率”和“旧值误召回率”，只看总准确率会掩盖冲突处理缺陷。
- 可以在 session 中人为插入与业务同分布的干扰内容，让基准更贴近真实场景。
## 五、MemoryBench：记忆与持续学习

[MemoryBench](https://arxiv.org/abs/2510.17281)（Ai et al., 清华 THUIR, 2025；[代码](https://github.com/THUIR/MemoryBench)、[数据集](https://huggingface.co/datasets/THUIR/MemoryBench)）把问题从“给定固定历史后能否答对”换成“系统在服务过程中能否从持续到达的用户反馈里学到东西”，即记忆与持续学习的联合评测。

### 5.1 评测思路

- 传统基准先灌入一段历史再提问；MemoryBench 按时间顺序逐条投喂数据，模拟真实服务期不断到来的用户反馈。
- 系统需要一边作答、一边沉淀可复用经验，后续任务的表现直接取决于前面沉淀的质量。
- 因此它覆盖的是生命周期中的巩固、演化与“使用即反馈”闭环，而不只是检索环节，阶段职责见[记忆生命周期](../3%20记忆生命周期.md)。

### 5.2 数据与任务构成

| 项目 | 内容 |
| --- | --- |
| 数据规模 | 28 个数据集 |
| 覆盖领域 | 学术与知识、法律、开放域 |
| 任务形态 | LiLo / LiSo / SiLo / SiSo，即长/短输入 × 长/短输出的四种组合 |
| 被测对象 | 10 个记忆系统 × 4 个基座模型 |
| 判分方式 | ELO 相对评分 + memory-time 效率指标 |

四种任务形态并非冗余：长输入短输出主要考检索与压缩，短输入长输出主要考生成时能否调用已沉淀的知识，单一形态的基准无法区分这两类失败。

### 5.3 使用注意

- ELO 是相对排名而非绝对分数，参赛系统或裁判模型变化后需整榜重算，不能与旧榜单的数字直接比较。
- memory-time 把收益与耗时放在一起看，正好对应核心维度中的“系统成本”，内部评测建议保留这一列而不是只报正确率。
- 持续学习设定下投喂顺序会影响结果，复现时必须固定数据流顺序、系统版本与随机种子。

## 六、其他可选基准

以下基准覆盖前三个基准未触及的侧面，按需组合即可，不必全跑：

| 基准 | 出处 | 覆盖重点 | 适用场景 |
| --- | --- | --- | --- |
| MemBench | arXiv:2506.21605（ACL 2025 Findings） | 参与/观察 × 事实/反思 × 准确性/召回/容量/效率 | 需要统一矩阵拆解记忆能力 |
| MemoryAgentBench | arXiv:2507.05257（ICLR 2026） | 准确检索、测试时学习、长程理解、冲突消解 | 增量多轮的 Agent 记忆 |
| MemoryArena | arXiv:2602.16313（2026） | 多会话 Memory-Agent-Environment 闭环，子任务之间相互依赖 | 记忆能否支撑连续任务而非事后回忆 |
| DialSim | arXiv:2406.13144 | 多方对话（平均约 350K token）+ 限时随机提问 | 实时性与多角色场景 |
| PrefEval | arXiv:2502.09597（ICLR 2025） | 长上下文对话中推断、记忆并遵循用户偏好 | 偏好一致性专项 |
| PerLTQA | arXiv:2402.16288（SIGHAN 2024） | 141 份画像、8,593 个问题，语义记忆与情景记忆分离 | 个性化记忆的分类/检索/合成 |
| MSC | arXiv:2107.07567（ACL 2022） | 多会话人人对话（Beyond Goldfish Memory） | 早期基线与对话连贯性 |
| M3Exam | arXiv:2606.07402（2026） | 15 个 persona、239 段多会话多模态对话 | 图像等多模态记忆 |
| STATE-Bench | Microsoft, 2026（[代码](https://github.com/microsoft/STATE-Bench)） | 客服/差旅/购物 3 个领域、450 个任务、确定性判分、记忆无关 | 企业工作流的任务级端到端评测 |
| StateMemBench | arXiv:2608.19652（2026） | 234 个多会话场景、两种对话长度区间、封闭候选池判分 | 状态随时间演化时能否跟上新值 |

组合建议：先用 LongMemEval_S 建立能力基线，用 LoCoMo 补跨会话事实召回，用 MemoryBench 或 MemoryArena 看持续学习与任务级收益；PrefEval、DialSim、M3Exam、StateMemBench 属专项加测，只在业务确实依赖该能力时引入。

## 七、自建测试集应覆盖的情形

公开基准与自建集分工明确：公开基准用于横向对比和能力体检，自建集用于验证与自身业务同分布的记忆是否真的生效。下列情形必须有自建覆盖。

- 跨会话偏好回忆：用户在早期表达的稳定偏好能被后续任务正确使用。
- 时效事实更新：新状态出现后，旧状态不会继续主导回答。
- 干扰与冲突：大量无关历史存在时，系统不会召回错误记忆。
- 多主体隔离：不同用户或租户的记忆严格不可见。
- 长任务恢复：中断后能恢复计划和关键中间状态，而不重复执行高风险动作。
- 弃答与编造率：历史中确实没有答案时应回答“没有相关信息”，并单独统计编造率。
- 删除与合规生效：用户要求遗忘后，原始记录、索引、摘要与派生数据一并清除且不再被召回。
- 成本与延迟预算：同等正确率下的检索耗时、token 消耗与存储增量应作为上线门槛而非事后指标。
- 标注规范：每条标准答案同时标注主体、时间范围、证据来源、是否允许写入长期记忆，以及存在多个正确答案时的判分规则。

## 八、评测原则与常见陷阱

离线检索指标只能作为诊断；最终应以真实 Agent 任务的正确性、成本和安全性作为是否上线的依据。

- 先固定判分协议：裁判模型、判分 prompt、是否提供完整历史、截断长度必须在对比前统一，否则不同论文的数字不可比。
- 警惕饱和与过拟合：LoCoMo 一类基准的历史规模已偏小，高分可能只说明长上下文能力，不代表记忆设计有效。
- 必须同时报成本：正确率提升若伴随数倍延迟或 token 消耗，应给出成本曲线而不是单点数字。
- 看退化曲线而非单点：按历史长度分桶（如 32K / 128K / 1M）统计正确率衰减，才能定位问题出在检索还是组装。
- 注意合成数据偏置：多数基准的对话由模型生成，事实密度与干扰分布与真实业务不同，结论迁移前需抽样验证。
- 记录复现差异：同一系统在不同实现下分数可能相差很大，内部评测应固定代码版本、数据流顺序与随机种子。
- 安全与隐私只能自建：公开基准基本不覆盖权限隔离与删除合规，这部分应作为发布前的阻塞项。
