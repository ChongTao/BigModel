# RAG 检索：从向量召回到混合检索

检索的职责是从知识库中找出能够回答当前问题的证据。它不直接生成答案；它决定后续重排器和大模型是否有机会看到正确的内容。

## 一 常见三类检索方式

### 1.1 稀疏检索：守住精确词面

稀疏检索通常依赖倒排索引，以 TF-IDF、BM25 等方法计算查询词与文档词的匹配程度。它擅长：

- 产品名、接口名、函数名、字段名和专有名词；
- 错误码、版本号、型号、日期和精确数字；
- 用户输入和原文表述高度一致的场景。

它速度快、可解释性强，但对同义改写和自然语言意图的泛化较弱。

### 1.2 稠密检索：理解语义接近

稠密检索（Dense Retrieval）即通常所说的向量检索。它把 query 与文档编码为稠密向量，再寻找语义距离最近的内容。

例如，用户问“怎样限制接口请求频率”，文档写“Rate limiting configuration”，两者没有完整的相同词，但仍可能在向量空间中接近。它特别适合自然语言问答、FAQ 和表达方式差异较大的知识库。

### 1.3 混合检索：同时覆盖词面与语义

生产系统常把 BM25 与向量召回并行使用：前者保证精确实体命中，后者补足同义表达与语义相近内容。两路结果经融合、去重后，再交给重排器。

`Query → BM25 召回 + 向量召回 → 融合 → Rerank → 上下文`

混合检索不是简单地“多取一些结果”，而是让两类误差模式互相补偿。包含错误码、配置项、自然语言问题的企业知识库尤其适合采用它。

## 二 向量检索的核心概念

### 2.1 从文本到向量

Embedding 模型把一段文本编码为固定维度的浮点数数组，例如：

`“如何配置限流” → [0.12, -0.03, ...]`

向量中的单个维度通常没有可直接解释的业务含义；重要的是整体位置关系。语义、主题、意图相近的文本，会被训练成在向量空间中更接近。

建库时，每个 chunk 都要生成文档向量；查询时，同一个或兼容的模型把 query 编码为查询向量。系统据此找出距离最近的 Top-K chunks。

### 2.2 双塔检索与“可比性”

多数向量检索采用双塔（bi-encoder）结构：query 与 document 分别编码，因此文档向量可以提前离线计算并建立索引，在线只需计算一次 query 向量，适合大规模召回。

这也意味着 query 与文档必须处于**同一个可比较的向量空间**，应注意：

- 查询与文档应使用同一模型、同一版本和一致的预处理方式；
- 有些模型要求在 query 前添加检索指令或前缀，文档侧也可能有不同模板；
- 更换 embedding 模型、维度或归一化策略后，必须重建对应向量，不能与旧索引混用；
- 多语言、代码、领域术语等数据，应选择在相应任务上表现可靠的检索模型。

### 2.3 相似度如何计算

常见的相似度或距离度量有：

| 度量 | 含义 | 工程注意事项 |
| --- | --- | --- |
| 余弦相似度 | 比较两个向量夹角，关注方向 | 文本检索中最常见；向量归一化后适用 |
| 点积 | 对应维度相乘后求和 | 计算高效；需遵循模型训练时的约定 |
| 欧氏距离 | 计算空间中的直线距离 | 更常用于特定索引或未归一化向量 |

以余弦相似度为例：

`cos(q, d) = (q · d) / (||q|| × ||d||)`

分数的绝对值并不天然代表“答案正确率”。不同模型、索引、数据集的分数分布不同，因此不要把一个未经验证的固定阈值直接迁移到另一套系统。

## 三 从文档到召回

### 3.1 离线：构建可检索知识库

1. **解析与清洗**：提取正文、标题、表格、代码和来源信息，去除导航、页脚等噪声。
2. **分块**：按标题、段落或语义边界切成可独立理解的 chunk，并适当保留上下文重叠。
3. **补充元数据**：写入文档 ID、chunk ID、标题、来源 URL、更新时间、文档类型、权限范围等。
4. **向量化**：对每个 chunk 生成 embedding；必要时把标题或父级章节与正文共同编码。
5. **建索引**：将向量、原文和元数据写入向量数据库或支持向量索引的搜索引擎。

一个可用的记录不应只有 `vector` 和 `text`，还应能追溯来源并支持过滤。例如：

```text
chunk_id: api-rate-limit-03
text: 限流配置说明……
title: API 限流
source: docs/api.md
updated_at: 2026-08-01
document_type: technical-doc
access_scope: engineering
embedding_model: example-embedding-v1
```

### 3.2 在线：处理一次用户查询

1. **查询理解**：识别语言、实体、时间范围、产品版本和权限条件；必要时做 query rewrite 或拆分子问题。
2. **生成查询向量**：用与文档侧兼容的 embedding 模型编码 query。
3. **过滤与召回**：在允许访问、符合时间或文档类型条件的范围内检索 Top-K。
4. **多路融合**：将向量结果与 BM25 等结果合并、去重并融合排序。
5. **精排与上下文构造**：用 reranker 选出最直接回答问题的少量片段，再按 token 预算组织上下文。

### 3.3 Chunk 是向量检索的最小语义单位

向量检索检索的通常不是整篇文档，而是 chunk。chunk 过小会丢失条件、定义或步骤；过大又会混入多个主题，使向量表示模糊、上下文冗余。

实用原则是让每个 chunk 尽量能独立回答一个小问题，并保留标题、章节路径或父文档信息。对于命中的子块，可在最终构造上下文时再补回其相邻段落或父级摘要。

## 四 向量索引与 ANN

### 4.1 为什么不能总是全量比对

如果库中有 N 个向量，精确搜索要计算 query 与全部 N 个向量的相似度。小规模数据可直接暴力搜索；当 chunk 达到数十万、数百万甚至更多时，延迟和成本会迅速上升。

ANN（Approximate Nearest Neighbor，近似最近邻）通过牺牲极少量理论最优性换取更低延迟。RAG 的初召回通常允许这一取舍，因为后续还有融合和重排。

### 4.2 常见索引类型

| 索引 | 基本思路 | 优点 | 典型权衡 |
| --- | --- | --- | --- |
| Flat | 全量计算相似度 | 结果精确、实现简单 | 大规模时延迟高 |
| HNSW | 构建多层近邻图并逐层导航 | 召回高、查询快、使用广泛 | 内存占用较高，构建和更新有成本 |
| IVF | 先把空间划分为多个簇，只搜索部分簇 | 可控制搜索范围，适合大规模 | 聚类质量和探测簇数会影响召回 |
| IVF-PQ | 在 IVF 基础上压缩向量 | 节省内存，适合超大规模 | 压缩会带来精度损失 |

没有一种索引在所有规模和硬件条件下都最好。选择时应同时衡量数据量、更新频率、内存预算、P95 延迟和 Recall@K。

### 4.3 ANN 的关键参数

不同引擎名称不同，但通常都在控制“搜索得多深”：搜索范围越大，召回越接近精确检索，但延迟也越高。调参应在固定测试集上观察 Recall@K 与延迟的曲线，而不是只追求单一指标。

## 五 混合检索与结果融合

### 5.1 何时需要混合检索

如果 query 中经常出现错误码、接口名、版本号或精确数字，纯向量检索容易出现“意思相近但事实不对”的结果；如果用户多为口语化、同义改写的提问，纯 BM25 又会漏召回。两者同时存在时，优先考虑混合检索。

### 5.2 常见融合策略

1. **合并去重**：分别取两路 Top-K，按 chunk ID 合并后送入 reranker。实现简单，适合先验证收益。
2. **RRF（倒数排名融合）**：不比较原始分数，而是按每一路的排名累加得分。它不依赖分数尺度，通常是稳健的默认方案。
3. **加权分数融合**：归一化 BM25 与向量分数后加权。可精细控制，但必须在验证集上校准，不能直接相加。
4. **路由检索**：检测到错误码、标识符时提高稀疏检索比重；描述型问题时提高向量检索比重。适合查询类型差异明显的场景。

融合后仍要处理重复和多样性：不要让前几个位置被同一篇文档的近似段落占满；对于需要多方面证据的问题，应保留不同子主题的高质量 chunk。

## 六 与 Reranker 的协作

向量检索擅长从全库快速找出“可能相关”的候选，reranker 擅长在较小候选集中判断“哪一段最能回答这个问题”。两者职责不同：

- 向量召回解决覆盖率与速度；
- BM25 补足精确词面；
- 融合解决多路候选的组织；
- Reranker 改善最终 Top-N 的排序质量；
- 上下文压缩控制 token 成本并保留证据。

更详细的模型类型、成本权衡和排障方式见 [`9 Reranker.md`](./9%20Reranker.md)。

## 七 如何评估向量检索

检索评估至少应区分“有没有找到”和“排得够不够靠前”。

| 指标 | 回答的问题 |
| --- | --- |
| Recall@K | 正确证据是否在前 K 个候选中出现 |
| Precision@K | 前 K 个候选中有多少真正相关 |
| MRR | 第一个正确结果是否排得靠前 |
| nDCG | 多个结果具有不同相关等级时，整体排序是否合理 |
| P50/P95 延迟 | 大多数及较慢请求的响应时间是否可接受 |
| 成本与索引规模 | 向量存储、计算和 rerank 是否满足预算 |

评测集应覆盖真实查询分布：自然语言问法、专有名词、短 query、长 query、多语言、过期内容、权限边界和无答案问题。除检索指标外，还需观察最终答案的正确性、忠实度和引用准确率。
