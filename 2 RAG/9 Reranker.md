# Reranker：RAG 的二阶段精排

Reranker（重排器）位于初召回之后，用来在一批候选 chunk 中找出最能回答当前问题的内容。

它不负责从全库搜索，也不负责生成最终答案。它解决的是：**正确内容已经被召回，但没有排在足够靠前的位置**。

典型链路如下：

`Query → BM25 / 向量召回 → 融合去重 → Reranker → Top-N 上下文 → LLM`

相关内容见：[`5 RAG检索.md`](./5%20RAG检索.md)。

## 一、为什么初召回后还需要重排

初召回需要在大规模知识库上快速运行，因此 BM25、向量检索和混合检索更关注“不要漏掉可能相关的内容”。它们往往能找回主题相近的文本，却未必能准确判断哪一段最直接回答问题。

例如，用户询问“如何关闭接口限流”，初召回可能同时返回限流原理、默认阈值、配置文件说明和真正的关闭步骤。Reranker 的目标是把最后一类内容排到前面。

可以将职责区分为：

| 阶段 | 主要目标 | 典型问题 |
| --- | --- | --- |
| 初召回 | 覆盖可能相关的证据 | 正确内容是否在候选集中 |
| 重排 | 让最有用的证据位于前列 | 哪些内容最直接回答问题 |
| 上下文构造 | 去重、压缩并控制 token | 最终给模型哪些证据 |

Reranker 的前提是正确证据已经进入候选集；若答案没有被召回，应优先检查数据、分块、召回深度和检索策略。

## 二、常见重排器类型

### 2.1 Cross-Encoder

Cross-Encoder 将 `query` 和 `chunk` 一起输入模型，直接输出二者的相关性分数。因为模型可以看到两者之间的完整交互，它通常比单纯的向量相似度更擅长判断细粒度问答匹配。

![](https://storage.ghost.io/c/3f/df/3fdf6ed2-17ac-4b12-a693-8078bd13e748/content/images/2025/01/Screen-Recording-2025-01-01-at-4.07.23-PM.gif)

- 优点：精度高，适合区分“同主题”和“真正回答”。
- 缺点：每个 query-chunk 对都要单独推理，成本和延迟较高。
- 适用：对初召回的 Top-K 候选做二阶段精排。

### 2.2 Late Interaction / ColBERT 类方法

这类方法保留 query 和文档的 token 级表示，在匹配阶段进行更细粒度的交互。它通常在效果与效率之间提供折中：精度往往强于双塔向量检索，推理成本又可能低于完整 Cross-Encoder。

![](https://storage.ghost.io/c/3f/df/3fdf6ed2-17ac-4b12-a693-8078bd13e748/content/images/2025/01/Screen-Recording-2025-01-01-at-3.44.35-PM.gif)

- 优点：细粒度匹配能力较强，适合大一些的候选规模。
- 缺点：索引、存储和系统实现更复杂。

### 2.3 LLM 重排

LLM 可以根据问题对候选片段进行选择、打分或排序，并可结合时间、权威性、答案完整性等任务规则。

- 优点：对复杂约束和推理型问题更灵活。
- 缺点：成本高、延迟高，输出稳定性需要额外控制。
- 适用：低吞吐、高价值或需要复杂判断的场景。

### 2.4 规则与元数据重排

专用模型之外，工程中常叠加轻量规则，例如：优先最新版本、权威来源优先、标题精确命中加分、已废弃文档降权、同一文档的近似段落去重。

规则不能替代语义重排，但对版本治理、权限边界和业务确定性要求很实用。

## 三、如何接入 Reranker

### 3.1 候选规模

常见做法是先从多路召回中得到相对较大的候选集，再精排并只保留少量 Top-N：

`向量 Top-30 + BM25 Top-30 → 去重 → Rerank Top-40 → 保留 Top-5`

具体数字应根据评测集、延迟和上下文预算调整。候选太少会限制重排上限；候选太多会显著增加成本，并把噪声带入精排阶段。

### 3.2 输入内容

传给重排器的 chunk 应尽量自包含。通常可以包含标题、章节路径和正文；对表格、代码或 FAQ，需要在解析阶段保留足以理解的上下文。若 chunk 只有一句孤立文本，重排器也难以稳定判断其价值。

### 3.3 输出后的处理

Reranker 输出不是最终 prompt。精排后仍建议：

1. 按 chunk 或父文档去重，避免重复证据占满上下文；
2. 保留来源、标题和链接，便于回答时引用；
3. 对长内容做压缩或抽取，但不要删除回答所需的条件和限制；
4. 对多部分问题保留覆盖不同子问题的证据，而不是只保留高度相似的片段。

## 四、效果、延迟与成本的权衡

Reranker 通常改善的是 Top-3、Top-5 等最终可用位置的质量，而不是替代召回。它的成本近似随候选数增长：候选越多，需要评分的 query-chunk 对越多。

常见控制手段：

- 在 rerank 前先做权限、时间和文档类型过滤；
- 通过 BM25 与向量融合提高候选质量，而不是无限扩大 Top-K；
- 为低价值或简单 query 使用轻量模型或跳过深度重排；
- 记录 P50、P95 延迟和每次查询的候选数，避免只看离线指标。

## 五、如何评估

评估重排时，要同时看候选集与最终排序。

| 指标 | 说明 |
| --- | --- |
| Recall@K | 正确证据是否已进入初召回候选集 |
| MRR | 第一个正确结果是否排得更靠前 |
| nDCG@K | 多个不同相关度的证据是否被合理排序 |
| Top-N 命中率 | 最终进入上下文的 N 个片段是否包含正确证据 |
| 端到端答案质量 | 最终回答是否正确、忠实且引用准确 |
| P95 延迟与成本 | 精排是否符合线上服务预算 |

应使用真实查询构造评测集，并包含表达相近但答案不同、版本混淆、精确术语、多跳问题和无答案查询。只看排序分数提升，不能保证最终答案一定更好。

## 六、常见问题与排查

### 6.1 重排后仍没有正确答案

先检查正确 chunk 是否在初召回候选中。若不在，问题属于召回：检查入库、分块、Embedding、Top-K、ANN 参数和混合检索，而不是继续调 Reranker。

### 6.2 正确内容在候选中，却没有排到前面

检查 chunk 是否缺少标题或前置条件；确认 query 与 chunk 的输入模板符合模型要求；再用标注数据比较不同 reranker 的 MRR、nDCG 和 Top-N 命中率。

### 6.3 重排更准，但最终答案没有改善

可能是上下文拼接阶段丢失关键信息、重复内容稀释了证据，或生成提示没有要求模型依据检索内容回答。应从“重排结果 → 最终上下文 → 模型回答”逐段检查。

### 6.4 成本或延迟过高

降低进入 rerank 的候选数，先做元数据过滤和去重，选用更轻量的模型，或按 query 类型有条件启用精排。不要在未评测的情况下直接牺牲召回深度。
