# 大模型生产成本

大模型生产成本不是单一的“模型单价”问题，而是由以下因素共同决定：

* 请求量
* 输入 Token
* 输出 Token
* Context 长度
* 模型选择
* Prompt Cache 命中率
* Agent / Tool 调用次数
* RAG / Rerank 调用
* 重试与失败
* 实时与 Batch 调用模式
* 模型路由策略
* 任务成功率与人工返工率

因此，成本治理的目标不是简单降低 Token 或选择最低单价模型，而是在满足 **业务质量、SLA 和可靠性** 的前提下，持续降低：

> **Cost per Successful Task：每个成功完成业务任务的实际成本。**

# 1 核心原则

成本治理遵循以下原则：

1. **先度量，再优化**
2. **先归因，再治理**
3. **成本优化不能以牺牲业务质量为代价**
4. **优先优化高成本、高频、高收益场景**
5. **模型选择遵循质量、时延、成本三维平衡**
6. **Agent 必须限制最大调用次数和最大任务成本**
7. **实时任务与异步任务进行差异化治理**
8. **成本数据必须与请求 Trace 关联**
9. **所有模型、Prompt、路由和价格变化必须可追溯**
10. **成本优化必须支持灰度、评测和回滚**

# 2 成本治理总体架构

大模型成本治理可以划分为三个层次：

```text
                         大模型成本治理
                              │
            ┌─────────────────┼─────────────────┐
            ↓                 ↓                 ↓
          成本度量           成本控制           成本优化
            │                 │                 │
```

# 3 成本模型

## 3.1 单次调用成本

一次模型调用的近似成本：

```text
调用成本
=
输入 Token × 输入单价
+
输出 Token × 输出单价
+
缓存 Token × 对应价格
+
推理 Token × 对应价格
+
失败与重试成本
```

对于 Agent 场景：

```text
Task Cost
=
Σ LLM Call Cost
+
Σ Tool / Search / Rerank Cost
+
Σ Embedding Cost
+
Σ Retry Cost
+
Σ Upgrade / Fallback Cost
```

因此：

> **不能使用单次 LLM Call 成本代表一个 Agent Task 的真实成本。**

---

## 3.2 有效任务成本

核心指标：

```text
Cost per Successful Task
=
Total Cost / Successful Task Count
```

例如：

```text
方案 A：

10000 个任务
总成本：¥1000
成功任务：9500

Cost per Successful Task
= 1000 / 9500
= ¥0.105
```

方案 B：

```text
10000 个任务
总成本：¥800
成功任务：7000

Cost per Successful Task
= 800 / 7000
= ¥0.114
```

虽然方案 B 总成本更低，但单个有效任务成本更高。

因此：

> **不能只看总成本，也不能只看单次模型调用价格。**

# 5 成本归因体系

成本治理的第一步不是优化，而是回答：

> **钱到底花在哪里？**

## 5.1 Cost Trace

每个业务任务建立唯一：

```text
task_id
trace_id
```

所有下游调用关联到该 Trace。

例如：

```text
Task: task_123

Total Cost: ¥0.38

├── Planner LLM       ¥0.08
├── RAG Retrieval     ¥0.01
├── Reranker           ¥0.02
├── Tool Call          ¥0.02
├── Executor LLM       ¥0.12
├── Retry              ¥0.06
└── Final LLM          ¥0.07
```

这样可以准确定位成本来源。

# 6 Context 成本治理

Context 是当前大模型生产系统非常重要的成本来源。

一个请求的 Context 通常包括：

```text
System Prompt
+
Tool Schema
+
Conversation History
+
Memory
+
RAG Context
+
User Input
+
Agent Intermediate Results
```

如果这些内容持续增长，会产生：

```text
Context 膨胀
    ↓
Input Token 增加
    ↓
模型成本增加
    ↓
时延增加
    ↓
Agent 后续每一轮成本继续增加
```

---

## 6.1 Context Token 拆解

建议分别统计：

| 类型                | 说明        |
| ----------------- | --------- |
| System Token      | 系统 Prompt |
| Tool Schema Token | 工具定义      |
| History Token     | 历史对话      |
| Memory Token      | 长期记忆      |
| RAG Context Token | 检索召回与重排结果  |
| Tool Result Token | 工具、搜索、代码执行返回内容 |
| User Input Token  | 用户本轮输入     |
| Reasoning Token   | 推理模型思考过程，通常按输出计费 |
| Multimodal Token  | 图片、音频、视频折算的 Token |

只有按段统计，才能回答“膨胀来自哪一部分”，也才能判断应该裁剪历史、压缩检索结果，还是精简工具定义。

---

## 6.2 Agent 场景的累积成本

Agent 每一轮都会把历史重新发送一次，因此输入成本不是线性叠加：

```text
第 1 轮输入：System + Tools + User
第 2 轮输入：System + Tools + User + 第 1 轮输出 + 工具结果
第 3 轮输入：System + Tools + User + 前两轮输出 + 工具结果
...
```

近似估算：

```text
Agent 累计输入 Token
≈
轮数 × 基础上下文
+
轮数 × (轮数 − 1) / 2 × 每轮新增内容
```

因此有两个同等重要的优化方向：

* 减少轮数：更完整的规划、批量工具调用、把确定性逻辑写成代码
* 压缩每轮新增内容：工具结果截断、结构化提取、中间产物外置

Prompt Cache 能显著缓解“基础上下文重复付费”，但无法消除“每轮新增内容”的累积。

---

## 6.3 Context 治理手段

| 手段 | 适用对象 | 注意点 |
| --- | --- | --- |
| 滚动窗口与裁剪 | 历史对话 | 保留关键决策与约束，避免裁掉前置条件 |
| 会话摘要 | 长会话 | 摘要放在稳定前缀，并设置刷新策略 |
| 检索结果压缩与 top-k 控制 | RAG | 先重排再截断，合并去重相似片段 |
| 工具结果截断与结构化提取 | Tool / MCP / 搜索 | 不要把整页 HTML 或整个 JSON 塞进上下文 |
| 工具与 Skill 按需加载 | Tool Schema | 工具过多时分组暴露，减少常驻 schema |
| 渐进式披露 | 长文档 | 先给目录或摘要，再按需取全文 |
| 记忆外置 | 长期记忆 | 写入外部存储，按相关性检索而非全量拼接 |
| 输出约束 | 生成内容 | 限制最大输出、要求结构化字段、禁止复述上下文 |

具体压缩方式见 [2 上下文压缩.md](../0%20LLM/4%20上下文工程/2%20上下文压缩.md)。

---

## 6.4 长上下文的隐性代价

即使单价不变，上下文变长还会带来：

* Prefill 计算量与 KV Cache 占用上升，时延和排队随之上升
* 部分供应商对超长上下文采用阶梯定价，单位 Token 反而更贵
* 有效注意力被稀释，质量下降，重试与人工返工上升
* 前缀任一位置变化，都会导致其后内容全部缓存未命中

因此应像设置 Token 预算一样，为每个场景显式设置 **上下文预算**，并对超预算请求告警。

# 7 Prompt Cache 成本治理

## 7.1 缓存的计费结构

Prompt Cache 通常把输入 Token 分成三类计价：

| Token 类型 | 说明 | 相对价格 |
| --- | --- | --- |
| 未命中输入 | 正常计费的输入 Token | 基准 |
| 缓存写入 | 首次建立缓存的 Token | 高于基准 |
| 缓存命中 | 复用已缓存前缀的 Token | 显著低于基准 |

缓存一般有存活时间（TTL），过期后重建需要再次支付写入费用；部分平台提供延长 TTL 的选项，但写入溢价更高。

单个前缀的净收益：

```text
节省
=
命中 Token × (未命中单价 − 命中单价)
−
写入 Token × (写入单价 − 未命中单价)
```

因此：

> **缓存只有在前缀被复用足够多次时才省钱。低频、过短、频繁变化的内容做缓存反而更贵。**

## 7.2 稳定前缀设计

把请求拆成稳定前缀和易变后缀：

```text
[系统提示词 | 工具定义 | 固定策略 | 已确认的长上下文]  ← 稳定、可缓存
[用户问题 | 本轮参数 | 最新检索结果 | 个性化数据]        ← 易变、不可缓存
```

设计原则：

* 顺序固定：缓存按前缀匹配，工具顺序、空格、字段序列化顺序变化都会导致未命中
* 稳定内容前置：系统提示词、工具 schema、长期有效的知识与示例放在用户变量之前
* 控制粒度：只为足够长且高频复用的前缀建缓存
* 版本隔离：Prompt、模型、工具定义、知识库或权限变更时用版本号隔离缓存
* 安全域隔离：不同租户、用户权限、地域、数据密级不可共享前缀，缓存键必须包含这些维度
* 不要把实时检索结果、隐私数据、时间戳、随机 ID 放进稳定前缀

会话历史不断增长时，可保留固定的会话摘要作为前缀，把近期对话放在后缀，并为摘要设置刷新策略。

缓存原理与写法细节见 [3 prompt cache.md](../0%20LLM/2%20提示词Prompt/3%20prompt%20cache.md)。

## 7.3 常见失效原因

| 现象 | 可能原因 |
| --- | --- |
| 命中率骤降 | Prompt 改版、工具定义或顺序变化、模型切换 |
| 命中率一直很低 | 时间戳 / 请求 ID 注入前缀、JSON 字段顺序不稳定 |
| 写入费用高但收益低 | 为低频前缀建缓存、TTL 过短导致反复重建 |
| 会话越长命中越低 | 历史被放进前缀，每轮前缀都在变化 |
| 租户之间命中率差异大 | 缓存键未包含隔离维度，或前缀被个性化内容污染 |

## 7.4 缓存相关指标

* Cache Hit Rate：命中请求占比
* Cached Token Ratio：命中 Token / 总输入 Token，更接近真实节省
* Cache Write Token：写入量与写入费用
* Cache Rebuild Rate：TTL 过期重建比例
* 按 prompt_version、model、app 分组的命中率对比

# 8 模型路由成本治理

## 8.1 分层路由

路由的核心是用可解释、可回退的规则，在质量、时延和成本之间做分层选择。

| 条件 | 路由建议 | 护栏 |
| --- | --- | --- |
| 固定格式抽取、分类、改写、简短问答 | 小模型或专用模型 | JSON 校验、置信度阈值 |
| 常规知识问答、单工具调用、摘要 | 中等能力模型 | 抽样质量评估与回归集 |
| 复杂推理、多步骤规划、代码审查、关键决策 | 强模型 | 人工复核或高质量评测集 |
| 输入超长 | 支持长上下文且单位 Token 更优的模型 | 先压缩、检索、缓存，再扩容上下文 |
| 高价值或低容错任务 | 强模型或双阶段处理 | 记录升级原因与结果 |
| 低置信度、工具失败、格式校验失败 | 升级模型或进入修复链路 | 限制升级次数，防止循环重试 |

## 8.2 级联与升级

先用确定性规则过滤，再对边界请求用轻量分类器或小模型评估难度：

```text
小模型执行
    ↓
格式 / 规则 / 置信度 / 评审模型校验
    ↓
通过 → 返回        未通过 → 升级（最多 N 次）
```

要点：

* 升级次数必须有上限，并记录每次升级的原因
* 校验环节必须比生成便宜，否则级联反而更贵
* 路由规则要与 Prompt 版本绑定：同一个 Prompt 在不同模型上的表现差异很大

## 8.3 路由决策记录

至少记录：候选模型、最终模型、命中的规则、预测难度、质量校验结果、是否升级、升级原因、本次成本。

只有保留这些字段，才能发现“便宜模型返工更多”或“强模型被用于简单任务”这类问题。

## 8.4 路由效果验证

用离线评测集加线上抽样，比较：任务成功率、人工返工率、P95 时延、Cost per Successful Task。

> **只看单价下降、不看成功率变化的路由调整，通常是负收益。**

## 8.5 常见反模式

* 默认所有请求都走最强模型
* 没有质量护栏的盲目降级
* 模型名硬编码在业务代码里，无法灰度与回滚
* 路由策略与 Prompt 版本脱钩
* 只比较 Token 单价，不比较每任务的调用次数

# 9 输出与推理 Token 治理

## 9.1 输出通常比输入更贵

多数供应商的输出单价高于输入单价，因此控制输出的收益常常大于压缩输入。

手段：

* 设置与任务匹配的 `max_tokens`，而不是统一给最大值
* 要求结构化输出，只返回必要字段，不要附加解释
* 明确禁止复述上下文或大段引用原文
* 约束礼貌性开场白、过程说明和自我总结
* 超长内容拆分生成，避免一次性生成后整段废弃

## 9.2 推理 Token

推理模型的思考过程通常按输出 Token 计费，却不直接产生业务价值，是最容易被忽视的成本项。

* 按任务难度设置思考预算 / effort 等级，简单任务用低档
* 不要为了“保险”全局开到最高思考强度
* 思考被截断同样已经付费：宁可降低预算，也不要生成到上限被切断
* 思考 Token 占比应单独统计和告警

## 9.3 流式与取消

* 用户中断、页面关闭、上游超时时必须主动取消请求，否则仍会为已生成的 Token 付费
* 在网关侧统计“客户端已断开但生成仍在继续”的比例
* 流式返回可以更早暴露问题，配合提前终止减少无效生成

## 9.4 输出侧指标

| 指标 | 含义 |
| --- | --- |
| 输出 / 输入 Token 比 | 输出失控的信号 |
| 每任务输出 Token P95 | 生成长度分布 |
| Reasoning Token 占比 | 思考成本占比 |
| 截断比例 | 达到 max_tokens 被切断的请求占比 |
| 无效输出比例 | 未通过格式或质量校验的输出 |

# 10 Agent 成本治理

## 10.1 Agent 成本的特征

与单次调用相比，Agent 任务的成本具有：

* 轮数不确定，成本方差大，难以用单价预估
* 上下文逐轮累积，越靠后的每一轮越贵
* 工具、搜索、MCP 与外部服务独立计费，容易被漏统计
* 子 Agent 并行执行时，成本是加和而不是取最大值
* 失败重试与自我修复会成倍放大消耗

因此：

> **不能用单次 LLM Call 的成本代表一个 Agent Task 的真实成本。**

## 10.2 必须设置的硬边界

| 边界 | 说明 |
| --- | --- |
| 最大迭代次数 | Agent Loop 的轮数上限 |
| 单任务最大 Token | 输入 + 输出总量上限 |
| 单任务最大成本 | 超过即中止、降级或转人工 |
| 单轮最大工具调用数 | 防止一次并发大量付费调用 |
| 最大升级次数 | 防止级联循环 |
| 最大并行子 Agent 数 | 控制并发成本 |
| 任务墙钟超时 | 防止长时间空转 |
| 单工具超时与重试上限 | 防止重试风暴 |

边界应可按场景配置，并在成本事件中记录“是否触发边界”和“触发原因”。

## 10.3 失控检测

出现以下信号时应立即暂停、降级或转人工：

* 轮数或成本斜率明显高于同类任务基线
* 连续多轮调用相似工具、参数几乎相同
* 上下文持续增长但任务状态没有进展
* 同一错误反复重试
* 输出反复未通过校验

Agent Loop 的典型失控方式见 [2 Agent Loop.md](../1%20Agent/3%20运行时/2%20Agent%20Loop.md)。

## 10.4 工具与外部服务计费

以下调用都要计入 Task Cost，并挂到同一个 trace：

* Web 搜索、代码执行、文件检索等内置工具，通常按次计费
* MCP 与第三方 API，可能有独立配额与费用
* Embedding、Rerank、OCR / ASR / TTS
* 向量库、对象存储等外部读写

> **只统计 LLM Token 的 Agent 成本报表，通常会低估真实成本。**

## 10.5 Agent 降本手段

* 能写成代码的确定性逻辑，不要交给模型推理
* 用 Workflow 固定流程，只在真正需要决策的节点使用开放式 Loop
* 一次规划、批量执行工具调用，减少轮数
* 工具结果先摘要再入上下文，中间产物写入外部存储
* 工具与 Skill 按需加载，避免全量 schema 常驻上下文
* 高频稳定的子任务蒸馏成小模型或专用服务
* 为探索型子 Agent 单独设预算，并把结果汇总回父任务成本

# 11 调用模式：实时与 Batch

## 11.1 模式选择

Batch 通常以更低单价和更高吞吐换取更长等待时间。

| 场景 | 优先模式 | 设计要点 |
| --- | --- | --- |
| 历史数据标注、离线摘要、审核回填、报表生成 | Batch | 聚合请求、可重放、记录幂等键 |
| 夜间知识库清洗、嵌入生成、质量评测 | Batch | 分片、失败重试、设置完成时限 |
| 聊天、交互式 Copilot、在线客服 | Real-time | 控制 TTFT，设置超时与降级 |
| 提交后数分钟内可见的结果 | 异步队列 + Batch | 先返回任务状态，完成后通知或拉取 |

判断方式：先定义业务的“结果最晚可用时间”。如果不要求同步返回，就不应该默认走实时接口。

## 11.2 Batch 的工程要点

* 幂等键：重跑不产生重复的业务副作用，也不重复计费
* 分片与限流：避免一次提交压垮配额
* 失败补偿：区分可重试与不可重试失败，只重跑失败分片
* 完成时限：超时后降级或转实时链路
* 去重：相同输入复用已有结果，避免重复跑批导致成本翻倍
* 可观测：任务级成本、失败率、平均等待时间

## 11.3 实时侧的降本手段

* 把评审、打标、长摘要、日志归档等非关键后处理移到异步链路
* 流式返回，尽早让用户看到结果，减少无效长输出
* 用优先级队列和配额隔离交互流量与后台流量
* 高峰期可临时降级模型规格或缩短上下文，但必须记录降级事件并评估质量影响

# 12 隐性成本与常见反模式

| 隐性成本 | 表现 | 治理方式 |
| --- | --- | --- |
| 失败任务成本 | 已付费但没有业务产出 | 统计失败率与失败成本，优先修可修复失败 |
| 重试风暴 | 超时、限流触发多层重试 | 统一重试入口、退避加抖动、限制总次数 |
| 人工返工 | 低质量结果需要人工修正 | 计入 Cost per Successful Task |
| 评测与回归 | 评测集、A/B、影子流量本身要花钱 | 预算化，抽样而非全量 |
| 数据侧重算 | Embedding 重建、知识库全量重刷 | 增量更新、版本化、变更前后对比 |
| 可观测存储 | 全量 Prompt 与输出落盘 | 采样、脱敏、生命周期管理 |
| 长上下文滥用 | 习惯性拼接全部历史与检索结果 | 设置上下文预算与告警 |
| 缓存写入浪费 | 为低频前缀建缓存 | 按最少复用次数评估收益 |
| 非生产环境消耗 | 开发、测试直接打真实大模型 | 使用小模型、mock、录制回放 |
| 无预算的自动化 | 定时任务、批量抓取加 LLM 处理 | 任务级预算与熔断 |
| 调价与口径变化 | 供应商调价、阶梯折扣、汇率波动 | 价格表版本化，保留原始用量 |

其中最容易被低估的是 **多层重试**：业务层、SDK 层、网关层各自重试 3 次，最坏情况下一个请求会变成 27 次调用。重试策略必须在一个统一层面收口，并把上游已重试的次数透传给下游。

成本日志与可观测数据本身也要治理：全量落盘 Prompt 和输出既增加存储成本，也带来合规与隐私风险，采样与脱敏规则见 [3 安全和沙箱.md](./3%20安全和沙箱.md)。

# 13 自建推理与 API 成本

## 13.1 什么时候考虑自建

适合自建的信号：

* 流量稳定且规模大，API 账单已明显高于自建 TCO
* 有数据合规、私有化部署或数据驻留要求
* 需要使用开源模型、定制微调模型或特定量化版本
* 需要自己控制吞吐、调度与优先级，例如多租户平台

反之，流量波动大、模型迭代快、团队缺少推理运维能力时，直接用 API 通常更划算。

## 13.2 自建 TCO 的构成

```text
自建成本
=
GPU（租赁或折旧）
+ 电力 / 机房 / 网络
+ 推理框架与调度运维人力
+ 监控、告警与值班
+ 冗余与容灾（多可用区、备用容量）
+ 模型获取、微调与评测投入
+ 存储（权重、日志、向量库）
```

只对比“GPU 单价 × 卡数”和“API 单价”是最常见的错误，人力与冗余往往占相当比例。

## 13.3 单位成本换算

```text
每百万 Token 成本
=
（单卡小时成本 × 卡数）
/
（每小时有效产出 Token / 1000000）
```

其中“每小时有效产出 Token”取决于并发、批处理效果、输入输出长度比、是否命中 Prefix Cache，必须用真实流量画像压测得到，不能用单次请求的 tokens/s 外推。指标口径见 [9 推理性能指标与Benchmark.md](../0%20LLM/5%20推理工程/9%20推理性能指标与Benchmark.md)。

## 13.4 利用率决定自建成本

* 按峰值备容量，低谷就会大量闲置
* 常见做法：基线容量自建 + 峰值溢出到 API；用离线批任务填谷；多租户共享资源池并做配额与优先级隔离
* 需要持续监控：GPU 利用率、显存占用、KV Cache 命中率、排队时间、每百万 Token 的实际成本

## 13.5 降低单 Token 成本的推理侧手段

| 手段 | 作用 |
| --- | --- |
| Continuous Batching | 提升吞吐，摊薄单 Token 成本 |
| Prefill / Decode 分离 | 避免长请求压住解码，提升整体利用率 |
| Prefix Cache | 复用相同前缀的 KV，减少重复预填充 |
| 量化（FP8 / INT4 等） | 降低显存与带宽压力，提高单机并发 |
| 投机解码 | 降低解码延迟，提高单卡吞吐 |
| Chunked Prefill | 平滑长上下文请求对队列的冲击 |
| 更小模型 / 蒸馏 | 从根本上降低单 Token 计算量 |

调度与缓存机制见 [3 Continuous Batching与调度.md](../0%20LLM/5%20推理工程/3%20Continuous%20Batching与调度.md)、[2 KV Cache与PagedAttention.md](../0%20LLM/5%20推理工程/2%20KV%20Cache与PagedAttention.md)；具体框架见 [2 vLLM.md](../5%20开源生态/9%20推理框架/2%20vLLM.md)。

## 13.6 决策清单

* 当前月 Token 量、增长曲线、峰值与均值比
* 质量能否用开源或更小模型满足，需要评测集验证
* 合规与数据驻留要求
* 是否具备推理运维、压测与容量规划能力
* break-even 测算：API 月账单 vs 自建 TCO（含人力与冗余）
* 常见路径：API 起步 → 流量稳定后混合部署 → 高频固定场景自建或蒸馏专用模型

微调与蒸馏的适用场景见 [7 微调.md](../0%20LLM/1%20大模型原理/7%20微调.md)。

## 13.7 供应商与商务侧的杠杆

除了工程优化，采购与供应商策略同样影响成本：

* 承诺用量折扣与阶梯价：适合流量可预测的业务，但要评估达不到承诺量的沉没成本
* 预留吞吐 / 优先级层：为高峰买确定性，代价是低谷闲置，需要用峰值均值比来判断
* 多供应商比价：同一质量档位在不同供应商之间价差可能很大，前提是评测口径统一
* 托管的开源模型：介于 API 与完全自建之间，省去运维但保留模型可替换性
* 模型下线风险：供应商停服会强制迁移，成本看板应跟踪各模型的生命周期状态
* 避免锁定：通过统一网关抽象供应商差异，保留随时切换的能力，例如 [1 OneApi.md](../5%20开源生态/8%20OneAPI/1%20OneApi.md)

# 14 成本监控、预算与控制

## 14.1 采集与计价

在统一网关或 SDK 包装层采集每次调用的结构化事件（字段见 5.2）。计价要点：

* 使用可版本化的价格表，保留原始 Token 用量与价格版本，确保调价后历史报表仍可复算
* 统一多供应商口径：Token 计数方式、缓存写入与命中计价、多模态折算、最小计费单位都不同
* 实时估算加账单周期对账，偏差超过阈值时告警并修正价格表
* 对用户内容只记录必要的脱敏标签或哈希，不把完整 Prompt 写入成本日志

## 14.2 看板

建议至少建设四类看板：

1. 全局：总费用、日 / 周趋势、预算消耗率、按模型的成本占比
2. 业务：每个应用、租户、任务类型的 Cost per Successful Task 与成功率
3. 效率：输入输出 Token 分布、缓存命中、路由分布、Batch 占比、重试成本
4. 异常：费用突增、单请求 Token 异常、路由漂移、缓存命中骤降、失败重试上升

## 14.3 告警

以“相对基线 + 绝对阈值”组合触发，例如：

* 某应用小时费用超过预算比例，且高于过去七天同期基线
* 单请求输入 Token 超过该场景的 P99
* 缓存命中率相对基线下降超过阈值
* 某个模型的路由占比突变
* 重试率或失败成本持续上升

告警后的排查顺序：新增或改版的 Prompt → 上下文膨胀 → 循环工具调用 → 重试风暴 → 路由配置变更 → 缓存失效 → 供应商调价。

## 14.4 控制措施

| 措施 | 说明 |
| --- | --- |
| 预算 | 团队、应用、租户的日月预算，达到阈值时预警、限流或转更经济的模型 |
| 配额 | 单请求上下文长度、最大输出 Token、工具调用轮数、重试次数 |
| 熔断 | 费用或错误率异常时关闭高成本功能、降级为检索或摘要、暂停非关键异步任务 |
| 门禁 | 新 Prompt、新模型、新路由上线前评估成本影响，灰度期设置成本上限 |
| 审计 | 单价、模型、路由、Prompt 版本变更全部可追溯 |

熔断与降级的实现方式见 [5 韧性.md](./5%20韧性.md)。

## 14.5 分摊与单位经济学

* Showback：把成本按应用与租户可视化，让使用方看到自己的消耗
* Chargeback：内部结算或对外计费，需要稳定且可解释的分摊口径
* 对外定价时，除模型成本还要计入重试、评测、存储、人工与失败率，并预留毛利
* 关注单位经济学指标：每工单成本、每会话成本、每成功任务成本、毛利率

# 15 优化闭环与检查清单

## 15.1 优化闭环

1. 选择一个高成本场景，建立成功率、时延与 Cost per Successful Task 基线
2. 归因：成本来自输入、输出、推理、重试、模型规格、工具调用还是实时模式
3. 依次尝试：上下文裁剪与缓存 → 路由分级 → 输出与思考约束 → Batch 迁移 → 模型替换或自建 → 微调蒸馏
4. 在固定评测集与线上灰度中同时验证质量、时延与成本，避免只看 Token 降幅
5. 固化有效规则，记录收益、适用范围与回滚条件，并持续监控回归

## 15.2 优化优先级

| 优先级 | 手段 | 特点 |
| --- | --- | --- |
| 高 | 上下文裁剪、Prompt Cache、输出约束 | 改动小、见效快、质量风险低 |
| 中高 | 路由分级与级联 | 需要评测集护栏 |
| 中 | Batch 迁移 | 需要业务能容忍延迟 |
| 中 | 减少 Agent 轮数、压缩工具结果 | 需要流程改造 |
| 低 | 模型替换、自建推理 | 收益大但周期长、风险高 |
| 低 | 微调与蒸馏 | 需要数据与训练投入，适合高频稳定场景 |

## 15.3 上线检查清单

* 是否为关键场景定义了成本 SLO 与预算
* LLM、工具、Embedding、Rerank、MCP 调用是否都进入统一 trace 与计价
* 是否设置了最大迭代、最大 Token、最大成本、超时与重试上限
* 是否有缓存命中率、路由分布、重试率、截断率的看板与告警
* 是否验证了降级、熔断、取消请求后的成本与用户体验
* 变更是否可灰度、可回滚，并记录了预期收益
* 最终判据是否为 Cost per Successful Task，而不是总成本或单次单价

## 15.4 与其他生产主题的关系

* 延迟：上下文与输出优化通常同时改善时延，见 [2 延迟.md](./2%20延迟.md)
* 安全：成本日志不能落盘完整 Prompt 与用户隐私，见 [3 安全和沙箱.md](./3%20安全和沙箱.md)
* 监控：成本指标应与质量、Drift 指标同源，见 [4 监控与drift.md](./4%20监控与drift.md)
* 韧性：降级与熔断既是可用性手段，也是成本护栏，见 [5 韧性.md](./5%20韧性.md)

---

成本优化最终服务于业务结果：当更强的模型显著提升转化、成功率或人工效率时，更高的调用成本是合理投入；反之，即使单价很低，低质量带来的重试与人工返工也会放大总成本。
