# 大模型生产成本治理

大模型成本不是单一的“单价”问题，而是由请求量、输入/输出 Token、模型选择、缓存命中率、时延目标和重试行为共同决定。成本治理的目标是在满足质量与 SLA 的前提下，持续降低每次有效任务的成本，而非简单压缩 Token。

## 成本拆解与度量口径

一次调用的近似成本为：

`调用成本 = 输入 Token × 输入单价 + 输出 Token × 输出单价 + 缓存读写 Token × 对应单价 + 失败与重试成本`

业务侧应同时关注以下口径：

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| 总成本 | 按模型、租户、应用、场景汇总的费用 | 预算与资源分配 |
| 单次有效任务成本 | 总费用 / 成功完成的业务任务数 | 避免只压低单请求成本而牺牲成功率 |
| 每千次任务成本 | 标准化后的场景成本 | 横向比较不同版本或方案 |
| 输入/输出 Token 比 | 提示词膨胀和输出失控的信号 | 优化上下文与生成上限 |
| 缓存命中率 | 可复用前缀请求的命中比例 | 评估 Prompt Cache 价值 |
| 路由分布 | 各模型承接请求的比例与成本 | 校验模型路由是否按预期生效 |
| 重试率与失败成本 | 超时、限流、格式错误导致的额外消耗 | 定位隐性成本 |

指标应以“模型、应用、接口、租户、环境、版本、任务类型”作为维度，并保留请求时间、Token 用量、时延、结果状态和路由决策原因。对用户内容只记录必要的脱敏标签或哈希，不把完整 Prompt 写入成本日志。

## Prompt Cache：围绕稳定前缀设计边界

Prompt Cache 适合复用相同或高度相似的长上下文，例如系统指令、工具定义、固定知识包、长文档模板和多轮会话的历史前缀。其收益取决于“可复用 Token 数量 × 命中率 × 缓存与常规输入的价差”。

### 缓存边界

将请求拆成稳定前缀和易变后缀：

```text
[系统提示词 | 工具定义 | 固定策略 | 已确认的长上下文]  ← 稳定、可缓存
[用户问题 | 本轮参数 | 最新检索结果 | 个性化数据]          ← 易变、不可缓存
```

设计时遵循以下原则：

- 把顺序固定：缓存通常按前缀匹配；即使内容相同，工具顺序、空格、序列化格式变化也可能导致未命中。
- 把稳定内容前置：系统提示词、工具 schema、长期有效的知识和示例应在用户变量之前。
- 控制缓存粒度：仅为有足够长度且复用频繁的前缀建立缓存；短 Prompt 或低频任务通常不值得为命中率增加复杂度。
- 明确失效边界：策略、模型版本、工具定义、知识库版本或权限发生变化时，使用版本号隔离缓存，避免旧规则或越权内容复用。
- 隔离安全域：不同租户、用户权限、地域或数据密级不可共享缓存前缀；缓存键必须包含这些隔离维度。
- 观察有效命中：区分“缓存命中率”和“命中的 Token 占输入 Token 的比例”，后者更接近实际节省。

不要为了缓存而把实时检索结果、用户隐私数据或频繁变化的业务状态放进稳定前缀。若会话历史不断增长，可保留固定的会话摘要作为前缀，将近期对话放在后缀，并设置摘要刷新策略。

## Model Routing：让合适的模型处理合适的任务

模型路由的核心是用可解释、可回退的规则，在质量、时延和成本之间做分层选择。不要只依赖“默认用最强模型”；也不要在没有质量护栏时盲目降级。

### 推荐的路由规则

先用确定性规则过滤，再对边界请求使用轻量分类器或小模型评估：

| 条件 | 路由建议 | 护栏 |
| --- | --- | --- |
| 固定格式抽取、分类、改写、简短问答 | 小模型或专用模型 | JSON 校验、置信度阈值 |
| 常规知识问答、单工具调用、摘要 | 中等能力模型 | 抽样质量评估与回归集 |
| 复杂推理、多步骤规划、代码审查、关键决策 | 强模型 | 人工复核或高质量评测集 |
| 输入超长 | 支持长上下文且单位 Token 更优的模型 | 优先压缩、检索和缓存，再扩容上下文 |
| 高价值或低容错任务 | 强模型或双阶段处理 | 记录升级原因与结果 |
| 低置信度、工具失败、格式校验失败 | 升级模型或进入修复链路 | 限制升级次数，防止循环重试 |

可采用“先廉价后升级”的级联：小模型先完成任务并通过格式、规则、置信度或评审模型校验；未通过时才升级。路由策略需要持续用离线评测集和线上抽样验证，比较成功率、人工返工率、P95 时延和单次有效任务成本。

路由决策至少记录：候选模型、最终模型、规则命中项、预测难度、质量校验结果、是否升级以及升级原因。这样才能发现“便宜模型返工更多”或“强模型被用于简单任务”等问题。

## Batch 与 Real-time：以时延预算换取单价

批处理通常以更低价格和更高吞吐换取更长等待时间，适合没有即时交互要求、可容忍延迟的任务；实时调用适合用户在环、需要秒级反馈的场景。

| 场景 | 优先模式 | 设计要点 |
| --- | --- | --- |
| 历史数据标注、离线摘要、内容审核回填、报表生成 | Batch | 聚合请求、可重放、记录任务幂等键 |
| 夜间知识库清洗、嵌入生成、质量评测 | Batch | 分片、失败重试、设置完成时限 |
| 聊天、交互式 Copilot、在线客服 | Real-time | 控制首 Token 时延，设置超时与降级 |
| 用户提交后数分钟内可见的结果 | 异步队列 + Batch | 先返回任务状态，完成后通知或拉取 |

判断方式是先定义业务的“结果最晚可用时间”。如果不要求同步返回，就不应默认走实时接口。对实时流量，可把非关键后处理（评审、标签、长摘要、日志归档）移至异步批任务；对批任务，需提供进度、失败补偿和重复提交去重，避免因重跑造成成本翻倍。

## Token 费用监控与预算控制

### 采集

在统一网关或 SDK 包装层采集每次调用的结构化事件：

- 请求标识、时间、应用/租户/用户匿名标识、环境和任务类型；
- 模型与版本、路由规则、缓存状态、调用模式（实时或批处理）；
- 输入、输出、推理和缓存相关 Token 用量，以及对应单价版本；
- 首 Token 时延、总时延、状态码、重试次数和最终业务结果。

费用计算应使用可版本化的价格表，并保留原始 Token 用量与价格版本，确保供应商调价后历史报表仍可复算。费用可按请求实时估算，按供应商账单周期再对账校准。

### 看板与告警

建议至少建设四类看板：

1. 全局：总费用、日/周趋势、预算消耗率、按模型的成本占比。
2. 业务：每个应用、租户和任务类型的单次有效任务成本与成功率。
3. 效率：输入/输出 Token 分布、缓存命中、路由分布、批处理占比、重试成本。
4. 异常：费用突增、单请求 Token 异常、模型路由漂移、缓存命中骤降、失败重试上升。

告警以“相对基线 + 绝对阈值”组合触发。例如，某应用小时费用超过预算比例且高于过去七天同期基线，或单请求输入 Token 突然超过该场景 P99。告警后优先定位新增 Prompt、上下文膨胀、循环工具调用、重试风暴、路由配置变更和缓存失效。

### 控制措施

- 预算：设置团队、应用和租户的日/月预算，达到阈值时预警、限流或转入更经济的模型。
- 配额：限制每次请求的上下文长度、最大输出 Token、工具调用轮数和重试次数。
- 熔断：当费用或错误率异常时，关闭高成本功能、降级为摘要/检索结果，或暂停非关键异步任务。
- 审计：所有单价、模型、路由和 Prompt 版本变更都应可追溯，并在上线前评估成本影响。

## 持续优化闭环

1. 选择一个高成本场景，建立成功率、时延和单次有效任务成本基线。
2. 分析成本来自输入、输出、重试、模型规格还是实时调用。
3. 依次尝试上下文裁剪与缓存、路由分级、批处理迁移和输出约束。
4. 在固定评测集与线上灰度中同时验证质量、时延和成本，避免只看 Token 降幅。
5. 固化有效规则，记录收益、适用范围和回滚条件，并持续监控回归。

成本优化应服务于业务结果：当更强模型显著提升转化、成功率或人工效率时，较高的调用成本可能是合理投入；反之，即使单价很低，低质量带来的重试和人工返工也会放大总体成本。
