# 《Are We Ready For An Agent-Native Memory System?》：Agent 记忆系统的系统性评测与设计准则

## 1. 论文信息

- 论文：[Are We Ready For An Agent-Native Memory System?](https://arxiv.org/abs/2606.24775)
- 作者：Wei Zhou、Xuanhe Zhou、Shaokun Han、Hongming Xu、Guoliang Li、Zhiyu Li、Feiyu Xiong、Fan Wu
- 发布：arXiv:2606.24775，2026 年 6 月
- 代码与评测数据：[OpenDataBox/MemoryData](https://github.com/OpenDataBox/MemoryData)

这篇论文不提出一个新的 Agent Memory 产品，而是追问一个更基础的问题：**今天的记忆系统，真的已经是面向智能体原生设计的基础设施了吗？**

作者的回答是：还没有。现有工作往往以任务最终得分（如 F1、BLEU）判断记忆是否有效，把存储、写入、检索、更新等过程看成不可拆的黑盒。这样会掩盖几个生产环境真正关心的问题：记忆能否找回原始证据、事实更新后会不会召回过期信息、长期运行是否退化，以及为结构化记忆付出的延迟是否值得。

论文据此把 Agent Memory 视作一个持续运行的数据管理系统，对 12 个代表性系统和两个基线，在 5 类负载、11 个数据集上做了统一评测，并进一步完成组件级消融。

## 2. Agent Memory 不等于 RAG 或上下文工程

论文中的 Agent Memory 指：**独立于模型参数和单次上下文窗口、持久保存智能体状态，并在未来推理与行动时可读写的数据管理对象。** 它可以保存多轮对话、工具执行轨迹、用户偏好、事实、计划与中间状态。

三个容易混淆的概念可以这样区分：

| 概念 | 核心职责 | 是否持续更新 |
| --- | --- | --- |
| RAG | 从通常静态的语料库中，为一次生成取回文本 | 通常否 |
| 上下文工程 | 在当前有限窗口中编排提示、工具说明与材料 | 针对当前推理轮次 |
| Agent Memory | 管理智能体跨轮次、跨会话、可演化的状态全生命周期 | 是 |

因此，Memory 不是“向量库 + 检索”这么简单。它必须处理相互冲突的新旧事实、容量约束、时间有效性、来源可追溯性，以及状态改变顺序。

## 3. 核心框架：记忆系统 = `<R, S, Q, U>`

论文将任一记忆系统形式化为 `M_sys = <R, S, Q, U>`。这个四段式框架也是理解全文最重要的线索。

| 模块 | 要回答的问题 | 典型方案 |
| --- | --- | --- |
| `R`：表示与存储 | 记忆长什么样、落在哪里？ | 文本/向量、图或树、复合对象；上下文寄存器、向量库、图数据库、多引擎存储 |
| `S`：抽取 | 原始对话和轨迹如何变为可存记忆？ | 原文拼接、无模式事实抽取、受 schema 约束的实体—关系抽取 |
| `Q`：检索与路由 | 针对当前问题如何找到并组合证据？ | 注意力读取、向量近邻、图遍历、LLM 工具调用规划、混合多阶段检索 |
| `U`：维护 | 新信息如何更新、压缩、淘汰、消冲突？ | 时间多版本、容量淘汰、LLM 语义合并、离线参数优化 |

这比“记忆分短期/长期”更可操作：系统出错时可以定位是写入时丢了细节，检索时没组装全证据，还是维护时把时间线压扁了。

### 3.1 表示与存储：结构带来能力，也带来维护成本

论文归纳出三类逻辑表示：

1. **Token 级序列**：事实文本、摘要、Embedding 或 KV Cache。简单、低成本，但缺少显式关系。
2. **图与树结构**：知识图谱能表达实体、关系和时间；层级树在叶子保留细节、在父节点提供摘要，适合跨会话导航。
3. **异构复合对象**：把文本、时间戳、标签、向量、关系等封装到一起，并结合向量、关系、图等多个后端。

物理存储也分为三档：只保留在上下文/KV Cache 的瞬态存储；单一专用引擎（向量库、图数据库或 SQL）；以及多引擎异构存储。后一类表达力更强，但写入时的索引构建、多库同步和全局整理会迅速放大成本。

### 3.2 抽取、检索和维护：记忆生命周期的三处关键分岔

- **抽取**：从原始序列直接保留，到抽取自由事实，再到按 schema 生成三元组或结构化记录。后两者更便于索引，但每次摘要、压缩、事实化都是一次不可逆的信息损失。
- **检索**：单纯向量 Top-K 擅长找最像的一条；图遍历、树检索和混合路由更适合拼接分散证据。LLM 可通过工具调用或查询改写充当查询规划器。
- **维护**：时间多版本通过 `valid_from/valid_to` 或失效标记保留历史；容量淘汰直接删旧项；语义合并用 LLM 去重、总结或发出 CRUD。维护策略决定系统面对“原来住巴黎、后来搬到伦敦”时能否正确回答带时间条件的问题。

## 4. 评测设计：不仅问“答对了吗”

作者在 LoCoMo、LongMemEval、DB-Bench 等基准上考察五个问题：

1. **端到端有效性**：长对话问答、跨会话记忆、带数据库操作的过程执行是否成功？
2. **检索保真度**：正确答案所需的源证据，是否真的被取回？
3. **更新鲁棒性**：事实修订后，系统能否选择当前有效状态并进行时间推理？
4. **长程稳定性**：证据与问题相隔许多会话后，性能是否仍能维持？
5. **运行成本**：构建索引和查询的摊销延迟、效用—成本边界如何？

这套设计的重要之处在于把“模型最后生成得好不好”和“记忆层实际做得好不好”分开。例如，数据库任务中字符串 Exact Match 最好并不代表任务执行成功率最高；跨会话问答则更需要 ROUGE-L、LLM Judge 等能容纳释义答案的指标。

## 5. 主要发现：没有通吃的记忆架构

### 5.1 结论一：记忆架构必须服从工作负载瓶颈

论文没有发现全场景赢家。

- 在跨会话、分散事实和事件顺序推理的 LongMemEval 中，显式时间或图结构更强：Zep 的 LLM Judge Accuracy 达到 **48.0**，Cognee 的 ROUGE-L F1 达到 **35.3**。
- 在长而语义连贯、要求精确落点的 LoCoMo 中，粗到细过滤的 MemOS 取得最高 **11.5 EM**。
- 在依赖中间状态变化和操作顺序的 DB-Bench 中，保留原始轨迹尤为关键；Long Context 的 EM 为 **48.2**，MemoChat 的任务成功率为 **55.4**。

含义是：不要把图、向量、摘要或多库架构当成普适升级。跨会话拼证据要关系与时间结构；精确定位适合分层过滤；过程型任务首先要保住轨迹。

### 5.2 结论二：检索的关键是“证据集完整性”，不只是 Top-1

SimpleMem 在 LoCoMo 的 Recall@1 最高（**39.0%**），但当检索预算扩大时，结构化系统更能把分散证据收齐：A-MEM 的 Recall@5/10 为 **69.5%/85.9%**，MemTree 为 **59.7%/80.5%**。并且，随着证据距离变远，扁平 Embedding RAG 下降更明显。

这说明应分开优化两个目标：先定位一个相关入口，再扩展出足够的互补证据。只追求向量检索的 Top-1 很容易在需要多跳、跨会话合成时失败。

### 5.3 结论三：更新问题本质上是“时间有效状态”问题

在知识更新切片上，Zep 的 Substring EM/ROUGE-L F1 为 **44.4/36.8**，表现最强；在分散时间证据推理上，Cognee 达到 **18.7/35.8**；LoCoMo 的最新状态精确匹配由 MemOS 以 **8.9 EM** 领先。

共性是保存了可验证的时间与结构。只做事实抽取、追加写入或密集相似度检索的方案，难以区分旧陈述与新修订，容易产生论文所称的“过去的幻觉”（hallucinations of the past）。更强的回答模型能改善表述，却不能弥补检索前的时间定位错误。

### 5.4 结论四：成本由“维护范围”决定，而不只由结构决定

低成本前沿上的 LightMem 达到 **48.3** 的归一化效用、单查询 **3.67 秒**；MemTree 达到 **63.5**、**15.9 秒**。更重的结构化系统虽可获得更高效用，Cognee 与 Zep 要达到 84 以上效用时，单查询成本分别超过 **116.5 秒**和 **155.1 秒**。

真正的分界线是一次更新影响多大范围：路径局部的树聚合、分段压缩、有限范围的混合检索较可控；全图重整、多存储同步、反复重写整个记忆库则会成为长程负载的主要延迟来源。

## 6. 组件级消融给出的工程原则

论文控制变量地改变 `R/S/Q/U`，得到了一组很实用的默认策略。

| 环节 | 实验现象 | 工程建议 |
| --- | --- | --- |
| 表示与存储 | LightMem 的原始用户文本在四项指标均最好；轻压缩接近原文，但摘要明显变弱 | 保留可追溯原始证据；结构改善访问，不能复原已丢信息 |
| 抽取 | 轻量、覆盖更广的抽取通常更稳；过细的 LLM 抽取会伤害组合推理 | **早写入、晚过滤**：写入时少做激进筛除 |
| 检索与路由 | 平衡的稠密—稀疏融合优于偏稀疏；显式规划优于直接检索；再加反思没有继续增益 | 使用轻量查询规划和均衡混合检索，避免无目的多轮反思 |
| 维护 | 保守合并优于延迟刷写和强制单主题粗摘要 | 及时、局部、保守地合并；为冲突保留时间版本与来源 |

其中最值得记住的因果链是：**抽象层越多，损失原始证据的机会越多。**摘要、压缩、事实抽取并非天然有害，但应只在能明确换得容量、延迟或可检索性的地方使用，并始终给关键记忆保留原文或可回溯来源。

## 7. 如何把结论用到系统设计中

可以将论文转化为一份简化的选型清单：

1. **个人助理与跨会话客服**：优先时间戳、多版本和实体关系；不要只存“当前偏好”的覆盖结果，要保留何时生效与来源。
2. **长文档/长对话问答**：保留原文片段或低损压缩，采用先粗筛再精排；对要精确回答的事实不要只保存摘要。
3. **工具调用、数据库操作和工作流 Agent**：将工具轨迹视作一等记忆，保留状态变迁和操作顺序，不能仅抽取最终事实。
4. **低延迟在线系统**：优先局部更新、分段存储和有界检索；慎用会触发全库重组的图合并与多库同步。
5. **评测阶段**：至少同时衡量任务结果、证据召回、更新后的时间正确性和端到端成本；只看最终 F1 很容易选错架构。

## 8. 局限与延伸

论文的结论是严格的横向评测结论，而不是对所有未来记忆系统的最终定论。系统实现、所选模型、提示词和基准分布都会影响绝对得分；部分图表中的不同系统也并非完全相同的功能集合。更重要的是，当前公开基准仍以文本记忆为主，对多模态记忆、隐私与权限隔离、并发一致性、跨 Agent 共享记忆等生产问题覆盖有限。

但其贡献已经足够明确：评价 Agent Memory 时，应从“它能否帮模型答题”升级为“它能否像一个可靠的数据系统一样，持续保存、定位、更新并治理智能体状态”。真正 Agent-native 的记忆，不是堆叠更多索引与摘要，而是在正确的负载下，以可验证的证据和可接受的成本完成整个生命周期。
